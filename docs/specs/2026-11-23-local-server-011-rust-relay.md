## User rulings (requirements; every review checks the result against these)

- **R1** Local mode is a locally run taskmaster server, one per project, shared by every Claude Code session on it; it replaces per-session stdio servers as the default.
- **R2** The point is RAM. One server for all sessions, and the per-session piece must be as small as we can make it.
- **R3** Seamless: no manual start step; opening a session just works.
- **R4** No separate terminal or console window, ever (this covers every process the relay or its helpers start).
- **R5** The taskmaster Claude mod (taskmaster-mods) keeps working, including its "connecting" vs "offline" wording matchers.
- **R6** Scope of the release line: local server mode plus the listed team-server leftovers (unchanged by this task).
- **R7 (2026-11-23)** The per-session relay is a **tiny compiled Rust binary** (target ~2-5 MB per session), replacing `uv run ... tm_bridge.py` (58 MB per session on Windows: uv.exe 39 MB resident + Python bridge 19 MB).
- **R8** It keeps every behaviour of tm_bridge.py that the reviews made us add (inventory §2): nothing regresses to get small.
- **R9** Seamless and no console window apply to the relay itself and to everything it spawns (R3, R4 restated for this task).
- **R10** The mods keep working through the relay (R5 restated).
- Standing: no push, PR or master merge without the user's go-ahead; Reuse Before Writing (one implementation of each behaviour where possible); server-first; public binaries carry no local paths or user names.

## 1. Decision

**The relay owns the session's hot path; the existing Python code owns every policy decision and every rare path.** Concretely:

- **Rust (`bin/tm-relay[.exe]`, resident, one per session):** stdio framing, the HTTP/1.1 + SSE relay to the loopback server, the GET stream, the lazy handshake (immediate initialize, held calls, cancellation of held calls, list hold, list_changed), the retry rule and its wording, reconnect + replay, session DELETE, size caps, loopback assert, and the **delegation** of a whole session to a child MCP process (stdio fallback, team clones, emergency lever). Delegation is not the `TASKMASTER_BRIDGE_HANDOFF` mode that the live gate proved breaks Claude Code: the relay never exits while a child runs. It stays the process Claude Code spawned and pumps both ways until stdin EOF.
- **Python (`tm_bridge.py --relay-helper`, transient, started by the relay at boot and on each reconnect):** root resolution, every opt-out and fallback reason, team-clone detection, private-file checks, discovery, token, status probe, skew matrix, retire, successor and lease waits, the hidden double-spawn launch with its env scrub and result-file statuses, the uv environment cache, the stale launch-file sweep, and the package digest. It prints its answers as JSON lines on a pipe and exits after its last line (§3). The relay does not use the handshake cache (§12, M1): it serves the shipped `tm_bridge_handshake.json`, which a test pins to the live registration.
- **Python, unchanged (`tm_bridge.py` full mode):** the team-clone relay (TLS, member key, 401/403, no-key tool list) as a delegate child, and the whole bridge on platforms that have no relay binary yet (macOS until §4.5 is done).

Why this split:

1. **Reuse Before Writing.** Discovery, skew, retire, launch and the private-file checks are the code the reviews hardened most (bridge review M6/M7, cold M1-M4, 002 M4, startup tests). They depend on `taskmaster.localserve`, `server_fence`, `ownership.verify_private` (Windows ACL walk), `package_digest` and `is_native_store` (SQLite). Porting them would make a second copy of the security-relevant rules in another language. The helper keeps exactly one copy; the relay only consumes its verdict.
2. **The cost of delegating is paid once per boot, not per session lifetime.** Measured: `uv run --no-project --python ">=3.11" python` + importing `tm_bridge`, `taskmaster.localserve` and `taskmaster.root` takes **340-420 ms warm** (3 runs). Today's bridge spends the same time before it can answer `initialize`, so the first answer is no later than today. The helper is transient: it exits once it has printed line 2 (within about a second, or after a launch it waited for), and a black-box test asserts it is gone (§7.1). R2 is about what stays resident. Its RAM (estimated 50-70 MB: uv plus Python with the localserve imports) and the peak with 8 sessions booting at once are measured in the acceptance probe (§7.4).
3. **Rare paths stay in one place.** TLS in Rust would mean rustls/webpki (MBs and a new trust-store story) or schannel FFI, for a path (team clones) that already works in Python. The stdio fallback is a child process either way.
4. **The relay stays std + serde_json.** Measured spike (same profile as the release build): 200-300 KB binary, **0.92-0.99 MB private bytes** resident with three threads and a held loopback TCP stream (§5).

Rejected alternatives: (a) port everything to Rust: the binary grows little but the policy code doubles, against R8 and the reuse rule; (b) Rust fast path for the common case (read local.json, verify ACL, probe, same digest) with Python only for the rest: saves ~0.4 s of helper time per boot but duplicates verify_private, read_discovery, the lease probe and package_digest. Kept as a possible follow-up only if the live gate shows the boot latency matters, which today's numbers say it does not.

**Lightvault reuse: none, deliberately.** Lightvault's Rust crates (`lightvault-server`: tokio + axum + rusqlite) are a server stack. The shared server core being extracted there is for servers. The relay is a synchronous client shim. A tokio runtime alone costs more resident memory than the whole relay budget, and Lightvault has no MCP or HTTP client to reuse. The relay uses std (threads, `TcpStream`, `Command` with `creation_flags`) plus `serde_json` and nothing else. If a Rust MCP client ever appears in the shared core, the relay can move onto it.

## 3. The helper protocol (v1)

`tm_bridge.py --relay-helper` (new mode, ~60 lines over existing functions). Started by the relay with its own environment plus `TASKMASTER_BRIDGE_DISCRIMINATOR`, cwd = the relay's cwd, stdin/stdout piped, stderr inherited, hidden (§4.3). Command: `uv run --no-project --python ">=3.11" python <plugin>/tm_bridge.py --relay-helper` (today's interpreter rule); tests override it with `TASKMASTER_RELAY_HELPER` (a JSON argv), honoured only when `TASKMASTER_BRIDGE_TESTING=1`.

Lines on stdout (one JSON object each, `"v": 1`):

1. `{"v":1,"kind":"session","root":..., "mode":"local"|"team"|"fallback", "reason":str|null, "build":{"version","digest"}|null, "plugin_dir":...}`. Written as soon as the fast checks are done (resolve_root, `_start_team_bridge`'s detection without starting it, fallback_reason, build). No handshake cache (M1, row 26). Any exception → `mode: fallback` with `local server unavailable: <repr>` (today's bridge_main rule).
2. Only for `mode: local`: `{"v":1,"kind":"endpoint","url":..., "token":..., "build":{...}}` or `{"v":1,"kind":"unavailable","reason":...}` once `ensure_server` settles (it may launch and wait up to 180 s). The helper then exits 0. For `team` and `fallback` it exits 0 after line 1.

The relay closes the helper's stdin as soon as it has the last line it needs (line 1 for team/fallback, line 2 for local) and reaps it. A helper still alive 5 s after its last line is killed and logged (`tm-bridge: relay helper did not exit; stopped`), because a lingering helper silently undoes R2 (M2).

**Reconnects (`--relay-helper --ensure-only`, M3):** one helper per reconnect episode, not per attempt. It prints no line 1 and reads `{"op":"ensure"}` lines on stdin; each is answered with an `endpoint` or `unavailable` line (one `ensure_server` call, with its retire, successor and lease waits). The relay sends one `ensure` per reconnect attempt and closes the helper's stdin when the episode ends (reconnected, switched to the fallback, or budget spent). On upgrade day 8 sessions therefore run at most 8 helpers for the episode instead of one per attempt; the acceptance probe measures a retire with 8 sessions (§7.4).

A helper that exits without the line the relay waits for, or prints `v` other than 1, counts as ServerUnavailable and is logged with its exit code; at boot that means delegating to the Python bridge (it re-decides everything itself), so a relay/helper version mismatch degrades to today's behaviour instead of failing.

**uv resolution (M5).** The relay finds `uv` itself: on Windows it searches PATH for `uv.exe` only (no PATHEXT, no `.cmd`/`.bat`, never the relay's own directory or the cwd first); on POSIX, PATH as execvp does. When no uv is found, or the helper cannot be spawned, the relay does not hold calls: held and new requests are answered at once with `taskmaster bridge error: uv not found on PATH` (today's Python text shape), initialize having been answered from the shipped handshake. A black-box test pins this ("uv missing": a held tools/call is answered within 2 s, not after HOLD_BOUND).

### 3.1 Boot sequence and initialize (I1)

The relay spawns the helper at once, then reads stdin. When the client's `initialize` arrives it waits for line 1 for up to INIT_WAIT (2.0 s), then:

| Line 1 | initialize is answered by | Then |
|---|---|---|
| `team`, within INIT_WAIT | **the team server**: the relay starts the Python bridge child (#31) and forwards the client's own initialize line, unchanged, and every later line; it relays the child's answers, including the initialize result. Nothing is replayed or swallowed | The relay is a pure pump for the rest of the session |
| `local`, within INIT_WAIT | the relay, from the shipped handshake (#26) | Lazy boot (#27, #28) once line 2 arrives |
| `fallback`, within INIT_WAIT | the relay, from the shipped handshake | Delegate to the stdio server with replay (#30). Forwarding is not used here: the instructions are the same build's (one `instructions=` site, backlog_server.py), and forwarding would make initialize wait on `uv run backlog_server.py`, which takes about 30 s on a cold environment, close to Claude Code's connect timeout |
| none within INIT_WAIT (cold uv fetching a Python) | the relay, from the shipped handshake | When line 1 then says `team`: delegate with replay and swallow the child's answer, logging once `tm-bridge: team clone detected after initialize; the team server's instructions apply from the next session`. Otherwise as above |
| helper exited before line 1 | the relay, from the shipped handshake | Delegate to the Python bridge with replay (it re-decides) |
| helper could not be spawned (no uv) | the relay, at once, from the shipped handshake | Every request is answered at once with the uv error (§3, M5). There is nothing to delegate to, since the Python bridge needs uv too; the SessionStart hook already warns that uv is missing |

The latency of the first answer is unchanged from today: today's bridge also runs these checks before it answers initialize. Black-box tests: a team clone's initialize result equals the fake team server's (a sentinel in `instructions` and `serverInfo.name`), not the shipped file; with `TASKMASTER_BRIDGE_TEST_BOUNDS` setting INIT_WAIT to 0, the late path logs the note and a write still lands on the fake team server.

## 4. Launch: one static .mcp.json command, no resident wrapper (spike results)

### 4.1 The command

```json
{"mcpServers": {"tm": {"command": "${CLAUDE_PLUGIN_ROOT}/bin/tm-relay"}}}
```

`bin/` holds `tm-relay.exe` (Windows), `tm-relay` (the sh entry: POSIX, and Claude Code's own fallback on Windows when the exe is gone; LF, mode 100755), and `tm-relay-<os>-<arch>` binaries (`uname -s` lowercased, `uname -m`: `linux-x86_64`, `linux-aarch64`, later `darwin-arm64`, `darwin-x86_64`). The sh entry:

```sh
#!/bin/sh
# User intent: the plugin's tm entry on POSIX (and Claude Code's sh fallback on Windows) - exec the relay binary for this OS/arch so nothing else stays resident; with no binary, or one that does not run, exec today's Python bridge.
dir=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)
if [ "${TASKMASTER_RELAY:-}" != python ]; then
  case "$(uname -s)" in
    MINGW*|MSYS*|CYGWIN*) bin="$dir/tm-relay.exe" ;;
    *) bin="$dir/tm-relay-$(uname -s | tr '[:upper:]' '[:lower:]')-$(uname -m)"
       [ -f "$bin" ] && [ ! -x "$bin" ] && chmod u+x "$bin" 2>/dev/null ;;
  esac
  if [ -x "$bin" ] && "$bin" --version </dev/null >/dev/null 2>&1; then exec "$bin" "$@"; fi
  [ -f "$bin" ] && echo "tm-bridge: $bin is present but does not run; using the Python bridge" >&2
fi
exec uv run --no-project --python ">=3.11" python "$dir/../tm_bridge.py" "$@"
```

Rev 2 changes to the entry (I2, M6): the Windows branch execs the exe only when it exists and runs, else falls through to the Python bridge, so a quarantined exe degrades instead of taking tm down (measured, §4.2); every platform probes the binary with `--version` before exec, so a binary that is present but cannot run (wrong arch, corrupt, blocked) also falls through instead of a failed exec ending the non-interactive sh; the probe's stdin is `/dev/null` so it can never read bytes of Claude Code's first message; `TASKMASTER_RELAY=python` applies on every branch. `tm-relay --version` must print and exit without reading stdin (it writes to a pipe here, which the GUI build can do, §4.2). The probe costs one extra process start, only on POSIX and on the Windows sh fallback path.

### 4.3 Hidden children (R4, R9)

- Helper and delegate children: `CREATE_NO_WINDOW` (std `CommandExt::creation_flags`), stdin/stdout piped, stderr inherited (helper) or inherited (delegate child, so its notes reach the MCP log as today). No job object, no breakaway: the helper does the double spawn exactly as the bridge does now, so the server's detachment from Claude Code's job is unchanged (re-verified in the live gate, §7.4).
- **No inherited Claude Code pipes (M4).** At startup the relay clears `HANDLE_FLAG_INHERIT` on its stdin, stdout and stderr handles (`SetHandleInformation`, a one-line extern, no new crate). Rust spawns with `bInheritHandles=TRUE`, so without this the helper chain (uv, then python, then the launcher) would inherit Claude Code's pipe ends, and a helper mid-launch (bounded 180 s) could hold them open after the relay is gone. A child's stderr is still Claude Code's pipe: `Stdio::inherit` duplicates an inheritable copy for the child only (verify against the pinned std; a cargo test spawns a child and checks that it holds no handle to the relay's stdin pipe). On POSIX the same holds through `O_CLOEXEC`, which Rust sets on every fd it opens; fds 0-2 are replaced by the child's own pipes or dup2'ed for inherited stderr.
- uv started with `CREATE_NO_WINDOW` owns a windowless console; the python it starts inherits it (today's bridge path, already live-verified); the launcher and server use CREATE_NO_WINDOW themselves.

Run /mcp to reconnect.`). From then on Claude Code finds no exe and the measured sh fallback applies; a plugin update restores the file. (Build note, after lane review: the probe runs detached so SessionStart never waits on it, and the notice moves to the next session start, shown once through the hook's systemMessage with a `.blocked.noticed` marker; the blocked session itself already shows tm failed.) Whether `/mcp` reconnects at once or Claude Code's ~15-minute failed-connect memory applies first is a live-gate check (§7.4 (9)).

`tests/fixtures/relay_parity.json` maps every §2 row that exists twice (5, 16-28, 30, 32, 33) to the black-box test functions that cover it. `tests/test_relay_parity.py` fails when: a duplicated row in the §2 table (parsed from this spec's markdown: rows whose "Where" names Rust) has no entry; an entry names a test that `tests/test_relay_blackbox.py` does not define, or one that is not parametrized over both relays; or the **pin** no longer matches. The pin is a sha256 over the source of the Python Bridge's duplicated functions (located by name with `ast`, so a reformat elsewhere does not trip it). A Python fix to a duplicated row therefore cannot land without touching the parity file, whose failure message says to port the fix to `relay/` and add or extend the black-box test, then re-pin.

## 8. Risks and rollback

1. **POSIX exec bit lost on install** → the sh entry cannot be executed and the session has no tm (worse than today). Git preserves 100755; whether Claude Code's plugin cache copy preserves it is unverified. Mitigation: static check on git modes; G-exec (§7.4) is a required gate before the switch, with "keep the uv entry" as its failure outcome; rollback below. Related, pre-existing and out of this task's scope: `hooks/session-start.sh` and the other `hooks/*.sh` are git mode 100644 but `hooks.json` runs them directly as commands, which on POSIX needs the exec bit (reported to the orchestrator, not changed here). Residual on macOS: Gatekeeper or xattrs on directory-marketplace copies, unverified until §4.5's CI job.
2. **Claude Code stops resolving `.exe` for an extensionless command on Windows** → measured fallback: it runs the sh entry, whose MINGW branch execs the relay (+6 MB sh resident). Degrades, does not break.
3. **Two relay implementations drift** (Rust; Python for no-binary platforms and as TeamBridge's base). Mitigation: §7.1 runs one suite against both. Follow-up: once macOS ships binaries, retire the Python local relay path (Python keeps the helper and TeamBridge).
4. **A child spawned without CREATE_NO_WINDOW from the GUI-subsystem relay would show a console** (R4). Mitigation: one spawn function, unit test, live-gate inspection.
5. **Boot latency under contention** (8 sessions start at once, 8 helpers): bounded by INIT_WAIT 2.0 s, then the shipped handshake; held calls wait as today. Measure in the acceptance probe.
6. **Unsigned binaries and antivirus/SmartScreen:** git-installed files carry no Mark of the Web, so SmartScreen should not apply; Defender heuristics on a small unsigned exe are unmeasured. Mitigation: the release-time Defender scan (§6). Code signing is out of scope.
6a. **Exe quarantined or blocked after install (I2).** Quarantine (file removed): Claude Code runs the sh entry, which execs the Python bridge; tm keeps working at today's 58 MB (measured, §4.2). Present but unrunnable (ACL, policy, damage): measured, Claude Code does not fall back and that session has no tm; the SessionStart self-heal (§6, D5) moves the exe aside so later connects take the sh path. Residual: the first session after the block, plus Claude Code's failed-connect memory (about 15 minutes, live gate) if `/mcp` does not bypass it.
6b. **Plugin updates while relays run (Windows, M7).** A running exe cannot be overwritten or deleted. Versioned cache dirs avoid the normal case. A same-version reinstall, the cleanup of an old version dir, and a checkout merge that changes `bin/tm-relay.exe` under a `--plugin-dir` session fail while sessions are open; the fix is to close those sessions (the merge case is a developer-only path). Live-gate item (10).
7. **Server lifetime under Claude Code's job object:** the chain gains one hop (relay → helper → launcher → server). Breakaway flags are unchanged in the helper; re-verify in the live gate (3).
8. **Leaked paths in public binaries:** remap flags plus a test.

**Rollback (one line):** set the tm entry back to `"command": "uv", "args": ["run", "--no-project", "--python", ">=3.11", "python", "${CLAUDE_PLUGIN_ROOT}/tm_bridge.py"]`. tm_bridge.py stays fully working in its full mode throughout (it is the no-binary path and the delegate target), so the revert restores 7.5.0's behaviour exactly. Without a file edit: `TASKMASTER_RELAY=python`.
