# team-server-034: one shared query snapshot per store revision

Status: design, for Opus security review. Author lane: design-034 (2026-11-22). Branch context: feat/local-server.
Inputs: task team-server-034; rulings.md 2026-11-12 (I-1 rounds 1-3, the "mitigate, then go live" ruling); 2026-11-17 60-agent probe;
docs/specs/2026-11-22-local-server-design.md (local profile, acceptance probe "p95 of the mods' read calls under 3 s").

## 1. Problem

Every backlog_query (native store) runs taskmaster/native/compatibility.py:query: it rebuilds the legacy SQL surface
(entities from entity_core via iter_entities, changes from domain_events, entity_fts from document_search, plus
projection, sessions, linear_queue, entity_paths, links, related, handover_tasks) into a private :memory: database,
serializes it, pipes the bytes to a query_worker child, which deserializes them and runs the statement. Cost per call:
the whole copy (Python, under the GIL, in the daemon), about 2 x S of daemon memory and 2 x S in the worker, where S is
the snapshot size. Mitigations in force (ruling 2026-11-12): SNAPSHOT_MAX_BYTES 32 MiB, worker cap 96 MiB + 2 S on Linux,
HEAVY_TOTAL 2 / HEAVY_PER_KEY 1 under MemoryMax=1G, OOMPolicy=continue. Measured p95 10.1 s in the 60-agent probe.

The local server (one serve process per project, ~8 sessions, MemberQueryScope and HeavyCalls off) runs the same path,
and the mods issue backlog_query for phase lists, linked tasks and the restore pane, so concurrent queries are normal there.

## 3. Options compared

**(a) One read-only snapshot file per store revision, shared by workers.** The existing copy code builds it once per
revision into an owner-only file; every statement at that revision opens it read-only. Removes the per-call copy (CPU,
GIL), the daemon's 2 S per call (the build is one bounded stream at a time, ~12-27 MiB), and the worker's 2 S (now a fixed
cache). Keeps the exact SQL surface, the clipping, the empty private tables and the authorizer unchanged. Costs: a cache
with a lifecycle (build, publish, lease, delete), disk of S per live file, a rebuild per revision that is queried.

**(b) The worker opens store.db read-only.** Same worker cost as (a), zero build. Rejected, for three reasons:
1. The surface does not exist in store.db. entities.doc is a JSON document assembled in Python (migrate._reconstruct_one
   over entity_core, *_operational, entity_extensions, relations); changes is domain_events; entity_fts is document_search.
   After cutover the store's own legacy entities/changes tables are stale staging copies, so a direct open answers from
   stale data. Serving the surface from store.db needs views or a rewrite of the surface.
2. It widens what one authorizer bug exposes from "the compat tables" to every private table: command_receipts,
   sync_state, id_reservations, projection_base (whole file bodies), path_claims, meta. Views reintroduce view-source
   exemptions, the CTE-impersonation class compatibility.py was built to remove (its docstring; re-review I-1).
3. WAL mechanics: mode=ro needs a -shm it cannot create (hook_reads.connect_ro avoids mode=ro for that reason); immutable=1
   on a live WAL store is unsafe (ignores the WAL, may read a torn state). A reader inside the worker also pins the WAL
   against checkpoints for up to the deadline, and a killed worker is a reader the daemon does not control.

**(c) Simpler alternatives.**
- c1, cache the serialized bytes in daemon memory per revision and pipe them to each worker: removes the per-call copy
  CPU, but the daemon holds S per live revision and every worker still needs 2 S (8 local workers: ~540 MiB). The memory
  problem, which is what forces HEAVY_TOTAL 2, stays. Rejected as the end state; it is a fallback if file handling on
  Windows proves unworkable (risk R3).
- c2, copy only the tables the statement names: entities dominate and nearly every statement names it. Rejected.
- c3, SQLite backup API of store.db into a file: copies private tables, not the surface. Rejected.

**Chosen: (a).** It is the only option that removes both the per-call CPU and the per-call memory while keeping the exact
SQL surface and the authorizer's model (no new schema, no view exemptions, no live-store reader in an untrusted child).
Measured: per-call cost goes from ~0.25 s CPU + ~135 MiB (daemon + worker) to <16 ms + ~16 MiB; 8 concurrent local calls
from ~19 s each (deadline failures in practice) to 0.22 s wall.

## 4. Design

### 4.1 What the shared base holds

The base snapshot has the same schema as today's per-call snapshot, built by the same copy and clip code (VALUE_COPY_MAX,
the _Budget batches, the deadline checks), with one change: **sessions, linear_queue and projection are created empty**,
like meta and projection_base today. Reasons: (1) they change without bumping the store revision (heartbeats, export
bookkeeping, Linear push attempts), so a revision-keyed file would serve them stale; (2) they are the host-private tables
(query_guard.HOST_PRIVATE_TABLES): a member's worker then never receives their rows at all, a defence beyond the
authorizer that today's design lacks (today the member's snapshot carries them and only the authorizer refuses them).

Callers whose authorizer may read a host table (operator on the team server, the local profile, solo stdio) get a
**per-call overlay**: those tables' rows, read in the caller's own read transaction, sent with the request (at most
OVERLAY_MAX_BYTES), loaded by the worker into TEMP tables of the same names before the authorizer is installed.
Unqualified names resolve temp before main, so the statement sees fresh rows; main.sessions reads the empty table.
temp is already in Authorizer._SCHEMAS, so the authorizer rule is unchanged. The overlay is built only when the
caller's readable set includes a host table and the masked statement names one (word match on query_guard._mask
output, which keeps double-quoted and bracketed identifiers; SQLite has no way to name a table other than by its name),
so the mods' entity reads never pay for it.

### 4.2 Key and freshness

Key: (store_id, revision, SNAPSHOT_FORMAT). revision = hook_reads.revision (MAX(domain_events.seq) + graph_repairs),
extended with a fingerprint of the derived tables the base copies (COUNT(*), MAX(rowid) of entity_paths, links,
related, handover_tasks, document_search_docsize), read in the same read transaction as the copy (risk R1).
SNAPSHOT_FORMAT is a code constant (bumped when the surface or VALUE_COPY_MAX changes; files never outlive the process).

A call arriving at revision r (read inside its own call.read() transaction, so it includes the caller's own committed
writes) may use a published snapshot s only if s.store_id matches and either s.revision == r, or s.revision > r and s's
build *started after the call arrived*. The second clause gives read-your-writes without accepting a snapshot from
before a store restore that lowered the revision under the same store_id.

### 4.3 Lifecycle

One QuerySnapshots object per store per process (serve daemon: created in start, closed in stop; stdio/solo: created on
first query, closed at exit).

- **Directory.** coordinator.ownership.private_directory(root, "query-snapshots") (owner-only, never a link, inside
  .taskmaster/local, which is gitignored), then a per-process subdirectory p-<pid>-<nonce>/ holding an owner.lock taken
  with the same kernel lock ownership.ownership_held probes. Never a tmpfs or /tmp path: tmpfs pages are charged to
  the unit as unreclaimable memory.
- **Build.** One builder thread per store with its own read-only connection (coordinator.protocol.connect(readonly=True)).
  Single flight: callers needing a revision newer than the current one wait on the next build; a build serves every call
  that arrived before it started. Builds never overlap and are spaced at least BUILD_MIN_INTERVAL apart. The build opens
  one read transaction (Repository.snapshot, WAL snapshot isolation), reads key and rows in it, writes
  r<revision>-<nonce>.partial (exclusive create, journal_mode=OFF, synchronous=OFF, cache_size 8 MiB), streams batches
  under the byte budget and its own deadline BUILD_SECONDS (not a caller's: a caller that gives up does not waste a build
  others wait for), commits, closes, marks the file read-only, renames it with os.replace to r<revision>-<nonce>.db, and
  only then publishes the entry. A failed build (StoreTooLarge, deadline, disk floor, I/O) deletes its partial and hands
  the error to its waiters; StoreTooLarge keeps today's message.
- **Share.** A call takes a lease (refcount) on the entry, sends the worker the file path and the optional overlay, and
  releases the lease when the worker answers or is killed. The worker opens file:<path>?mode=ro&immutable=1, sets
  mmap_size 0 (the file must not count against RLIMIT_AS) and cache_size 8 MiB before the authorizer, and accepts only
  a path inside the snapshot directory matching the published name pattern (never .partial).
- **Invalidate.** Lazily: there is no watcher. A newer published entry supersedes older ones; a superseded entry with no
  lease is deleted at once, a leased one when its last lease is released.
- **Cleanup.** Delete failures (Windows: a file still open in a worker being killed) go to a retry list run at every
  release, publish and close. close() deletes the subdirectory. At start, the sweep deletes every p-* subdirectory whose
  lock is not held (a crashed process) and nothing else.
- **Disk.** At most 1 current + 1 building + leased superseded files per process; a superseded file lives at most one
  statement deadline + kill grace after its successor is published. Bound: (concurrent statements + 2) x SNAPSHOT_MAX_BYTES
  per process; team server 5 x 32 MiB = 160 MiB; local 6 x 32 MiB.

### 4.4 Security properties kept (and how)

1. **Denied tables stay denied.** The authorizer, its readable/declared/excluded rules, MemberQueryScope's
   READ_ENDPOINT_TABLES restriction (team-server-026), and the served-only DENIED_FUNCTIONS keyed on
   query_guard.serving() (client.ORIGIN_PROVIDER) are unchanged and still run inside the worker. In addition, a member's
   worker holds no host-private rows (base empty, no overlay for a member), and meta / projection_base stay empty.
2. **No memory exhaustion.** The daemon never holds a snapshot: the build streams batches into a file (measured 12-27 MiB
   peak), one build at a time, independent of the number of callers. The worker's cap becomes fixed
   (WORKER_MEMORY_BYTES; the 2 x S term is removed). Answer limits (RESULT_MAX_BYTES, MAX_ANSWER_BYTES) are unchanged.
3. **No disk exhaustion.** Per-file cap (the byte budget, enforced while building), file-count bound (4.3), a free-space
   floor checked before each build, and on Linux the worker gets RLIMIT_FSIZE WORKER_TEMP_FILE_MAX with SIGXFSZ ignored, so
   a sort that spills (temp_store=FILE, kept) fails with "database or disk is full" instead of filling the disk.
4. **No other revision's partial state.** A snapshot is one read transaction of the live store (consistent at its
   revision); a partial file is never published or accepted by a worker; immutable=1 is safe because a published file is
   never written again (read-only attribute; the builder has closed it before rename).
5. **No cross-call leakage.** The base is identical for every principal (members see all entities today; no row-level
   visibility exists); per-principal data (host tables) travels only in the caller's own overlay.
6. **No CPU monopoly.** Builds are single-flight, spaced and bounded by BUILD_SECONDS; statements keep the deadline kill;
   HeavyCalls per-key/total limits stay on the team server.

### 4.5 Limits (initial values)

| name | value | note |
|---|---|---|
| SNAPSHOT_MAX_BYTES | 32 MiB (unchanged) | now bounds build time and disk, not memory; raise only after Linux measurement |
| BUILD_SECONDS | 15 s | store100 (126 MB) built in 1.1-3.0 s here |
| BUILD_MIN_INTERVAL | 1.0 s team, 0.25 s local | caps build duty cycle at ~22 % of a core on a 32 MiB store |
| OVERLAY_MAX_BYTES | 4 MiB | refused past it with a clear error |
| WORKER_MEMORY_BYTES (Linux RLIMIT_AS) | 96 MiB fixed | re-measure VmSize with an open file snapshot on WSL / the team host |
| WORKER cache_size / mmap_size | 8 MiB / 0 | |
| WORKER_TEMP_FILE_MAX (Linux RLIMIT_FSIZE) | 256 MiB | |
| DISK_FLOOR | 4 x SNAPSHOT_MAX_BYTES + 512 MiB free | build refused below it |
| HEAVY_TOTAL | 2 -> 3 (team) | budget: daemon 300 + build 32 + 3 x (96 worker + 32 answer frame + 8 rows) = 740 MiB of 1,024, below today's 770 with 2; confirm on Linux before changing |
| HEAVY_PER_KEY | 1 (unchanged) | |
| local concurrent statements | 4 (pool semaphore, wait up to the deadline) | the local profile has no HeavyCalls; 8 sessions x mods polling |

### 4.6 Local profile: what isolation it keeps

Keeps: the worker process with its deadline kill (one runaway statement must not stall eight sessions' tools on the
shared server), the fixed SQLite limits, the read-only authorizer with the full READABLE_TABLES (no member restriction),
the shared snapshot and the overlay, and a pool-level bound of 4 concurrent statements. Drops (as 002 decided):
MemberQueryScope, HeavyCalls. The deny list follows query_guard.serving() unchanged; whether the local daemon installs
ORIGIN_PROVIDER (and so loses hex/printf like a team server) is local-server-002's call (open question Q1). The Windows
worker has no memory cap, as today (risk R7).

## 5. Failure modes

| failure | behaviour |
|---|---|
| store past SNAPSHOT_MAX_BYTES | build stops at the crossing row, partial deleted, today's StoreTooLarge message to every waiter; the next call retries only after the revision changes (negative entry per revision) |
| build deadline or I/O error | partial deleted; waiters get "query snapshot could not be built: <reason>"; next call retries |
| disk below floor | build refused with a message naming free space; nothing written |
| caller deadline while waiting for a build | "query exceeded 5 s" as today; the build continues for others |
| worker killed (deadline, cap) | lease released; file kept for other calls; WorkerStopped as today |
| snapshot file missing or unreadable at open | worker answers an error; the entry is dropped and the call fails once ("retry"); no fallback to a per-call copy (that path is deleted, so there is one code path to review) |
| Windows delete of an open file fails | retry list; swept at close and next start |
| daemon crash | files left in its p-* subdir; next start's sweep deletes them (lock not held) |
| two processes on one store (stdio fallback + server) | separate subdirs and builds; correct, only less sharing |
| store restored to a lower revision, same store_id | the build-started-after-arrival rule rejects old snapshots; a fresh build serves |

## 6. Risks

- **R1 High impact / medium likelihood: revision key misses a change** (a path that rewrites a base table without an
  event or graph_repairs bump, e.g. an FTS rebuild or relation repair), so a stale snapshot is served. Mitigation: the
  derived-table fingerprint in the key; test T3 over every write family; a test-only verify mode that rebuilds and
  compares digests. Staleness is a correctness bug, not a confidentiality one (same rows a member may read).
- **R2 Medium: daemon CPU/GIL under write churn.** With 60 agents writing, nearly every query may need a new revision;
  builds are serialized and spaced, but each is Python under the GIL (0.28 s at 31 MB here). If the probe shows bystander
  latency, move the builder into a child process (trusted code, read-only store open via hook_reads.connect_ro, own
  memory cap); the cache contract does not change.
- **R3 Medium: Windows file semantics.** Deleting or renaming over a file a worker has open fails; immutable opens on
  Windows network or synced folders (OneDrive) are untested. Mitigation: unique names per build (no rename over a live
  file), retry list, sweep. Fallback design c1 if this cannot be made reliable.
- **R4 Medium: disk.** Bounded per 4.3, but statement temp spill is bounded only on Linux (RLIMIT_FSIZE); on Windows
  (local) it is bounded by the deadline only, as today.
- **R5 Low: immutable=1 trusts the file.** Anyone who can write the daemon's private directory can already read
  store.db; mitigated by owner-only directory, read-only attribute, published-name check.
- **R6 Low: page cache.** The snapshot's pages sit in the OS page cache, charged to the unit but reclaimable; never put
  the directory on tmpfs.
- **R7 Medium (unchanged): Windows workers have no memory cap.** Follow-up: a Job Object memory limit for query workers.
- **R8 Low (future): row-level visibility.** If members ever see only some entities, the base must be keyed by
  visibility class; the design comment in the module must say so.
- **R9 Medium: measurement validity.** Synthetic store on a Windows dev box under other lanes' load; derived tables
  empty. Numbers must be re-taken on Linux (WSL lane and the team host) before HEAVY_TOTAL changes.

## 8. Tests

- T1 Equivalence: every TABLES table and the existing backlog_query suite answer identically from the shared snapshot
  (+ overlay) and from a fresh build.
- T2 Read-your-writes: a write then a query sees it; a heartbeat update is visible to an operator query without a
  revision bump (overlay).
- T3 Revision coverage: for each write family (commands, batch, sync import, graph repair, FTS refresh, cutover helpers),
  any change to a base table changes the key; property test comparing table digests.
- T4 Single flight: 16 concurrent calls at one revision cause exactly one build; calls arriving during a build at a newer
  revision cause exactly one more.
- T5 No partial state: a build failed at each stage (injected) publishes nothing, removes its partial, fails its
  waiters; the worker refuses a .partial or outside path.
- T6 Isolation: a writer commits during the build; the snapshot equals the store at its recorded revision.
- T7 Restore: store_id kept, revision lowered: the old snapshot is not used.
- T8 Member: every existing denial test (main. qualifier, CTE shadowing of excluded names, denied functions when served)
  passes; the member worker's file has zero rows in sessions, linear_queue, projection, meta, projection_base, and no
  overlay is sent for a member (asserted on the request).
- T9 Limits: StoreTooLarge with today's text; disk floor refusal; overlay cap; BUILD_SECONDS.
- T10 Memory (Linux lane, WSL): worker refused at the fixed cap by today's bombs (FACTORED, INSTR, randomblob when not
  served); daemon growth during a 32 MiB build under 64 MiB; HEAVY_TOTAL calls together within the budget; RLIMIT_FSIZE
  stops a spilling sort cleanly.
- T11 Cleanup: superseded unleased file deleted at publish; leased one at release; Windows delete-while-open retried;
  start sweep removes a dead process's subdir and keeps a live one's; close removes its own.
- T12 Disk bound under churn: interleaved writes and queries never leave more than concurrency + 2 files.
- T13 Local acceptance tie-in: 8 concurrent mods-style queries on a ~30 MB synthetic store, p95 under 3 s.

## Review 1 resolutions (2026-11-22, review: docs/handoffs/2026-11-22-local-server-lanes/reviews/team-server-034-design-review.md)

- **I-1 Windows deletes.** Every delete clears the read-only attribute first (os.chmod to writable) and treats WinError 32 (open by a worker) as "pending". Files on the pending/retry list count toward the disk bound; while the bound is exceeded no new snapshot is built and the query falls back to today's refusal text for over-limit stores (never an unbounded build). The start sweep clears read-only and retries; T11 runs on Windows as well as Linux.
- **I-2 Local profile deny list.** Ruled: the local profile behaves like stdio. `deny_functions` comes from the serve profile: the team profile installs `client.ORIGIN_PROVIDER` as today; the local profile does not (daemon.py:376 becomes profile-dependent), so hex/printf work locally. T8 gains a local-profile case.
- **Minors taken as build requirements:** `PRAGMA temp_store=FILE` must be set before any overlay TEMP table is created (or not at all), with a test that the operator's overlay rows are visible; the worker's request frame cap is raised to at least the 4 MiB overlay limit (or the overlay limit lowered to fit) with a test at the limit; the start sweep never deletes a folder whose owning process holds its lock (take the lock first, sweep only unlocked folders). The other Minors are batched once at the end of the branch.

### Review 1 re-check resolutions (fix round 2)

- **I-R1.** The pending-delete retries run at the start of every backlog_query (cheap: a directory scan bounded by the retry list), not only on publish/release, so a store that went over the bound recovers without a restart. Over-the-bound refusals get their own message ("query snapshots are waiting for cleanup; try again shortly"), distinct from StoreTooLarge. T11 gains a case: exceed the bound with files held open, release them, the next query succeeds.
- **Local deny list (I-2 caveat).** ORIGIN_PROVIDER stays installed in both profiles (it also drives the coordinator safety checks). A separate profile-dependent `deny_functions` flag controls the served-only SQL deny list: on in the team profile, off in the local profile; tested in both (local-server-002 implements the flag).
- **Frame cap.** The worker's cap is measured on the encoded frame (JSON bytes on the pipe), sized to carry the 4 MiB overlay limit plus envelope; a test at the limit.
- **Sweep race.** A process takes its lock file before it creates its snapshot folder (lock path outside the folder, named after it); the start sweep deletes only folders whose lock is not held **and** that are older than 10 minutes.
