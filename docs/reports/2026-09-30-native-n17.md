upgraded client could meet a coordinator of the old build and run commands through it (the guide
carried a placeholder for that). The user decided:

- **Version 7.0.0; release candidate 7.0.0-rc.1.** A behavioural and schema migration is not a
  patch, and the plan forbids preassigning one. The CHANGELOG entry is titled `## 7.0.0-rc.1` and is
  retitled `## 7.0.0` at the final bump.
- **Fix the handshake** in N17 rather than document it as a limit. See
  [Build handshake](#build-handshake).
- **`backlog_sync` is tool-only.** Hand edits are imported only when an agent or operator calls
  `backlog_sync()`; nothing syncs on a schedule or at session start. See
  [`backlog_sync`](#backlog_sync).

### Build handshake (`a270fa0`)

Every IPC message and discovery record carries the sender's **build**: the plugin version and a
digest of the package's Python sources (CRLF hashed as LF, so a Claude install and a Codex snapshot
of one release are one build). A coordinator runs commands only for a client of its own build
(`74b9302`). The one cross-build request is `retire`:

- a **newer** client asks an idle older coordinator to retire, waits while it is busy, and starts its
  own once the kernel ownership lock is released;
- the **same release with other code** (a source checkout beside an install) retires only an idle
  owner and refuses at once when busy;
- an **older** client refuses without touching the coordinator ("will not downgrade it; restart
  this session");
- a coordinator from **before the handshake** cannot be retired; the refusal says how to stop it.

Versions compare by SemVer precedence; equal digests are one build whatever the version reads.
Same-build clients ride through their own coordinator stopping (`b252b86`).

### `backlog_sync` (`9b13edc`)

The explicit import of hand edits on a native store (a no-op on legacy), inside Codex's
`tool_timeout_sec: 30`. `backlog_sync()` starts a **sync job** the coordinator runs to the end in
rounds under the normal 120 s budget; each tool call waits at most 15 s, then answers with progress
and `backlog_sync(sync_id=...)`. Ids are minted by the coordinator; a second caller attaches to the
running job; a finished id replays its final state, labelled, from memory or from the store; an
id whose job never finished is reported, not re-run. Counts are cumulative per file and add up to
the files selected (`cbe08b8`, `4170a1a`, `c185a9c`, `8d58721`).

### Git-classification budget (`bb2376a`)

Before importing, a sync classifies the selected files against Git. That pass read every file with
no budget and ignored the stop signal: on a cold 37,010-file checkout one `backlog_sync` round sat
in it for 9+ minutes, and a coordinator asked to stop could not exit. It now takes the sync's
deadline (less the per-file reserve) and checks `stopping` per file. When either runs out it stops
before holding or importing anything, answers pending with `Git classification stopped (...);
nothing imported; retry the same sync id`, and keeps the fingerprints it took, so the next round
continues. A cold first sync of a very large project therefore takes several rounds; the total time
is not measured.

### Merge-stamp queue (`b010597`, `860a756`)

On a native store the merge recorder writes only through a running coordinator; a hook never starts
one (no writer fallback). With none running, the stamp is queued durably in
`.taskmaster/local/merge-stamps-pending.jsonl` and applied by the MCP server after its next write,
or after a later call while a coordinator runs (`1ecf9de`). Queue rules (`52ce854`): lines parsed one
at a time, bad ones moved to `merge-stamps-rejected.jsonl`; an `O_EXCL` lock with stale recovery
around every change; a claimed queue is never removed by a replayer that lost it; replay writes
`task.merge` with the snapshot's task revision as the expected revision, so a merge recorded in
between is a Conflict and the decision is redone; Git ancestry decides whether a stamp is still
wanted. Since `860a756` the replay never holds a call (a background thread, one per project;
`backlog_sync` never replays) and the hook records the current merge first, then replays older
stamps under a deadline.

## Known limits

From [`docs/native-store.md`, *Known limitations*](../native-store.md#known-limitations):

- **By design:** write p95 misses 250 ms at 8–12 concurrent clients (one `synchronous=FULL`
  writer; up to ~1.6 s); managed Git reads every file (6.9–7.6 s on the CodeMaestro copy); hand edits
  wait for a sync; cold coordinator start ~6 s and first write ~8 s; no rollback after activation,
  and the escape hatch loses database-only state; MCP tool-call retries are not deduplicated; the
  Windows process scan lists other projects' servers; interrupted managed Git on POSIX needs
  `--acknowledge-quiescent`; Git locks are never removed automatically; before the first backup,
  rollback compares rows only; identical-value updates commit or not depending on the minute.
- **Open follow-ups:** a racing `backlog_link` create answers `linked` with no seq; repeat
  `sync.apply` events for conflicted files on every full sync; linked-worktree sync is not batched;
  the CodeMaestro full viewer read is 164 ms p95 (budget 100 ms); a cold first sync or managed commit
  on a fresh copy took 40–88 s in the harness, and a cold 37,010-file sync takes several rounds (total
  unmeasured); legacy adoption is roughly quadratic (~87 min at 10×); the 10× acceptance was not run;
  4 orphan CodeMaestro tasks are unreachable; legacy `backlog_link create` (N14 D1) and the
  `target_kind` fallback; 6.0.2 and older fail uncleanly on a native store; the handover/issue
  resyncs and the Python client's sync can outlast Codex's 30 s tool timeout; a merge recorded while
  no coordinator runs waits in the queue until the next write.
- **Packaging:** script environments are not locked (`uv run` in script mode ignores `uv.lock`); the
  first server start after upgrading builds a new uv environment (~15 s, network).
