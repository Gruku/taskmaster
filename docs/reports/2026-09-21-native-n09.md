# N09 evidence: agent context, change queries and atomic claims

Branch `feat/database-native-foundation`, from `8cd55db` (the N08 merge) to
`7cdcad6` (the S5 collapse merge). Nothing was pushed, activated or run against a
live project; the installed plugin and every project's `.taskmaster/` are
untouched. The decisions, per-track findings and review tables this report
summarises are in the [N09 scope](../plans/2026-09-20-n09-scope.md), §4a–§4f.

The range also carries work that is not N09: the 6.0.3 back-merge (`c760833`,
`b18afda`, with `fefe0d6`/`8785ff8` holding every export of a flagged entity) and
the N11 scope (`775ed0f`, `a2d30ab`). Excluding master's own 6.0.3 commits, the
range is 92 commits, 78 of them non-merge.

## The exit criterion and what proves it

The plan's exit has two halves: representative agent journeys need fewer
calls/bytes **while yielding the same required context**, and **missing mandatory
context is never reported as clear**.

**The second half is proven by the §5.2(1) invariant gate,**
`tests/test_native_routing_context_invariant.py` (`29d9233`). For each of five
seeds it generates 30 tasks across every blocker dimension: lanes and gate
records, dependency graphs including missing and malformed ids, bugs, handovers,
`human_action`, and claims. Claims are produced through the real tools on a
controlled clock. Each task's `mandatory` answer is compared per task and per
producer against a naive oracle written from the scope document, not by calling
`blockers.py`. `clear` must imply that the oracle finds nothing, the converse must
hold, and legacy must equal native. The gate failed on review A's expiry and
`human_action` defects before they were fixed. Since the S5 collapse,
`tests/test_native_blocker_callers.py` also pins every availability reader
(`next_up`, `backlog_next_available`, `backlog_pick_task`, `backlog_dependencies`)
to `backlog_context` on both stores.

Supporting gates from §5.2:

- **Cursors (§5.2(2)):**
  `test_native_queries.py::test_no_change_is_lost_or_duplicated_across_a_cursor_chain`,
  plus the named cases for rebuild, floor expiry, scope change, epic-scope
  removal and commit grouping.
- **Claims (§5.2(3)):**
  `test_native_routing_claims.py::test_two_sessions_racing_for_one_task_have_exactly_one_winner`.

**What is not proven:**

- **The first half is measured, and only half met.** See "Journey
  measurement" below: pick and resume need fewer calls and fewer bytes on both
  stores; orientation and close do not, and the CodeMaestro run is incomplete.
- **The invariant gate is a seeded sample,** 5 × 30 tasks per store, not an
  exhaustive or generative proof. It covers the blocker kinds the oracle
  models; a producer the oracle does not know about is invisible to it.
- **Liveness of a remote holder is unknown by design.** Only proven local death
  expires a claim early; everything else waits out the TTL (§4c′).

## Journey measurement (the exit's first half)

Added on `feat/native-n09-journeys` after the milestone merge. This measures
improvement; it is not a correctness gate (§5.2(4)).

**Harness.** `tests/test_agent_journeys.py`, with the journeys in
`tests/agent_journeys.py`, uses a seeded project of 6 epics and 48 tasks, with
bugs, handovers, an issue and notes. The project is built once through the
tools, then copied and activated natively. Each journey runs its old path (the
call sequence today's playbooks give) and its new path on separate fresh copies
of the same start state. The harness counts calls and UTF-8 answer bytes, and
writes are counted on both paths. Required context is fixed from the seed, not
read back from the tool under test. The old path is credited with a blocker
whenever the blocker's id appears anywhere in its answers.

| Journey | Old path | New path |
|---|---|---|
| orient (start-session glance) | status, thread_list, note list | status, context(project, handovers+notes) |
| pick (pick-task steps 1–5) | next_available, status, dependencies, pick, handover_list, issue_list | next_available, claim status, context(task, handovers+issues), pick |
| resume (after a gap in which a peer filed a P1 bug and a handover) | thread_list, thread_resume, get_task, pick, handover_list, issue_list | changes_since (cursor taken before the gap, counted), changes_since(cursor, epic), context(session), claim renew |
| close (review-gate + close) | get_task, pipeline, bug_list, bug shelve, record_gate, complete | get_task, context(task, bugs), bug shelve, record_gate, complete |

**Seeded store** (calls old → new, bytes old → new):

| Journey | Legacy | Native | Required context |
|---|---|---|---|
| orient | 3 → 2, 2,341 → 2,952 B | 3 → 2, 2,341 → 2,952 B | **lost**: project context selects pinned notes only, so an unpinned desk note disappears |
| pick | 6 → 4, 5,149 → 3,925 B | 6 → 4, 5,149 → 3,925 B | 4 required blockers; the old path names only 2 of them (it misses the pending review gate and the P1 bug) |
| resume | 6 → 4, 2,284 → 1,926 B | 6 → 4, 2,284 → 2,086 B | 2 required; the old path misses the peer's new P1 bug |
| close | 6 → 5, 860 → 1,210 B | 6 → 5, 860 → 1,210 B | gate plus a P3 bug; both paths name both |

Pick and resume pass outright. Orient (required context and bytes) and close
(bytes) are **strict xfails** that carry the measured reason. A context answer
carries a fixed JSON envelope of several hundred bytes, so where it replaces a
few short markdown answers rather than `backlog_status`, one call fewer still
costs more bytes.

**CodeMaestro copy** (`scripts/native_n09_journeys.py`). It copies `cm-base`
(2,434 tasks, 495 bugs, 395 handovers, 171 epics, 4,677 change rows) into the
scratchpad, keeps the adopted store, and activates a native twin. The live
checkout is never opened. Adoption took 313 s and activation finished at 327 s.
**The run was stopped for low system memory after three measurements**, and it
was not restarted:

| Journey | Store | Calls | Bytes | Wall time |
|---|---|---|---|---|
| orient | legacy | 3 → 2 | 146,464 → 143,339 | 42.1 s → 28.0 s |
| orient | native | 3 → 2 | 146,466 → 143,339 | 0.76 s → 0.55 s |
| pick | legacy | 6 → 4 | **165,907 → 19,700** | 63.1 s → 63.8 s |
| pick (native), resume, close | — | not measured | — | — |

At real scale `backlog_status` is 135,741 B. Pick's old path pays for it in its
parallel-task check; the new path does not, which is an 8.4x byte cut. On pick,
the old path names **none** of the three required blockers (the lane's pending
`spec-review`, `plan-review` and `review-gate`). The CodeMaestro orient saves
3,125 B (2%) but still drops unpinned notes. Legacy wall time is dominated by
the known CodeMaestro store slowness (46–55 s for `next_available`), not by the
N09 tools.

**Finding: `clear` is not "closable".** `blockers.BLOCKING_BUG_SEVERITIES` is
P0/P1 plus unstated severity, as D8 decided. `backlog_complete_task` refuses on
an open `found_in` bug of any severity. On the seeded close, `mandatory` omits
a P3 bug that the close then refuses on. The comment in
`native/blockers.py` claims the two match; they do not. The close journey
therefore selects `include=["bugs"]`. Whether `mandatory` should widen is a
contract decision, not a harness fix.

**Index decision: no index.** On the CodeMaestro native copy (4,677
`domain_events`), timed through the SQL the tool issues:

- a scoped feed over all history takes at most **22 ms** (epic scope,
  correlated subqueries served by `ix_domain_events_entity`);
- `kinds=` uses that index: 0.1 ms;
- `ids=` alone scans the primary-key range: 6.7 ms from 0, 0.0 ms over the last
  200 events;
- the legacy `changes` table matches.

An `(id, seq)` index would remove the 6.7 ms scan. That is not worth a staging
schema change and D6's migration cost.

**Playbooks changed.** Only pick-task: `playbooks/pick-task/playbook.md` (steps
2, 3 and 5 now use one `backlog_claim` status call and one `backlog_context`
call instead of `backlog_status`, `backlog_dependencies`,
`backlog_handover_list` and `backlog_issue_list`) and
`references/v3-context-loading.md` (same-session resume). Start-session and
review-gate are unchanged, because the harness shows no byte win for them.
Skills are thin wrappers around the playbooks and needed no edit.

## Behaviour changes to shipped tools (§4f)

The S5 collapse routed every availability reader through
`blockers.unmet_dependencies` and `claims.foreign_holder`. Where a shipped answer
changed, the stricter reading won: unknown is not clear. Each change is pinned by
a test on both stores.

**The `locked_by` contract** (decided with the user, §4e; `ff19644`/`78bef63`;
`tests/test_native_locked_by_contract.py`):

- Only `backlog_pick_task` and `backlog_claim` write `locked_by`.
- `backlog_update_task field=locked_by` and the batch line
  `update <id> locked_by …` refuse with `claims.HOLDER_WRITE_REFUSAL`. The claim is
  untouched and the other batch lines still apply.
- `commands=` reserves the field (review B).
- Viewer PATCH/PUT/POST drop all three claim fields (`claims.CLAIM_FIELDS`)
  rather than refusing them, because a PUT sends back the holder it read.
- A non-terminal status change on a task a peer holds keeps the claim unless it
  is proven expired (`claims.survives_status_change`). The holder's own change,
  or one over a proven-expired claim, still drops it.

**The terminal-status rule** (orchestrator decision, 2026-09-21: a claim only
protects work in flight):

- A move to `done` or `archived` always releases `locked_by`, whoever makes it:
  update/batch status, complete, archive, the epic-archive cascade, the
  phase-advance archive and the viewer.
- `claims.read` treats a claim on a terminal task as expired
  (`claims.TERMINAL_STATUSES`), so `backlog_claim(action="release")` always
  clears a stranded one.
- Leaving a terminal status always clears any claim (`claims.keeps_claim_through`,
  review D), so a claim from before the rule cannot revive on reopen.

**Malformed `depends_on`:**

| Case | Before | After |
|---|---|---|
| A missing dependency id | read as `todo` by three readers, `NOT FOUND` by `backlog_dependencies` | blocked by all, as unresolved; one decider |
| A number, or a list holding one | `TypeError` in every reader; on legacy `_derive_context` runs on every load, so one row took down every tool | blocked on `depends_on (unreadable)`; `backlog_dependencies` prints `[unreadable]` and "met: **No**" |
| A mapping | its keys guessed as ids | unreadable, as above |
| A bare string, in link derivation | one edge per character | one edge |
| Unreadable, in link derivation | `TypeError`; no write to that task succeeded, a pick included | no edge; the resolver reports the shape |
| `backlog_get_task`, `backlog_validate`, viewer related panel, `validate_task_write` (review C) | raised, listed `5` as a dependency, said "All clear" for a mapping, or split a string | one normaliser, `taskmaster_v3.dependency_ids`: `**Depends on:** unreadable (<shape>)`, a `validate` issue, one id for a bare string, a refused unreadable patch |

**`backlog_pick_task` and `backlog_next_available` on peer claims:**

- A peer's `locked_by` on a `todo` or `in-review` task used to be taken silently
  by a single pick, in both tools and in the native `task.pick` core. Now the pick
  refuses unless `force`, with wording that names the status.
- An expired peer claim gets the informed refusal and the
  `backlog_claim(release)` path.
- `next_available` lists such tasks under "N tasks claimed by another session"
  (singular for one, review C). `next_up` leaves them out. This includes an
  *expired* peer claim, which `backlog_context` reports as clear: availability
  follows the pick, and the pick never takes a claim silently.
- A batch `pick` line obeys the same rule (review C). `backlog_batch_preview`
  now gives the batch's own refusal line and the resolver's dependency warnings
  (reviews C and D).

**Also changed:**

- Legacy `backlog_context` reads one snapshot (`BEGIN` … rollback). Called
  inside another store transaction, it refuses.
- `native_routing/tasks.py::_open_handovers` is deleted; `Snapshot.open_handovers`
  is now the only reader.

## What the reviews found

Every fix was made test-first and on both stores. The detail is in scope §4d–§4f.

| Pass | Found | Defects |
|---|---|---|
| Integration (merging the parallel tracks) | 1 | Context judged a claim holder live only by a `sessions` row; claims had established that `locked_by` and the `sessions` key are minted independently and never match. Together, `backlog_context` reported a task held by a live peer as `clear: true` on both stores (`b0792ce`, `55b2fc9`). S12–S13 had already hit the same mismatch inside its own track (`d891cac`) |
| Review A | 4 | Context cursors re-delivered finished sections and could loop forever; a new holder inherited an earlier claim's `claim_expires`, so a live claim read as expired, context said clear and any peer could release it; a bundle renew re-claimed dropped members; a non-string `human_action` raised. The §5.2(1) gate was built in this pass |
| Review B | 6 | `commands=` could speak for another session (`task.pick`/`claim_renew`/`claim_release` now internal; `note.create` `author`, `task.merge` `merge_targets` and `task.update` `locked_by` reserved); `commands=` could store any text as an imported document; epic scope was current membership, not membership at each event; the importer read any path and crashed on a directory; a partial import hid what committed; a floor above the high-water mark looped on resync, and a cursor past a restored store's end skipped the gap (new reason `history_rewound`) |
| Review C | 6 | Legacy and native disagreed on phase-advance archive; a claim stranded on a terminal task could never be cleared; a batch `pick` line took a peer's claim and the preview misread dependencies; readers of a malformed `depends_on` disagreed; viewer writes could set or erase `locked_by`; "1 tasks" |
| Review D (re-probe of C) | 3 | A viewer write could forge `claim_expires`/`claim_expires_for`; the preview showed a peer-claimed pick as applying; a pre-rule claim revived when a `done` task was reopened |
| Final re-probe | 0 | Clean |

**The recurring pattern: tracks that each passed their own tests but
disagreed.**

- Claims and context held two liveness rules, and the merged tip reported a held
  task as clear, the one answer the milestone says must never be wrong.
- `claim_expires` was "read beside" `locked_by` by one track while a dozen writers
  in others moved `locked_by` without it.
- Before the collapse, four readers of "is this task blocked" each decided
  dependencies their own way.
- `commands=` gave callers arguments that the tools supply themselves.
- Phase-advance archive disagreed between the two stores.

Each defect sat on a seam between two correct-looking pieces. The fixes were the
same each time: one predicate (`blockers.resolve`/`unmet_dependencies`,
`claims.read`/`foreign_holder`/`keeps_claim_through`,
`taskmaster_v3.dependency_ids`, `cursors.epic_condition`) and a test that pins
every reader to it. N11's scope adopts this as its ownership rule: one owner per
shared file, and one `held()`.

## Known characteristics carried forward

- **`budget.budget` is quadratic in rows delivered (to N16).** Each candidate row
  rebuilds and re-encodes the trial answer, and `assemble` runs the loop up to
  three times. `PAGE = 50` bounds rows at 550. At the default 8,000-byte budget
  that is about 1,100 encodes of an answer of 8 KB or less. At `MAX_BUDGET`
  (1 MiB) with prose-heavy sections it is on the order of a gigabyte encoded
  (scope §4d). No benchmark was run. The fix is to size each row once, keep a
  prefix sum and render once; it is deferred to N16 with a measurement, because
  it rewrites the loop that holds the `used_bytes` invariant.
- **The viewer shows `locked_by` without the expiry predicate (to N10).** It can
  display a claim that `backlog_claim` considers expired (§4c′, §5.3). The viewer
  no longer lets anyone *write* claim fields; only the display is open.
- **Flag notices and exporter-lease visibility (to N11).** On a native store,
  `_attach_conflict_notices` finds no opened legacy `Store`, so a native answer
  carries no per-call flag warning; `backlog_store_status` lists flagged files
  under Flagged. N11 creates native flags, lifts `backlog_resolve_conflict
  take="store"`, and must show the exporter lease holder's liveness in
  `backlog_store_status` (N11 scope §2.5, §5.4). These belong to N11's changelog
  and projection work, not N09.
- **Also open:**
  - No history pruner ships (D4); expiry is tested by setting
    `sync_state.change_history_floor`.
  - `take="file"` conflict resolution and document staleness belong to N13.
  - The three inline session-liveness copies that feed `store_status` were left
    alone (§4c′).
