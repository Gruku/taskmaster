# N11 evidence: durable projection outbox and native changelog

Branch `feat/database-native-foundation`. N11 is two tracks merged there:

- **Protocol** (`feat/native-n11-protocol`, S1–S6, S10, S11): 22 non-merge commits
  from `4fbbff5` to `7448204`, tip `c8b23a9`, merged as `22052d4`.
- **Changelog** (`feat/native-n11-changelog`, S7–S9 and the two items routed from
  the protocol track): 4 commits, `506d203` to `1aa33c3`, merged as `b3cbebc`.

Nothing was pushed, activated or run against a live project; the installed plugin
and every project's `.taskmaster/` are untouched. The CodeMaestro evidence was
taken on a scratchpad copy of the live backlog, never on the project itself. The
decisions, per-track findings and review fixes this report summarises are in the
[N11 scope](../plans/2026-09-21-n11-scope.md): the resolutions, then "Protocol
track notes" and "Changelog track notes".

## What shipped

**Protocol track: the outbox (`taskmaster/native/projection.py`, new).** The
synchronous drain in `native_routing/projection.py` is now a thin adapter over it.

- **Exporter lease** with a generation fence (D1). Recovery is by generation:
  taking the lease recovers every `claimed` job an earlier exporter left.
- **Claim and ack.** Claim takes the latest job per file and skips held entities.
  Ack is one short transaction per job. `sync_state.exported_through` is kept.
- **Publish-intent transaction.** Before any file is touched, it records the hash
  of every byte string about to be published, in a per-file own-bytes ring (the
  last 8), plus the aside and temp names.
- **Aside-verified install** (review P1). The current file is renamed aside
  under a generation-owned name and its bytes are verified. Only then is the
  temp file installed with a no-overwrite rename, or the aside file dropped for
  a removal. A mismatch puts the file back and flags it.
- **Expected-base verification** (§2.4), for entity files and for `backlog.yaml`
  and `ideas/IDEAS.md`. It matches line-ending variants (review P8).
- **Flag-and-keep-both** (D2). A native flag stores the disk bytes in
  `projection_conflict` (the B-089 shape) and holds the entity. One `held()`
  answers for claim, status and resolve.
- **Moves write then remove.** The removal is deferred unless the paired write
  was exported in the same attempt (review P6/P7).
- **Retention and tombstones** (D7). The latest terminal job per file is its
  export record, and a tombstone when it is a delete. Older terminal jobs are
  deleted after the acks.
- **`backlog_resolve_conflict` `take="store"`** on native (D3). It records the
  exact replaced and flagged bytes in the resolution event. `take="file"` refuses
  and points to N13.
- **No writer lock during file I/O.** A caller waits at most 5 s for its own
  commit's files, then gets the pending notice.

**Changelog track: `native_routing/progress.py` (new).**

- **Paragraphs are rows.** Each paragraph is a `sync_state` row,
  `progress.pending.<commit_seq:012d>.<n:04d>` (D4). A completion inserts one row
  and rewrites nothing.
- **One-time seed from legacy `meta`** (D5). `meta.progress_log` becomes
  `progress.applied`, and `meta.pending_progress_log` becomes rows at sequence 0.
  The `progress.seeded` marker is written in the same transaction. `meta` is only
  read.
- **Fenced PROGRESS.md render** under its own lease, `progress.writer`. The file
  is written first. Then one fenced transaction moves the rows to the applied log
  (cap 200, legacy rule). The dashboard is refreshed at most every 5 s,
  cross-process (D6).
- **The changelog refusal is lifted.** `_append_changelog` is split into a pure
  formatter (`_changelog_entry`) and legacy queueing. The native adapter passes
  `changelog=` to `task.complete`.
- **Two items routed from the protocol track:**
  - every native result names every flagged file;
  - `backlog_store_status` has an `Exporter lease:` line with the holder's pid
    check.

**Refusals and intentional differences.**

- **N08 differences 2 and 7 are lifted.** Difference 2 was the refused
  changelog completion; difference 7 was the missing native dashboard.
- **The native guidance table drops from 12 entries to 11.**
  `backlog_resolve_conflict` is routed now.
- **The handover and issue resync guidance is corrected.** It used to say a hand
  edit is exported over; it now says the edit is flagged and kept.
- **Still refused:** Linear `retry` (D8, to N12) and `bootstrap_apply` (N13).

**One intentional difference is new: D2.** A native export that finds a file
changed since it last wrote it no longer overwrites it silently. It keeps both
versions, pauses that entity's exports and routes the choice through
`backlog_resolve_conflict`. This is the B-089 contract legacy already follows,
and the user chose it on 2026-09-21.

## The exit criterion and what proves it

The plan's exit has three clauses: **no committed effect loses its export
intent; no stale job overwrites newer content; retry/rollback preserves
authored data and local-only state.**

**Verdict: met for projection files and for changelog paragraphs.** One named
exception is below: PROGRESS.md's own file, which is not a projection job.

### No committed effect loses its export intent

- **Jobs commit with the command**, in the same `BEGIN IMMEDIATE` (N05,
  unchanged). Each carries the complete immutable entity (`input_json`).
- **Acks are per job**, so a published file never loses its record because a
  later file failed. `test_native_projection_today.py` pinned the old rollback
  defect; it flipped at S6.
- **The §5.2 matrix, in `tests/test_native_projection_faults.py`.** Every cell
  runs twice: as an in-process exception, and as `os._exit` in a subprocess
  followed by recovery in a fresh process. The cells:
  - before the DB commit;
  - after the commit, before the claim;
  - after the claim, before the temp write;
  - after the temp write, before the replace;
  - after the replace, before the ack, and during the ack;
  - after the ack, before retention;
  - between a move's write and its removal.

  After each recovery, every exported file must hold the newest revision and
  parse back **losslessly** to its job's `input_json` through the legacy parser
  (`assert_lossless`), with no false flag.
- **Changelog paragraphs.** A paragraph is a row that is deleted only by the
  transaction that moves it into the applied log, after the file carrying it is
  on disk. `tests/test_native_progress.py` covers each PROGRESS checkpoint:
  - `progress_written`, in both variants (exception, and `os._exit` in a
    subprocess): recovery rewrites identical bytes and applies the paragraph
    once.
  - `progress_seeded`, `progress_applying` and `progress_temp_written`, as
    in-process exceptions: nothing is seeded half-way, the move rolls back as a
    unit, and a failed write keeps its rows and removes its temp.

  **Gap found, then closed.** When this report was first written, the scope's
  changelog-track notes said all four checkpoints were also tested as
  `os._exit`, but only `progress_written` was. A kill at
  `progress_temp_written` left a stray `PROGRESS.md.tmp.<session>` that nothing
  removed, because the render removed only its own temp and a recovering process
  has a different session. The stray held no authored data.

  Closed since: `test_a_killed_process_at_every_checkpoint_loses_nothing_and_leaves_no_temp`
  kills a subprocess at each of the other three checkpoints. The next call
  writes the paragraph exactly once and leaves no temp. The lease holder now
  records its temp name in `progress.temps` before writing, and the next lease
  holder removes recorded names that match `PROGRESS.md.tmp.<session>` in
  PROGRESS.md's directory. `test_recovery_removes_only_the_exporters_own_recorded_temps`
  pins that nothing else is touched: unrecorded or non-matching names, paths
  outside the directory, and traversal names all stay.

  Its other tests pin the rest: more pending paragraphs than the cap are all
  written, the seed is idempotent, and the pre-N11 native queue is folded in
  ahead of newer rows.

### No stale job overwrites newer content

- **One exporter at a time.** A generation-fenced store-wide lease; a file never
  has two claimed jobs.
- **A stale exporter cannot install.** The aside rename plus the no-overwrite
  install mean an exporter paused past its lease finds its successor's file and
  cannot replace it. Review P1 turned this from "detected and repaired" into
  "prevented":
  `test_a_paused_exporter_past_its_lease_cannot_install_over_its_successor`
  asserts that the stale bytes never land.
- **The interleavings §5.2 names:**
  - a newer DB edit while an old job renders publishes after it;
  - an external edit while an old job renders is flagged and kept byte for
    byte;
  - two real processes exporting one store converge without a flag.

  All three are in the faults file.
- **Review 2** (`tests/test_native_projection_review2.py`) re-probes the install
  mechanism: a kill at every step, with and without a file appearing at the
  path; kills during a move; repeated kills.

### Retry/rollback preserves authored data and local-only state

- **Retries execute once.** A retried `request_id` executes once (the
  before-commit cell) and logs its paragraph once (receipt dedup,
  `test_a_retried_completion_logs_its_paragraph_once`).
- **A hand edit to a projection file is never lost.** It is flagged and kept
  byte for byte. `take="store"` records the exact replaced bytes in its event
  (review P4).
- **Local-only state survives.** The seed never writes `meta`, and a test
  compares every `meta` row and the manifest state before and after. The legacy
  session log survives activation: on the CodeMaestro copy its 44 paragraphs
  were seeded and rendered identically (below). A failed PROGRESS write keeps
  its rows and removes its temp.

### The exception: PROGRESS.md itself

PROGRESS.md is a local, store-owned region inside a user-owned file. It is
deliberately not verified against a base (§2.4), exactly as on legacy. Two
windows remain, and both are recorded in the scope's changelog-track notes:

- **A stale PROGRESS render can transiently replace a newer one.** A writer's
  lease can expire after its check and before its `os.replace`. It then installs
  a file lacking paragraphs a successor already moved to `progress.applied`, and
  its fenced move records nothing. **No paragraph is lost:** they are in the
  applied log and reappear on the next render.
- **A hand edit to PROGRESS.md between the render's read and its replace is
  overwritten**, exactly as on legacy.

So, read literally, "no stale job overwrites newer content" holds for every
projection job, but not for this non-job local file. The first window is
self-healing and loses nothing. The second window is legacy's behaviour carried
over. Neither is a regression.

### What the proof cannot show (scope §5.3)

- **Power loss.** `os._exit` proves process-death recovery, not write reordering
  below the filesystem. Directory `fsync` is not available on Windows.
- **Real sharing violations.** Antivirus and indexer locks are simulated with
  injected `errno` values.
- **N12 behaviour.** Asynchronous export with pending receipts is N12's. The
  synchronous adapter proves the protocol under today's call pattern.
- **A stale file visible to a concurrent Git operation.** Whether that can
  happen is N13's generation barrier.

## CodeMaestro copy: PROGRESS.md twins and the dashboard read

`scripts/native_n11_progress_parity.py`, run alone on 2026-09-22 on `22a3d49` (`82f8fe6`'s code plus N09 documentation).
It used the same fresh scratchpad copy as the N09 rerun: 2,457 tasks, 176 epics,
and a legacy session log of 44 applied paragraphs. The script adopts the copy,
copies the adopted project and activates that copy as a native twin, then drives
both through `Twins`. Both twins re-render the dashboard on every call:

- **legacy**, because each call opens a fresh store;
- **native**, because its throttle clock moves 10 s per reading.

`datetime` is pinned by `install_clock`, so `_time_remaining` agrees. The live
checkout is never opened. Raw output is private and stays in ignored
`test-results/n11-cm-progress.txt`. Adoption took 45.8 s, activation finished at
60.3 s, and the run took 156.3 s.

**Parity: PROGRESS.md was byte-identical at all 17 comparisons.** The 16 tool
calls, each compared as an answer on both stores:

1. On four tasks chosen on the native twin (`sp-audit-0720-001`,
   `sp-audit-0720-002`, `sp-v5-032`, `spbill-006`): lane `express` and a passing
   `review-gate`.
2. Each task picked, then completed:
   - with a structured changelog (`session_title`, `done`, `decisions`);
   - with `auto_summary`;
   - with `done` only;
   - with no changelog.

After the calls, committed state and every projected file also matched
(`assert_state_matches`, `assert_files_match`). The native store ended with 47
applied paragraphs (44 seeded plus 3) and no pending rows. Its marker reads
`progress.seeded = {"seq": 4926, "applied": 44, "pending": 0}`.

**Why epic order did not diverge.** Native orders epics by `entity_key` and
legacy by `rowid`. The backfill allocates entity keys in legacy row order
(`c15f77d`), so the two orders agree at activation for all 176 epics. After
activation, both stores append new rows in creation order. The run created no
epic, so an epic created after activation is not exercised here; the seeded twin
suite covers creation on small fixtures.

A first attempt (kept aside in the scratchpad) completed only one task. On the
real backlog `backlog_complete_task` refuses a `todo` task on both stores, so the
script now picks each task first. Its one changelog completion also matched.

**The dashboard read (D6), timed on the copy, best of 5, with no file written:**

| Store | Full read | Render |
|---|---|---|
| native `reads.tree` (context derived) | min 400 ms, median 411 ms, max 503 ms | median 14 ms |
| legacy `_load_dict_from_connection` (context derived) | min 110 ms, median 120 ms | — |

**The native full read is about 3.4x legacy's.** On a native store it runs at
most once per 5 s, plus once for each changelog-carrying completion, so it adds
about 0.4 s to such a call at this scale. This is D6's accepted cost. It is
evidence for N16's targeted dashboard queries, not an N11 defect.

## Carried forward

- **N16 performance:**
  - **More commits per export.** Each drain went from one commit to claim +
    intent + one ack per file + retention + release, each `synchronous=FULL`.
  - **The dashboard full read.** Native `reads.tree` has a 411 ms median on
    CodeMaestro, against 120 ms for the legacy read. Option (b) is to replace it
    with targeted aggregate queries.
  - **Every exported file is hashed.** §2.4's `mtime`/`size` short-circuit was
    not implemented.
- **N13:**
  - `take="file"` needs the native importer. So do `backlog_handover_resync`,
    `backlog_issue_resync` and Linear `bootstrap_apply`.
  - Tombstones are kept for N13 to tell a user-deleted file from a moved one.
  - Lossless export is proven; that an import would accept the file is not.
  - Whether a transient stale file is visible to Git is the generation
    barrier's question.
- **N12:**
  - Linear `retry` stays refused (D8); its owner is the coordinator's worker.
  - Asynchronous export and pending receipts read `exported_through`, which
    N11 only maintains.
- **N15:** the cutover verifies the seed rather than reconciling two queues from
  scratch. The one-shot legacy handover-status backfill is still its job (N08).
- **The pid-reuse liveness limit.** The `Exporter lease:` line cannot recognise a
  reused pid or a hostname shared by two machines; either reads as running. It
  reports the pid rather than claiming the holder is alive, and recovery relies
  only on lease expiry.
- **Stated limits:**
  - **The own-bytes ring.** Restoring a file to one of the last 8 renders gets it
    overwritten without a flag. That is an earlier DB state; no authored data is
    lost.
  - **`exported_through` covers jobs only** and can move backwards when a hold
    is released.
  - **The timeout notice** lists every pending file in the store, not only the
    caller's.
  - **The worst-case wait is 10 s:** the drain's 5 s wait followed by the
    PROGRESS writer's 5 s wait.
  - **A hand-converted CRLF PROGRESS.md is written back as LF**, as on legacy.
  - **PROGRESS temps from before the fix are not removed.** Recovery removes
    only temps recorded in `progress.temps`. A stray left by a build that did
    not record it stays on disk. (The earlier gap, three PROGRESS checkpoints
    with no `os._exit` variant, is closed; see above.)

## Where this does not reach

Activation remains test-only; nothing moves a real project to native. N11 proves
the outbox and the changelog under the synchronous call pattern that exists
today. Asynchronous export, service ownership, managed Git barriers and the
importer are N12–N14.
