# N16 report: scale, durability and end-to-end acceptance

Status: **complete locally; activation gated. The exit is met on the correctness gates; the 10×
acceptance was not run (user decision).** Native activation remains a release decision. No live project was migrated. Scope:
[`2026-09-24-n16-scope.md`](../plans/2026-09-24-n16-scope.md). Batched sync:
[`2026-09-29-n16-batched-sync.md`](../plans/2026-09-29-n16-batched-sync.md). Runbook:
[`native-cutover.md`](../runbooks/native-cutover.md). Branch `feat/native-n16`, merges `0259ce3`…`40512e8`
(10 first-parent merges, 42 non-merge commits).

The plan's exit: all correctness gates pass; performance improvements and remaining limits measured,
without claiming model or network latency as DB performance. Every latency below is a local
process/IPC measurement on this machine. None includes a model call or a network hop.

## Decisions

- **Cutover preflight (user, 2026-09-28).** The cutover refuses while any projection file is
  quarantined or flagged. Native managed Git refuses in that state, so a project cut over with one
  could not commit or check out afterwards (CodeMaestro carried 4 such files).
- **Batched full sync (user, 2026-09-29).** The full sync scans in bounded batches instead of refusing
  above `sync.MAX_FILES` (10,000). The refusal left a large project permanently unsynchronizable, and
  its managed-Git barrier refused every operation.
- **Exporter fingerprint cache dropped (track B review).** Once made safe, it gave no benefit on
  Windows. See track B.

## What was built

### Track A: first sync after activation (`0259ce3`)

- **Seeded merge bases.** Activation reads and hashes every projection file with no base. When the
  bytes match the recorded `content_hash`, it stores them as `projection_base` inside the activation
  transaction, after `verify_carryover`. The seeded paths are journaled, and the oracle accepts
  exactly those (`e9585f2`). The same reads seed the sync fingerprint cache.
- **Observes no longer spawn Git per file.** The completion check still re-reads HEAD. A file starts
  only with a time reserve. A write the budget runs out on gets a grace period, then is reported
  `committed` (receipt found), `not_committed` (cancelled while queued) or `uncertain` (the writer is
  still running it) (`c07142a`, `5b041a6`, `dad17f2`). "Uncertain" no longer appears for a committed
  write.
- **Sync fingerprint uses NTFS ChangeTime.** On Windows, `lstat` `st_ctime` is the creation time, so a
  same-size rewrite with its mtime restored matched the old fingerprint. `generation()` keeps its full
  read: a write through a memory mapping moves no timestamp (measured), so no stat fingerprint can
  vouch for managed Git (`f13b974`).
- **Single-read backup.** The archive and the manifest's hashes come from one read per file
  (`5d5f500`).
- **Result (CodeMaestro copy, 3,704 files):** the first sync after activation went from **626 s**
  unbounded (about 680 s over six 120 s rounds) to **4.4 s in one round**. Seeding adds about 9 s to
  `activate`. Source: runbook, *Verify* (`docs/runbooks/native-cutover.md:265`).
- Three review rounds (merge message).

### Track B: carried performance defects (`ace409a`)

| Item | Before → after | Oracle | Source |
|---|---|---|---|
| `budget.budget` fill | O(n²) → O(n): 1,600 rows 872 ms → 21 ms; 6,400 rows 27.8 s → 0.18 s | pre-N16 fill kept verbatim in the test; byte-equal over 1,000 randomized cases plus every boundary; falls back to the rendering fill on a size divergence (review, `e210dd8`) | `6e5d78f` |
| Dashboard (`backlog_status`, PROGRESS.md) | `reads.tree` → `reads.dashboard_tree` (15 fields, no prose), derived indexes paged: CodeMaestro copy 230–450 ms → 103–120 ms (legacy 120 ms) | renders equal to the full tree and the legacy twin; a key recorder fails if a renderer reads an omitted field (review hardened it, `d309a1a`) | `b3053e5` |
| Backup archive | one read per file: CodeMaestro copy (3,708 files, warm) 7.3 s → 1.3 s | archive and manifest cannot disagree | `5d5f500` |
| Exporter fingerprint cache | **removed** | see below | `48868b6` |

**The exporter cache was a critical review finding.** The first version (`ee37611`) let an unchanged
`lstat` fingerprint stand in for a read. The review showed that it could approve an overwrite,
set-aside or removal of a file whose edit no fingerprint shows (a utime-restored same-size edit, or
an mmap write), so the **hand edit was overwritten and lost** (`1bd29f7`, CRITICAL). The fix limited
the cache to the no-write "agrees" verdict and proved the change time through `fstat`. That costs an
open, so the cache gave no win on Windows (warm agrees 252–320 ms vs 263–317 ms; changing publishes
502–1,272 ms vs 286–451 ms). It was then removed entirely: `projection.py` is back to its pre-N16
bytes. The real utime-restore and mmap tests stay, as `test_native_export_invisible_edits.py`.

`generation()` still reads every file: 6.9–7.6 s per managed Git operation on the CodeMaestro copy
(`f13b974`). This is a remaining limit, kept for correctness.

### Track C: opt-in metrics (`6ccf5a6`)

`TASKMASTER_METRICS=1` (in memory) or `=<abs path>.jsonl`. When it is off, each point costs one module
flag check. It records:

- **command:** lock wait/hold, DB/commit time, rows written, sampled VM steps (a rows-read proxy),
  receipt bytes, graph and FTS counters;
- **sync:** files stat-ed/read/parsed, bytes, fingerprint cache hits;
- **coordinator:** queue/admission/service time, IPC reply bytes, client connect/startup, export lag;
- **server:** tool and viewer reply output bytes.

Review (`03ac258`): shared Windows appends tore and lost records (7,581 of 9,000), so recording is now
one file per process (0 lost of 6 × 1,500). `rows_written` is counted only on committed commands.

### Track E: hardening found while running the matrix

**Grounded no-op wording (`e782a5f`).** A write whose value already matched said "(not persisted)".
It now says "No change … already X" (`4229afa`). That reply used to read a fresh snapshot after the
command, so a peer write landing in between could make it claim a value the command never saw. The
core now returns the entities a write left unchanged (receipt `unchanged`, read inside the
transaction), and the replies render from it (`6d832cc`, with a peer-write regression test).

**Cutover quarantine/flag preflight (`fb25737`).**

- The fresh run and the dry run refuse before any fence, backup or journal, listing each quarantined
  file with its logged reason (`ef5f93d`).
- Review (`409c86a`):
  - `reconcile` and `compare` re-check held files on the fenced connection and abort before
    activation;
  - a `project.yaml` that never parsed (no projection row) is refused through `meta.quarantine_log`;
  - flagged conflicts are refused too.
- **Always-on reconcile scan (`0884086`).** The reconcile flush was the only disk scan, and it ran only
  with export work pending, so a file that broke after the preflight reached activation unseen. It
  now always runs. On a copy of CodeMaestro's legacy store (3,708 projection rows) it takes 2.4 s
  (scan state current) or 2.5 s (forcing a hash of every file). A one-off 30.4 s occurred only on the
  first scan of an old backup.
- `f1165d7` documents what the fence still cannot see: a new file added after the reconcile scan, and
  a tracked file changed after the last drift check. Both are left to native sync. The runbook forbids
  pulls, checkouts and file edits from the final tool call to the end of the cutover.

**Batched full sync (`40512e8`).** One sync operation (one begin, Git classification, writer pause,
publication, completion check and finish) scans its files in slices of `batch_size()` (10,000) paths.
Whole-set judgements stay whole-set but memory-bounded: Git classification keeps digests, not bytes.
The fingerprint cache is persisted per batch, and a retry under the same id is safely restartable
with no cursor. Measurements from the design note:

Reads and the DB core are within budget, with one exception: the CodeMaestro full viewer read, a
whole-board read of 3,700 entities. Writes are within budget at 1 client and mostly at 4. Under
contention at 8 and 12 clients they miss, and same-entity `create` is the worst case. This is the
designed cost of one writer with `synchronous=FULL`: every client queues behind one fsync'ing
writer, and p95 grows with queue depth. The DB core's own p95 stays at 2–5 ms. The scope says a
miss of this kind is raised to the user, not bought with a durability relaxation, so these misses
are reported and nothing was relaxed.

**Working hypothesis (unverified).** Every harness scenario copies the project first. The copy gives
every file a new ChangeTime, so the sync fingerprint cache misses on every file, and the sync becomes
a genuinely cold full read. That is what a user would see after a fresh clone. The design note's
15 s ran with the cache already seeded by the cutover, and so did the rehearsal's 4.65 s. The
samples were not broken down (the instrumented pass would show `sync.cache_hits` and
`sync.files_read`), so this stays a hypothesis. It is an open follow-up together with a question
that follows from it: does a cold 37,010-file sync fit the 120 s budget? The 10× numbers in the
design note all had a seeded cache.

### Machine noise

- **The A/B in `%TEMP%\tmn16\ab\`** reran reads and writes at 1 and 8 clients, three times in

  slow**, so its 8/12-client misses overstate the product. Old and new code were indistinguishable
  (no regression from the Track E changes).
- **8/12-client tails are noise-dominated.** Across the three sequences, 8-client p95 varied up to

  m1 repeats (`m1.out`), 8-client `write.meta` same-entity p95 ranged 162–401 ms. A single run's
  tail at 8 or more clients is not a stable number.
- **Load logs:** `run-cm.load.log` (30 s samples, 02:18–04:26) shows 8.0–9.3 GB free with CPU 1–86 %

## Not run

From the summaries' "Not run" sections:

- **Migration:** the old runtime ACTIVE during cutover is not exercised. The quiesce probes refuse a
  live runtime, and driving a live 6.0.x server against a copy needs its own design.
- **Failure:** exporter lease expiry. Only the claim lease is exercised here; the exporter lease is
  covered by the N11 in-process tests.
- **Failure:** disk full. Only an injected commit error is exercised.
- **Allocations:** RSS per process is recorded; allocation counts are not.
- **Scaling (required output vs unrelated data):** needs `read.details` or `read.context` passing on
  two dataset sizes in one run. **Not measured:** the 10× run was stopped (user decision, below).
- **10× acceptance (user decision):** 10× read and write latencies, 10× sync through the harness, and
  the scaling check are not measured. The only 10× evidence is the batched-sync measurement.
- CodeMaestro only:
  - **History:** store rebuild. The dataset has no legacy snapshot to rebuild from.
  - **Migration:** interrupted cutover and recovery, for the same reason. It passed on small: crash
    at `backfill:after-commit` then resume took 5.3 s + 3.1 s, and crash at
    `activate:before-commit` then resume took 5.0 s + 3.0 s.
