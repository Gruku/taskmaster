# N17 packaging: launch paths and version alignment

Branch `feat/native-n17-pkg`, based on the N16 merge `a12d3aa`. Commits: `5524695`,
`14ae4fd`, `b0a07dd`, `e0b57a0`, and a docs commit. The procedure is in
[release-packaging.md](../runbooks/release-packaging.md).

## Evidence class

Everything below is **packaged runtime on disposable copies**, not local tests and not a
project migration. Setup, all under `%TEMP%\tmn17\pkg\`:

- **Plugin layout.** A clone of claude-tools `aac4e8e` with this branch checked out as
  `plugins/taskmaster`, and the Codex snapshot regenerated by claude-tools' own sync script.
- **Environments.** Built from each script's PEP 723 header by `uv run`. Each run used a
  fresh `UV_CACHE_DIR` so that no environment from the live machine was reused.
- **Interpreter.** uv 0.7.9, uv-managed CPython 3.12.9.
- **MCP client.** A standard-library JSON-RPC client over stdio, launching exactly the
  manifest commands.
- **Projects.** Synthetic `--scale small` native and legacy projects from
  `scripts/native_synthetic_dataset.py`.
- **Hooks.** Run the way `hooks.json` runs them: `run_hook.sh` sourced, JSON on stdin,
  a 10 s cap. The interpreter was a bare Python with no site-packages, standing in for a
  fresh machine's system Python.

Nothing was installed into a live Claude or Codex configuration, and no live project was
touched. The real hosts, Claude Code and Codex, were not driven; their manifest commands
were run as written.

## Fixes

| Commit | Defect | Fix |
|---|---|---|
| `5524695` | The script header declared only `fastmcp` and `pyyaml`, unpinned, so a fresh `uv run` resolved **FastMCP 4.0.10**, a major version no test had run against (the dev venv has 3.4.3, the live install 3.2.4). `httpx` and `pydantic` are imported directly but arrived only through fastmcp | `fastmcp>=3.4,<4`, `httpx`, `pydantic>=2`, `pyyaml`, identical in every `uv run` header and in `pyproject.toml`. A test checks that the lists are identical and that every third-party import is declared |
| `5524695` | B-091: no command produced a venv that could run the suite | `[project.optional-dependencies] dev` (pytest, pytest-xdist, pytest-timeout); relocked |
| `5524695` | `serverInfo.version` was FastMCP's version, and the Codex snapshot (no `.claude-plugin/`) reported `0.0.0` to the viewer and to board ETags | `FastMCP(..., version=VERSION)`; the version falls back to `.codex-plugin/plugin.json` |
| `5524695` | No packaged way to run the cutover, managed-Git or pre-commit CLIs | `taskmaster_cli.py`, a PEP 723 front door that never imports the server (importing it starts the viewer). A test checks that its command line does not match the cutover's launcher inventory |
| `5524695`, `b0a07dd` | The merge stamp ran on the hook's system Python and needs fastmcp, so on a machine without it every merge went unrecorded, silently | The stamp runs on the hook interpreter when that interpreter can import the modules. Otherwise it runs detached under `uv run --script`, so a first-use environment build cannot overrun the 10 s hook timeout. It logs to `hook.log` when it cannot import the server |
| `5524695`, `14ae4fd` | A bump meant editing five files by hand, plus a test that hard-coded `6.0.3` | `scripts/bump_version.py <version>` and `--check`. The rehearsal found that a pre-release left the badge stale (shields.io escapes `-`). The script now accepts only `X.Y.Z` or `X.Y.Z-rc.N` |
| `e0b57a0` | The pre-commit refusal told users to run `python -m taskmaster.coordinator.git_cli` | It prints `uv run "<plugin>/taskmaster_cli.py" git commit/status` |

## Version strings

All of them currently read `6.0.3`. In taskmaster: `.claude-plugin/plugin.json`,
`.codex-plugin/plugin.json`, `pyproject.toml`, `uv.lock` (the taskmaster entry), the README
badge, and the `CHANGELOG.md` heading. In claude-tools: `.claude-plugin/marketplace.json`,
plus the generated `codex-plugins/taskmaster/.codex-plugin/plugin.json` and
`.taskmaster-distribution.json` (live `upstream_commit` `94c6e27`). No `__version__`
exists. `bump_version.py` changes the first five; the full release sequence was rehearsed
in the disposable clone (see the runbook).

## Open before a release candidate

1. **Choose the version.** That belongs to the compatibility review.
2. **Apply the claude-tools sync change.** Add `taskmaster_cli.py` to `FILES`, or the Codex
   snapshot ships without the CLI front door. The exact diff is in the runbook.
3. **Codex project root, unverified.** The Codex manifest sets `cwd: "."`. If Codex starts
   the server in the plugin directory and does not set `TASKMASTER_ROOT`, every tool call
   refuses. The 6.0.3 manifest is identical, so this is not a regression, but no evidence
   shows it works. It needs one run in a real Codex host.
4. **First launch after upgrading.** The dependency change gives the header a new hash,
   so every existing install builds a new uv environment on its first server start. That
   takes about 15 s and needs network access. Codex allows 120 s at startup.
5. **Script environments are not locked.** `uv run` in script mode ignores `uv.lock`, so
   an install resolves the newest version inside each range. It resolved fastmcp 3.4.7;
   the suite ran on 3.4.3. `uv lock --script` would pin them exactly, but the lock files
   would need shipping in the Codex snapshot too.
6. **A system Python that has fastmcp.** The stamp runs there, not in the uv
   environment. On a native store with no coordinator running, it would start the
   coordinator under that interpreter. Not observed; the risk is noted.
7. **Not covered:** POSIX (no Job Object; `contained=False` by design); a Microsoft Store
   Python as the base interpreter (containment would fail closed, not open); the real
   Claude Code and Codex hosts.
