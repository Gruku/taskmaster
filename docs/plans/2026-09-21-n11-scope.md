## 1. What is actually true today (evidence, not assumption)

### 1.1 Half the outbox already exists. The protocol does not.

N05 delivered durable export intent, but N08 only used it as a work list.

- **Jobs commit with the command.** `Transaction._changed` inserts a
  `projection_jobs` row for every changed entity that owns a file, in the same
  `BEGIN IMMEDIATE` transaction as the domain events (`native/commands.py:170-178`).
  A move (archive/unarchive) inserts a `delete` job for the prior path, then a
  `write` job for the new one (`commands.py:173-178`, `prior_file` from `replace`,
  `:216`).
- **Inputs are already immutable.** `input_json` is the complete entity
  (`kind, id, revision, last_seq, archived, deleted, fields, body`) at that
  revision (`commands.py:165-166`). The drain renders from `input_json` and does
  not re-read the entity (`native_routing/projection.py:207-217`). The spec's
  "jobs reference immutable committed revision data" is met for per-entity files.
- **The schema anticipates the protocol, but nothing uses it.** `projection_jobs`
  has `state IN ('pending','claimed','exported','superseded','conflict')`,
  `lease_owner`, `lease_until` and `expected_hash` (`native/schema.py:80-84`).
  Grep finds no reader of `lease_owner`, `lease_until`, `expected_hash`, or the
  states `claimed` and `conflict` in `taskmaster/`. `expected_hash` is written as
  the `projection.content_hash` the committing transaction saw
  (`commands.py:173-178`) and never read.
- **The receipt already distinguishes commit from export.** `projection_state:
  "pending" | "unchanged"` (`commands.py:305-306`). Nothing ever reports
  "exported".
- **There are DB-side failure seams but no drain-side ones.** `execute` takes
  `checkpoint(stage)` at `admitted`, `mutated`, `receipt` and `before_commit`
  (`commands.py:297-311`). The drain has no equivalent.

### 1.2 What the N08 drain actually guarantees, and how

`native_routing/projection.py::drain` (`:266-299`) is the only native code that
writes projection files. The N08 bypass gate allowlists it. It runs after every
command (`native_routing/runtime.py:39-55`), and:

1. **It holds the writer lock for the whole drain, file I/O included.** It runs
   `BEGIN IMMEDIATE` through every render, `fsync` and `os.replace`, including
   `_replace_bytes`'s retry loop of up to 2 s per file (`:68-88`, `:274-295`).
   Its "no stale overwrite" guarantee comes entirely from this lock
   (docstring `:12-15`). N12 has to remove the lock, so N11 must replace the
   guarantee with something else.
2. **Coalescing is per file, latest job wins.** Every older pending job for the
   same file is marked `superseded` (`:281-291`). Jobs run in
   `(commit_seq, job_key)` order, so within a move the delete runs before the
   write. `moved_crlf` carries the old file's line endings to the new path
   (`:155-157`, `:216-217`).
3. **One failure un-does the whole drain's bookkeeping.** An exception anywhere
   rolls back every `projection` row and job state, including the ones whose
   `os.replace` already happened (`:297-299`). Today this is harmless, because
   the next drain simply rewrites. It stops being harmless once §1.4's
   expected-base check exists: a file whose bytes reached disk but whose record
   was rolled back will look like an external edit.
4. **Terminal jobs are never deleted.** Grep finds no `DELETE FROM
   projection_jobs`. Each commit keeps a full entity copy, body included, for
   each file it touches, so `projection_jobs` grows without limit.
5. **Derived files have no job.** Their freshness is `projection.exported_seq`
   compared with `MAX(entity_core.last_seq)` over the input kinds (`:222-229`).
   That covers `backlog.yaml` (backlog/epic/phase plus `derived.KINDS`) and
   `ideas/IDEAS.md`. Their intent is recomputed from committed state rather than
   stored, so it is already crash-safe. They are rendered from the current DB,
   not from an immutable input. That is correct for a whole-file derived render,
   but they need the same fencing as entity files (§2.3).
6. **PROGRESS.md is not rendered at all** (docstring `:22`; N08 intentional
   difference 7).

### 1.3 Quarantine and flags after the 6.0.3 back-merge

- `projection_conflict(file, kind, id, flagged_at, file_hash, file_content)`
  is a retained legacy table (`store.py:340-347`). B-089 made the legacy store
  keep both sides: the file bytes go into the row, the store keeps its version,
  and every export of that entity pauses until `resolve_projection_conflict`
  (`store.py:3718-3790`) picks `file` or `store`.
- The native drain honours flags **per entity**, as the legacy `_export_blocked`
  (`store.py:5316-5343`) does. `_held_files` (`projection.py:117-126`) combines
  `quarantined=1` and flagged files. `_entity_held` (`:191-205`) marks them dirty
  and warns once per drain. `8785ff8` fixed archive-of-a-flagged-task writing a
  second copy. Twin tests pin this
  (`tests/test_native_routing_overview.py:217-254`).
- **On a native store nothing can create a flag or a quarantine.** Both come from
  the legacy scan-before-write (`store._scan_projection`, `store.py:4459+`).
  Native never reads files back (bypass gate), so it only inherits flags made
  before activation. `backlog_resolve_conflict` refuses on native
  (`native_routing/registry.py:84-87`).
- **So a hand edit to a projection file is silently overwritten today** the next
  time that entity is written. `_Drain._write` compares the render against
  `projection.content_hash` (`:175-180`) and never against the bytes on disk.
  The N08 refusal text says so openly for handovers ("the next write to a
  handover re-exports its file over any hand edit", `registry.py:65-68`). The
  design forbids it: "External edits enter three-way merge or quarantine; never
  overwrite them just because a DB revision is newer" (§7). This is the gap
  N11's expected-base verification closes.

### 1.4 The two changelog stores, and why N08 had to refuse

- **Native queue:** `workflow._queue_progress_log` (`native/workflow.py:446-465`)
  runs inside `task.complete` (`:914-915`). It reads the whole
  `sync_state['pending_progress_log']` JSON list, appends
  `{"ts","text"}`, and writes the whole list back. Every completion therefore
  costs O(pending), so a store's lifetime costs O(n²). Nothing drains it.
- **Legacy queue and applied log:** `meta['pending_progress_log']` and
  `meta['progress_log']` (`store.py:179-183`, `:6298-6340`). The legacy exporter
  renders `applied[-room:] + pending` with `_PROGRESS_LOG_CAP = 200`. The cap
  trims only the applied tail, never unwritten paragraphs. It writes the file,
  then moves pending→applied in the same transaction (`store.py:5395-5452`).
- **The session-log region is regenerated whole from the applied log**
  (`backlog_server._render_session_log`, `:1780-1800`). Text outside the markers
  is preserved (`_changelog_section`, `:1803-1823`). This is why a crash between
  the file write and the pending→applied move is idempotent. It also means that
  a native applied log starting empty would **erase the legacy region's 200
  paragraphs** on the first native render. No real store is activated yet (only
  the test path in `tests/native_twins.py:119-150`), so this is latent. It is
  real at N15.
- **The native side cannot touch `meta` at all.** `native_stale_meta_*` triggers
  (`native/migrate.py:43-49`) set `native_manifest.state='stale'` on any `meta`
  write, and `assert_native` then refuses the store (`native/db.py:53-55`).
  Reading `meta` is safe.
- **The refusal:** `backlog_complete_task` with `session_title`, `done` or
  `auto_summary` answers `CHANGELOG_REFUSAL` and changes nothing
  (`native_routing/tasks.py:34-39`, `:395-396`). The core operation already takes
  a `changelog` argument (`workflow.py:914`). Only the adapter withholds it.
- **The paragraph text** is built by `backlog_server._append_changelog`
  (`:7222-7295`), which mixes formatting with queueing onto the legacy
  transaction (`_queue_changelog_entry`, `:7298-7312`). The native path needs
  the formatting without the queueing.
- **PROGRESS.md is local-only** (`.taskmaster/local/PROGRESS.md` for v4,
  `backlog_server.py:512-514`). The dashboard is not a pure function of committed
  state: `_time_remaining` reads the wall clock. The dashboard is rendered from
  a full `load_dict` plus `_derive_context` (`store.py:5419-5421`), throttled to
  once per 5 s unless paragraphs are pending (`:5401-5409`).

### 1.5 Recovery machinery the legacy store has and native does not need

The legacy export-intent journal (`export-intent.*.json`,
`store.py:1878-1990`) exists because legacy writes files *before* its
transaction commits, so a crash must restore prior bytes. Native commits first
and exports later: an interrupted export leaves a committed DB and an intent
row, never a file that is ahead of the DB. N11 needs the opposite recovery:
**finish forward**, never roll back. No journal file is required.

### 1.6 Summary: reuse vs build

| Need | Reuse | Build |
|---|---|---|
| Durable intent | `projection_jobs` rows committed with the command; immutable `input_json` | Retention rule; `exported_through` watermark |
| Leases | `state='claimed'`, `lease_owner`, `lease_until` columns; Linear queue's lease precedent (`store.LINEAR_CLAIM_LEASE_SECONDS`) | Exporter lease, claim/recover/ack transactions, fencing |
| Expected base | `projection.content_hash`, `mtime`, `size`; legacy flag table and `resolve_projection_conflict` semantics | Disk-vs-record verification before replace; own-bytes recognition; native flagging |
| Coalescing / moves | Per-file latest-wins, commit order, `moved_crlf` | Coalescing under leases; move ordering under crash |
| Tombstones | `delete` effect jobs | A retained per-file export record that says "absent on purpose" |
| Rendering | `store.render_entity_file`, `render_backlog_file`, `render_ideas_index`, `_render_progress_dashboard` | None. No second renderer. |
| Changelog | `task.complete` `changelog` argument; region renderer; legacy cap semantics | Per-paragraph rows, native applied log, seed from `meta`, adapter lift |
| Proof | Twin byte comparison (`native_twins.assert_files_match`, `:262-269`), fake clock, command checkpoints | Drain checkpoints, fault-injection matrix, subprocess kill, interleaving harness |

## 2. Concrete contract proposal

### 2.1 Layering: protocol in `native/`, rendering in `native_routing/`

- **New `taskmaster/native/projection.py`** holds the outbox *protocol*: leasing,
  recovery, coalescing selection, expected-base verification, the ack transaction,
  retention and tombstones. It does no rendering. It takes a `render(job) ->
  bytes | None` callable and a `checkpoint(stage, file)` hook. N12's
  `native/service.py` reuses it unchanged.
- **`native_routing/projection.py`** keeps the renderers, which call the legacy
  store's render functions so one entity is rendered one way, and exposes the
  synchronous compatibility drain. After N11 it is a thin adapter over the
  protocol.

### 2.2 Job lifecycle (design §7, made concrete)

```
pending ──claim(lease)──▶ claimed ──ack──▶ exported
   │                         │   └─verify fails──▶ conflict (entity held; see 2.5)
   │                         └─lease expires──▶ pending (recovered, same row)
   └─coalesced by a newer job for the same file──▶ superseded
```

- **Claim** is a short `BEGIN IMMEDIATE` transaction. It selects, per file, the
  latest pending job, skipping held entities (§2.5). It marks older ones
  `superseded`. It marks the survivors `claimed` with `lease_owner = <exporter
  nonce>` and `lease_until = now + LEASE`. Held entities' jobs stay `pending` and
  are **not** re-claimed on every call. Today's drain walks them every time.
- **Render and publish happen outside any transaction:** read `input_json`,
  render, write the temp file, verify the base, `os.replace`.
- **Ack** is one short transaction per job, not per drain. It re-checks the
  fence (§2.3), upserts the `projection` row (`content_hash`, `mtime`, `size`,
  `exported_seq`, `dirty=0`), sets the job to `exported`, applies retention
  (§2.6) and advances `sync_state.exported_through`. Per-job acks remove the
  §1.2(3) hazard: a published file is never left without its record because a
  later file failed.
- **Recovery:** a `claimed` job whose `lease_until` has passed goes back to
  `pending` at the next claim. It keeps its `job_key` and `commit_seq`, so
  ordering is unchanged.
- **`exported_through`** (`sync_state`, kv, no DDL) is the highest `commit_seq`
  S such that no job with `commit_seq <= S` is `pending` or `claimed`, excluding
  held entities, which are reported separately. N12's pending-projection receipts
  and N13's `flush_through` read it. N11 only maintains it and tests it.

### 2.3 Fencing: how a stale job can never overwrite newer content

There are two stale writers to defeat: an older job for the same file, and a
paused exporter whose lease expired while it was mid-publish.

1. **One exporter at a time per store.** A store-wide exporter lease
   `sync_state['projection_exporter'] = {owner, generation, until}` is taken in
   the claim transaction and renewed at each ack. Per-job leases then only
   matter for crash recovery. They are not the concurrency control. This is D1.
2. **Latest-per-file claim.** A file never has two claimed jobs, so an exporter
   holding the lease cannot publish an older revision after a newer one.
3. **Generation fence at ack.** Ack refuses if the exporter lease's `generation`
   is not its own. The refused exporter records nothing, and its job goes back
   through recovery.
4. **Residual window, stated honestly.** An exporter that checked its lease and
   was then paused past `until` can still `os.replace` after a successor
   published. No lock spans a filesystem rename, so the protocol cannot prevent
   this. It detects it instead. The successor's record now disagrees with the
   bytes on disk. The next verification (§2.4) sees a mismatch, and
   **own-bytes recognition** classifies it: bytes whose hash equals the render of
   any retained job for this file are the exporter's own and are safely
   overwritten. Anything else is an external edit and is flagged. The worst case
   is a brief stale file that the next export repairs. It is never a lost edit.

### 2.4 Expected-base verification

Before `os.replace`, the exporter compares the file on disk with the
`projection` row, i.e. the bytes the exporter last recorded for that file:

| Disk state | Record | Outcome |
|---|---|---|
| hash == `content_hash` | present | publish |
| missing | present, not a tombstone | **repair**: publish (design §7: "missing files are repaired") |
| missing | absent, or tombstone | publish (new file) |
| present | tombstone or absent | **flag** (a file appeared where we removed one or never wrote one) |
| hash == render of a retained job for this file | any | own bytes (crash or §2.3(4)): publish |
| anything else | present | **flag-and-keep-both** (D2) |

- `mtime`/`size` short-circuit the hash only when both match *and* the recorded
  `mtime` is older than the lease start (racy-git rule). Otherwise the exporter
  hashes. On CodeMaestro this costs one hash per exported file, not a scan.
- The job's `expected_hash` is **not** the base. It records what the committing
  transaction saw, and once jobs coalesce it is stale by design. It stays as a
  diagnostic, and the ack test asserts that it is never consulted for the
  decision.
- The same verification covers `backlog.yaml` and `ideas/IDEAS.md`. Hand edits
  to `backlog.yaml` are the most common case in practice.
- PROGRESS.md is **not** verified. It is a local, store-owned region inside a
  user-owned file, re-read on each render exactly as legacy does (§2.8).

### 2.5 Quarantine and flag-and-keep-both on the native side

- **Hold definition:** one function, `native/projection.held(connection, kind,
  id)`, replaces `_held_files`. Claim, `backlog_store_status` (`overview.py:112-115`)
  and resolve all call it. N09's §4d is the reason: two readers of one safety
  question drifted apart and reported a held task as clear.
- **Native flagging:** a §2.4 mismatch inserts `projection_conflict(file, kind, id,
  flagged_at, file_hash, file_content)` with the disk bytes, exactly the B-089
  shape. It sets the job to `conflict`, marks the row `dirty=1` and holds the
  entity. The DB keeps its version, and nothing on disk is touched. The caller
  sees `export pending: <file> is flagged`, the same text as today.
- **Held entities:** their newest job stays `pending` (older ones are coalesced
  as usual) and is not claimed until the hold clears. A move of a held entity
  writes neither path. `8785ff8` already pins this and it must stay green.
- **Resolution:** `take="store"` clears the flag, and the entity's latest job
  becomes claimable again. The replaced file text goes into the resolution's
  domain event, as legacy records it in its change row. `take="file"` needs a
  parse-and-import through native commands, which is N13's importer. D3 decides
  whether N11 ships only `take="store"`.
- **Quarantine** (`projection.quarantined=1`) is only ever inherited from legacy
  on a native store. N11 treats it as a hold, identical to a flag, and does not
  create new quarantines. Native has no unparseable-file state, because it never
  parses its exports.

### 2.6 Coalescing, archive moves, tombstones and retention

- **Coalescing** stays latest-per-file. It is coherent because every job is the
  complete truth for its file at its revision. A superseded delete for a file
  whose latest job is a write is simply not performed.
- **Move order: write the new path first, then remove the old one.** Today's
  order is the reverse (`job_key` order). A crash between the two steps then
  leaves the id in two places rather than in none. Two copies are visible and
  self-heal when the job is recovered. No copy at all is invisible, and N13's
  absence-is-not-deletion rule would never repair it. `moved_crlf` probes the
  old file before the new one is written, so line endings are unchanged.
  Implementation: claim orders a move's `write` before its `delete` by pairing
  jobs on `(entity_key, commit_seq)`, with no schema change.
- **Tombstones:** the latest terminal job for a file is kept as that file's
  **export record**. When that record is a `delete` (or a write that rendered
  `None`), it is the tombstone: the file is absent on purpose. §2.4 reads it, and
  so will N13 when it tells a user-deleted file from a moved one. Tombstones
  never expire in N11. A tombstone is superseded only by a later job for the
  same path. No native command sets `entity_core.deleted=1` today (grep), so
  every N11 tombstone is a move or a heavy-field-cleared epic/phase, not an
  entity deletion.
- **Retention (D7):** the ack transaction deletes every older terminal job
  (`exported`, `superseded`) for the same file. The table is then bounded by the
  number of files plus in-flight work, not by history. `conflict` jobs are
  kept until resolved.

### 2.7 The synchronous compatibility drain

- `NativeCall.execute` keeps calling `drain()` after each command. `drain()`
  becomes: claim through `commit_seq`, publish, ack. If another process holds
  the exporter lease, the call **waits** (bounded, default 5 s, on the fake
  clock in tests) until `exported_through >= commit_seq` or a hold explains the
  gap. On timeout it returns `export pending: … — retried on next call`, the
  notice the legacy store already uses. That is the N12/N13 `flush_through`
  barrier with a finite target.
- **Visibility is unchanged:** on a single-client store every command's files
  are on disk before the call returns, byte-identical to today's. The existing
  twin suite (`native_twins.assert_files_match`) is the regression fence and
  must pass unmodified.
- **The writer lock is no longer held during file I/O.** This is the one
  observable change: a peer's command no longer waits behind a slow `fsync`.

### 2.8 Changelog: rows, applied log, seed, render

- **Pending paragraphs become rows (D4).** One `sync_state` key per paragraph,
  `progress.pending.<commit_seq:012d>.<n>`, with value `{"ts","text"}`. Lexical
  order is commit order, the drain reads it with one PK range scan, and an append
  is a single insert with no read-modify-write. No DDL is needed. The drain also
  reads the pre-N11 key `pending_progress_log` (a list) as entries that come
  before every keyed row, then deletes it.
- **Native applied log:** `sync_state['progress.applied']`, capped at 200 with
  the legacy rule that the cap trims only the applied tail, never unwritten
  paragraphs. The render uses `applied[-room:] + pending`. The file is written
  first. Then, in one transaction, pending rows are deleted and appended to
  applied. A crash between the two re-renders an identical region. Rewrite cost
  is O(200 + pending) per completion, bounded, instead of O(lifetime).
- **Seed once from `meta` (D5), read-only.** If `progress.applied` is absent,
  copy `meta.progress_log` into it, and `meta.pending_progress_log` into keyed
  rows, then set `sync_state['progress.seeded'] = {"seq": …}`. `meta` is never
  written. N15 then verifies the seed instead of assuming either store is empty,
  as the plan requires.
- **Render:** PROGRESS.md is a local artifact, not a projection job. The drain
  renders it when pending rows exist, and otherwise at most every 5 s (the
  legacy throttle). The dashboard input comes from native reads (D6). A failed
  write leaves the rows pending and warns `export pending:
  local/PROGRESS.md — retried on next call`, as legacy does.

## 3. Step breakdown

Twelve steps. Each is `test-first`: a failing behavioural test commit, then the
implementation commit.

has exactly one owner.** The other track reaches it only through a named seam
that the owner creates first.

- **Track P (protocol): S1–S6, S10, S11.** Owns `native/projection.py` (new),

## 4. The open decisions

### D1 — Exporter concurrency: store-wide lease, or keep the writer lock?

**Options.** (a) Keep today's `BEGIN IMMEDIATE` across the drain, and exercise
leases only through simulated interleavings. (b) A store-wide exporter lease in
`sync_state` with a generation fence, I/O outside the writer lock, and callers
waiting through their `commit_seq` (§2.3, §2.7). (c) Per-file leases, allowing
several exporters in parallel.

**Tradeoff.** (a) is safest today, but it tests a protocol that never runs
concurrently, and N12 must re-do the concurrency work under time pressure.
(c) buys parallel `fsync` that nobody needs at 3.6k entities, at the cost of
cross-file ordering: a move spans two files. (b) matches N12's "one coordinator
serializes export/import publication" and is testable now with multiple MCP
processes, which already exist.

**Recommendation: (b).** Lease 30 s, renewed per ack; wait-through 5 s.

### D2 — What does a native export do when the file on disk is not what it last wrote?

**Options.** (a) Flag-and-keep-both: `projection_conflict` holds the file bytes,
the entity's exports pause, and resolve picks a side. (b) Quarantine: the file is
set aside and the export proceeds. (c) Overwrite, as today.

**Recommendation: (a).** It is B-089's contract, the table and hold logic already
exist on both stores, and the design forbids (c). **This is a user-visible
behaviour change on native stores.** Today a hand edit is overwritten silently.
After N11 it is kept and the entity's exports stop until someone resolves it.

### D3 — How much of `backlog_resolve_conflict` ships in N11?

**Options.** (a) `take="store"` only; `take="file"` refused until N13's importer.
(b) Both, pulling a single-file parse-and-import forward from N13. (c) Neither;
flags are cleared only by legacy tooling, which cannot open a native store.

**Recommendation: (a).** (c) creates a state that no native tool can leave.
(b) duplicates N13's revalidate-and-apply path in a hurry. Under (a), a user who
wants the file's version can copy the text from the flag detail into a normal
edit, and the refusal text says how.

### D4 — `pending_progress_log`: bound it, or move it to rows?

**Options.** (a) Keep the JSON list and cap it (a cap on pending text destroys
paragraphs that exist nowhere else). (b) Keep the list uncapped but drain it
every call; the cost is bounded in steady state and quadratic while PROGRESS.md
cannot be written. (c) Rows as per-paragraph `sync_state` keys, no DDL.
(d) A new `progress_log` table, which means a staging schema bump to 4 and a
re-backfill of every native store.

**Recommendation: (c).** Append becomes O(1) and never read-modify-writes. It
needs no schema change, which is the cost N09's D6 also avoided. The applied log
stays a capped blob, which the cap bounds.

### D5 — Does N11 seed the native changelog state from legacy `meta`?

**Options.** (a) Seed once, read-only, behind a `progress.seeded` marker. (b)
Leave it to N15's activation.

**Recommendation: (a).** Without it, the first native render rewrites the
session-log region from an empty applied log and erases up to 200 paragraphs
(§1.4). N15 would then carry a data-loss trap that only its own diligence
prevents. Reading `meta` is safe. N15 still owns cutover-time reconciliation,
which becomes verifying the seed.

### D6 — Where does the native PROGRESS dashboard get its data?

**Options.** (a) The existing native tree read plus `_derive_context`, throttled
to 5 s as legacy does, recorded as a known full read for N16. (b) Targeted
aggregate queries now (per-epic done/total, first in-progress, active phase,
context lists), proven equal by twin tests. (c) Refresh only when a paragraph is
pending.

**Recommendation: (a) in N11, with (b) filed for N16.** The dashboard is local,
throttled and already a full read on legacy, so it is no regression. (c) makes
it stale by design. (b) is a performance change and belongs to N16's gates.
Exclude it from the "no full-tree materialization on a normal command" assertion
by name, not by silence.

### D7 — Job retention

**Options.** (a) Keep the latest terminal job per file as its export record and
tombstone, and delete older terminal jobs at ack. (b) Keep everything, as today.
(c) Time-based pruning.

**Recommendation: (a).** (b) grows by a full entity copy per commit per file.
(c) can delete the tombstone that N13 needs. Nothing reads job history today:
receipts and cursors use `domain_events`.

### D8 — Does Linear `retry` stay refused through N11?

**Recommendation: yes; its owner becomes N12.** It is an outbox too, but a remote
one. Running it inside a synchronous per-call drain puts network latency and
retries in every tool call, which N12's coordinator worker exists to avoid.
Queued rows are already kept and listed.

## 5. Risks, and what the proof method can and cannot prove

### 5.1 What stays the regression fence

The twin suite compares legacy and native projection bytes (`assert_files_match`)
after every journey. N11 must not change a single byte of any exported file on a
single-client store, apart from PROGRESS.md, which is newly produced and
compared by its own twin test in S8/S9. Unchanged-byte behaviour is asserted
directly: an edit that renders the same bytes performs no `os.replace`, which
is counted.

### 5.2 The failure-injection matrix (the plan's list, made exhaustive)

Each cell is a test with two variants: an exception injected at the checkpoint
(in-process), and `os._exit` at the checkpoint in a subprocess, followed by
recovery in a fresh process.

| Injection point | Expected state after the crash | Recovery must |
|---|---|---|
| before DB commit | no events, no job, files untouched | nothing to do; retry of the same `request_id` executes once |
| after DB commit, before claim | job `pending` | next drain exports it; `exported_through` catches up |
| after claim, before temp write | job `claimed`, lease live | after lease expiry, recover to `pending` and export; before expiry, the waiting caller times out with the pending notice |
| after temp write, before replace | stray `*.tmp.<session>`, file unchanged | export normally; the stray temp is removed only if it is this job's temp name |
| after replace, before ack | file has new bytes, record has old hash | own-bytes recognition acks without a flag and without a rewrite |
| during ack (manifest upsert or job state) | transaction rolled back as a unit | same as the previous row |
| after ack, before retention | old terminal jobs remain | next ack prunes them; tombstone unaffected |
| move: after new-path write, before old-path remove | id in two places | next drain removes the old path |
| PROGRESS: after file write, before pending→applied | file carries the paragraphs, rows still pending | re-render gives an identical file; no duplicate paragraph |

Two concurrency scenarios, with interleaving forced by checkpoints and then one
real two-process run:

- **A newer DB edit while an old job is rendering.** The older job publishes,
  the newer job publishes after it, and the final bytes are the newer
  revision's. With a paused exporter past its lease (§2.3(4)): a transient stale
  file, own-bytes recognition, then the correct final bytes, and no flag.
- **An external edit while an old job is rendering.** The flag is created with
  the external bytes preserved exactly. Nothing is published for that entity.
  `take="store"` then publishes the newest revision.

**Lossless v4 artifacts:** after every recovery, each exported file parses back
through the legacy parser to its job's `input_json` (fields, body and field
shapes), using `render_entity_file`'s round-trip oracle. `backlog.yaml` is
compared by document. This proves that export loses no authored data. It does
not prove that an import would accept the file; that is N13.

### 5.3 What this proof cannot show

- **Power loss.** `os._exit` proves process-death recovery. It says nothing about
  write reordering below the filesystem. Directory `fsync` is not available on
  Windows. Record this as a limit and do not claim it.
- **Real sharing violations.** Antivirus or indexer locks are simulated with
  injected `errno` values. The existing retry path is reused, not re-proven.
- **Unbounded pauses.** §2.3(4) is detected and repaired, not prevented. The
  tests prove the repair. Whether a stale file is ever visible to a concurrent
  Git operation is N13's generation barrier, and the report must say so.
- **N12 behaviour.** The synchronous adapter proves the protocol under the call
  pattern that exists today. Asynchronous export with pending receipts is N12
  and is not implied.

### 5.4 Risks specific to N11

- **False flags are the failure mode to fear most.** Every cause is a place where
  the recorded hash drifts from bytes the exporter itself wrote: the rolled-back
  drain, line-ending matching, a render that is not deterministic. Each flag
  halts an entity's exports. Test each drift source separately. Line endings:
  the render must match what `_match_line_endings` produced from the file
  before replace, so own-bytes recognition compares against the matched bytes,
  not the LF render.
- **A behaviour change hides inside "visibility unchanged."** D2 turns silent
  overwrites into flags. The N11 report must list it as an intentional
  difference, and the refusal and guidance texts that describe the old
  behaviour must change in S10.
- **The dashboard reads the wall clock.** `_time_remaining` makes PROGRESS.md
  differ between renders on different days. The twin test pins the clock. The
  throttle must not treat a date change as a reason to render.
- **Wait-through can turn into a hang.** A holder that crashed keeps the exporter
  lease until `until`. Callers must time out and report pending rather than
  block. This is tested, and the lease holder's liveness is visible in
  `backlog_store_status`.
- **Seeding reads `meta` on every drain until the marker exists.** A crash
  between seeding and setting the marker must not seed twice. Write both in one
  transaction.
- **Track C starts on files that `n09-collapse` is still changing.** Starting it
  before that merge recreates exactly the §4d debt this plan is structured to
  avoid.

## Protocol track notes (S1–S6, S10, S11, recorded 2026-09-21)

What the implementation found that this document did not say, and where it
deviates. Branch `feat/native-n11-protocol`.

**Protocol (S2–S5)**

- **Own-bytes recognition cannot re-render retained jobs.** §2.3(4) and D7
  conflict: retention deletes exactly the superseded job whose bytes a paused
  exporter publishes, so "hash equals the render of any retained job" misses
  it and false-flags. Instead, a fenced *publish-intent* transaction records,
  before any file is touched, the hash of every byte string about to be
  published in a per-file ring (`sync_state['projection.own.<file>']`, last
  8). Verification treats bytes in the ring as the exporter's own. A user who
  restores a file to one of the last 8 renders gets it overwritten; that loses
  no authored data (it is an earlier DB state), but it is not a flag.
- **The §2.3(4) repair needs a trigger.** Nothing re-exports a file whose
  record is newer than its stale bytes. An exporter whose ack is refused by the
  fence re-queues the file's export record (latest `exported` job back to
  `pending`; a derived file marked stale) unless the file already has a
  pending, claimed or conflicted job. The next drain then sees own bytes and
  repairs. Residual gap: an exporter that dies between that late replace and
  its refused ack leaves the stale file until the entity's next write.
- **Recovery is by generation, not by per-job `lease_until`.** Taking the
  exporter lease recovers every `claimed` job, since only an earlier
  generation can hold one. Per-job `lease_owner` (`owner#generation`) and
  `lease_until` are diagnostic. An in-process failure releases the lease at
  once; only a dead process makes the next caller wait for expiry.
- **Retention runs in its own transaction after the acks** (`Exporter.finish`),
  matching §5.2's "after ack, before retention" row rather than §2.2's "ack
  applies retention".
- **Verification runs twice:** before the temp write (so an unchanged render
  does no I/O) and again right before `os.replace`. A `before_replace`
  checkpoint names the residual rename window. The `mtime`/`size`
  short-circuit of §2.4 is not implemented: every exported file is hashed.
- **Temp names are per job** (`<name>.tmp.j<job_key>`, `.tmp.d<seq>` for
  derived files). A recovered job overwrites its own stray; strays of jobs
  superseded after a crash are never removed.
- **`projection_conflict` may not exist** on a store no 6.0.3 writer opened.
  The first native flag creates it with the legacy definition
  (`CREATE TABLE IF NOT EXISTS`), the only DDL in N11.
- **`exported_through` covers jobs only.** Derived files have no job and are
  not in it. It can move backwards when a hold is released; resolve
  recomputes it.
- **Hold by entity or by file.** `held()` joins on `(kind, id)`; the claim
  predicate also holds a job whose own file is flagged or quarantined, which
  covers legacy rows whose `id` is NULL (for example `project.yaml`).

**Drain (S6)**

- **The S1 defects flip at S6, not S2/S3:** S2–S5 test the protocol with an
  injected renderer, and the tool path only moves onto it at S6.
- **Commits per drain grew** from one to claim + intent + one ack per file +
  retention + release, each `synchronous=FULL`. An N16 performance-gate
  input.
- The timeout notice lists every pending file in the store, not only the
  caller's.
- Test infrastructure: the conftest projection-write guard now admits
  `native/projection.py`; `tests/native_twins.py` gained `commit_only` and
  `native_connection`.

**Resolution (S10)**

- `take="store"` adopts the hash of the bytes the resolver saw as the file's
  base, so the next export replaces exactly them and a newer hand edit is
  flagged again. It queues fresh jobs at the resolution's own sequence: a
  write of the entity's current path, plus a delete of the flagged path when
  the entity now lives elsewhere. A flag inherited from legacy with no native
  job is therefore also re-exported. Derived files are marked stale.
- The `projection.resolve` handler lives in `native/projection.py`;
  `native/lifecycle.py` only dispatches to it.
- The adapter must read the flagged file through `native_routing/projection.py`
  (`read_file`, `store_version`), because the N08 bypass gate allows
  projection reads only under the export module. The gate gained an exercise
  for the tool.

**Gaps outside this track's files**

- **Native results do not carry the per-result flag notice.** Legacy
  `_attach_conflict_notices` names every flagged file on every result through
  `store.opened_store`, which is None in a native process. A native flag is
  named only on the call that creates it, on calls that queue a write for the
  held entity, in `backlog_store_status` and in `backlog_resolve_conflict`.
  The fix is in `backlog_server.py`, which belongs to Track C; route it to S9
  or S12.
- **Exporter-lease liveness is not in `backlog_store_status`** (§5.4). The
  report shape (`StoreStatus`, `_render_store_report`) lives in `store.py` and
  `backlog_server.py`. Deferred.
- **§5.2's PROGRESS row** belongs to S8 (Track C) and is not covered here.

  `test_native_contracts.py::test_native_inventory_matches_registered_source_contracts`

### Review fixes (adversarial review of `4f5f377`, probes P1–P8)

An independent review confirmed seven defects. Each now has a test in
`tests/test_native_projection_review.py` (failing commit `9662c9b`, fix

1. **P1, HIGH: an edit in the rename window was overwritten, and removals had

3. **P8, MEDIUM: a line-ending-only flip was flagged.** The verdict now matches

4. **P3, MEDIUM-LOW: `LeaseLost` from `intend` escaped after the command had

5. **P2, LOW: a waiting caller trusted `exported_through`, which ignores

6. **P4, LOW: `take="store"` decoded the replaced bytes lossily and dropped the

   - `file_missing`;

7. **P5, LOW (pre-existing): an inherited quarantine could never clear.**

## Changelog track notes (S7–S9, recorded 2026-09-21)

What the changelog track found that this document did not say, and where it
deviates. Branch `feat/native-n11-changelog`, off `22052d4`. Tests:
`tests/test_native_progress.py`.

**Rows and seed (S7)**

- **Keys are `progress.pending.<commit_seq:012d>.<n:04d>`.** §2.8 left `<n>`
  unpadded, which misorders from the tenth paragraph of one commit. A completion
  counts only its own commit's keys (a bounded range scan) and inserts one row. A
  test diffs `sync_state` around each of 30 completions: exactly one added row,
  none changed or removed. That pins the plan's quadratic note.
- **Seeded and pre-N11 paragraphs are rows at commit sequence 0.** Two sources
  become `progress.pending.000000000000.*` rows, so they sort before every
  completion:
  - `meta.pending_progress_log`: legacy paragraphs not yet written;
  - `sync_state.pending_progress_log`: the pre-N11 native list.

  §2.8 reads the old list at render time and deletes it afterwards. Here it is
  folded into rows and deleted in one write transaction, the one that takes the
  writer lease and seeds. A pre-N11 process that appends to the old key later is
  folded in on the next render.
- **The seed never overwrites.** Suppose `progress.applied` existed without the
  marker. The seeded entries would go in before it, and nothing would be dropped.
  The copy and the `progress.seeded` marker share one transaction. A crash
  injected before its commit leaves neither behind. `meta` is only read. The seed
  test compares every `meta` row and the manifest state (`ready`) before and
  after.
- **Retry dedup is the receipt's.** A retried `request_id` returns the first
  receipt and queues nothing, so the paragraph is logged once.

**Render (S8)**

- **A second lease: `sync_state['progress.writer'] = {owner, generation, until,
  rendered_at}`.** §2.8 did not say what stops two processes rendering at once
  when no writer lock spans file I/O. The seam runs after the projection
  exporter has released its lease. Without its own lease, a slower process's
  older render could replace a newer one. The steps:
  1. Take the lease and seed, in one short `BEGIN IMMEDIATE`.
  2. Render from one read snapshot.
  3. Write the temp file, check the lease, then `os.replace`.
  4. Move the rows and end the lease, in one fenced transaction.

  An in-process failure ends the lease at once. A dead process holds it for
  `LEASE_SECONDS` (30).
- **Waiting.** Only the paragraphs a caller's own commit queued can make it
  wait. They are the rows keyed by its `commit_seq`, passed through the drain as
  `through`.
  - If another writer holds the lease, such a caller waits up to 5 s. It then
    reports `export pending: local/PROGRESS.md — retried on next call`, and its
    rows are kept.
  - It waits at most once per call. After the pending notice, later commands in
    the same `NativeCall` do not wait again (`progress_wait=False`).
  - A caller that owes only a dashboard refresh returns at once and reports
    nothing, even while other paragraphs are pending behind a dead writer.
  - **In the worst case this wait stacks on the drain's own 5 s wait, for 10 s
    in total.**
  - Review fix, 2026-09-21: the first version waited whenever any paragraph was
    pending. During a crashed writer's 30 s lease, that cost every native write
    5 s.
- **Failures are logged** to `local/store.log` as `progress export failed:
  {exc!r}`, as the legacy `_regenerate_progress_if_due` logs them. One case is a
  PROGRESS.md that is not valid UTF-8. That file is left byte-for-byte alone, the
  rows stay pending, and every completion warns until someone repairs the file,
  exactly as on legacy. Like legacy, the render writes LF, so a PROGRESS.md
  converted to CRLF by hand is written back as LF.
- **The throttle is cross-process.** It is `rendered_at`, on the wall clock
  (`HOOKS["clock"]`). Legacy uses a per-process monotonic clock. A clock that
  goes backwards makes a render due; it never stalls one. A date change is not a
  reason to render.
- **The move deletes rows by key and appends only the rows it deleted.** A render
  that raced a successor can therefore never double a paragraph in the applied
  log. The cap rule is legacy's: `applied[-room:] + moved`, where
  `room = CAP - len(moved)`. With more than 200 paragraphs pending, all of them
  are written and kept.
- **Residual window, stated honestly.** A writer's lease can expire after its
  check and before its `os.replace`. It then installs a file that lacks
  paragraphs a successor has since moved to `progress.applied`, and its fenced
  move records nothing. Nothing is lost: those paragraphs are in the applied log
  and reappear on the next render (at most 5 s later, or with the next
  changelog). This has the same shape as §2.3(4). PROGRESS.md is not verified
  against a base (§2.4).
- **§5.2's PROGRESS row is covered in both variants.** Each checkpoint below is
  tested as an in-process exception and as `os._exit` in a subprocess. (This
  note first claimed that before it was true: the N11 report found only
  `progress_written` killed in a subprocess. The other three kill variants were
  added afterwards, in `test_a_killed_process_at_every_checkpoint_loses_nothing_and_leaves_no_temp`.)
  - At `progress_written`, recovery writes byte-identical bytes and applies the
    paragraph once.
  - At `progress_applying`, a crash inside the move transaction rolls it back as
    a unit.
  - At `progress_seeded`, nothing is left half-seeded.
  - At `progress_temp_written`, a failed write keeps the rows, removes the temp
    and warns. A kill cannot remove its temp, so the lease holder records the
    temp name in `progress.temps` before writing, and the next lease holder
    drops every recorded name that matches `PROGRESS.md.tmp.<session>` in
    PROGRESS.md's own directory, and nothing else.
  - After every kill, the next call writes the paragraph exactly once, moves it,
    and leaves no `PROGRESS.md.tmp.*`.
- **D6's full read is named, not silenced.** The suite has no "no full-tree
  materialization" assertion to exclude the dashboard from. Instead, a test names
  `reads.tree` as the one full read a normal native command makes. It pins that
  read to at most once per 5 s unless a paragraph is pending.

**Lift (S9)**

- `backlog_server._append_changelog` is split:
  - `_changelog_entry` is the pure formatter;
  - `CHANGELOG_LOGGED` and `CHANGELOG_AUTO_LOGGED` are the answer suffixes;
  - legacy queueing is unchanged.
- The native adapter passes `changelog=` to `task.complete`. `CHANGELOG_REFUSAL`
  and its test are deleted.
- Twin tests compare answers and PROGRESS.md byte for byte after structured,
  `auto_summary` and done-only completions. They also do so after a legacy store
  that already has a session log is activated.
- Differences 2 and 7 are lifted. The N08 report, a historical record, still
  lists them. S12's N11 report should say they are lifted.

**Routed from the protocol track**

- **Flag notices on native results.** `registry.dispatch` names every flagged
  file on the outermost native result. It uses one query against
  `projection_conflict` and the legacy `_with_conflict_notices` (split out of
  `_attach_conflict_notices`).
  - **The wording differs from legacy at the end.** It offers `take="store"` and
    says that keeping the file's version needs N13 (D3). Legacy offers
    `take="file"`, which native refuses.
  - `test_native_projection_resolve`'s `take="file"` test now reads the refusal
    text ahead of the appended notice.
- **Exporter-lease liveness in `backlog_store_status`.** The drain now writes the
  lease owner as `<session>:<nonce>:<pid>@<host>`. A native-only `Exporter lease:`
  line reports one of:
  - `free`, naming the last holder;
  - held, with the time left and either `pid N running on this host` or
    `pid N not running on this host`;
  - `not checkable from here` when the holder is on another host;
  - `holder process unknown` when the owner was written before this change.

  **Limit:** a pid check cannot recognize a reused pid, or one hostname shared
  by two machines. Either reads as running. So the line reports the pid rather
  than claiming the holder is alive. Recovery never relies on it; it relies on
  the lease's expiry. Comparing the process start time would close the gap, but
  that needs per-OS code (`GetProcessTimes`, `/proc/<pid>/stat`). It is not
  worth it for a diagnostic line.

  `StoreStatus.exporter_lease` defaults to None, so the legacy report is
  unchanged. The overview label test now expects the one extra line. The
  `sessions` table is not used, because native stores do not write it.

**Open risks**

- **The dashboard's cost at scale is unmeasured.** The full read, at most every
  5 s, has not been timed on CodeMaestro. It is D6's accepted cost; targeted
  queries are N16's.
- **Dashboard parity is proven only on small fixtures.** Native orders epics by
  `entity_key` and legacy by `rowid`. S12's copied-CodeMaestro twin must compare
  `local/PROGRESS.md` too.
- **A hand edit to PROGRESS.md can still be lost.** An edit made between the
  render's read and its replace is overwritten, exactly as on legacy.
