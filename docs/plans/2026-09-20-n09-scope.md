## 1. What is actually true today (evidence, not assumption)

### 1.1 The read path N09 has to replace

Every whole-backlog read tool on a native store goes through
`native_routing/reads.py::tree()`, which its own docstring admits reads *every*
task (`reads.py:203-240`). `tree()` backs `backlog_status`,
`backlog_blast_radius`, `backlog_validate`, and — through
`reads.epics()` + `reads.epic_tasks()` per epic — `backlog_next_available`
(`tasks.py:891`) and `backlog_dependencies`' downstream scan (`tasks.py:876-881`).
`backlog_dependencies` additionally does one `find_task` per declared dependency,
and `find_task` itself is a full `snapshot.get(..., include_body=True)` — prose
included — for a call that only needs `status` and `title`.

So the N09 "fewer calls/bytes" exit is not only a tool-count argument. The
current native answer to "what should I do next" reads every task, every body,
and re-derives `context` (`backlog_server.py:1595`) on each call. That is the
baseline to beat, and the only honest way to report it is per-call
(entities read, bodies read, encoded answer bytes), measured on the CodeMaestro
copy, not inferred.

### 1.2 Is `domain_events.seq` a sound cursor basis? — Yes, with three caveats

Evidence:

- `seq` is `INTEGER PRIMARY KEY AUTOINCREMENT` (`schema.py:73`), so it is
  monotonic and never reused within a store's life.
- It is allocated inside the command's writer transaction (`events.py:9`), and
  a native command is one transaction under `BEGIN IMMEDIATE`
  (`commands.py:255-285`). SQLite permits one writer at a time, so seq order
  **is** commit order — there is no "committed out of sequence" window, and a
  reader can never see seq N without also seeing every seq < N.
- A rolled-back command rolls back `sqlite_sequence` with it, so an aborted write
  leaves no gap and no phantom seq.
- Multi-entity commits are already grouped: every event carries
  `commit_key → command_commits(first_seq, final_seq, operation)`
  (`schema.py:72-75`, `events.py:12`). The spec's "multi-entity commit grouping"
  cursor test has a real column to assert against; nothing needs inventing.
- The store-wide watermark is maintained: `commands.py:280` writes
  `_put_manifest(event_high_water=transaction.seq)` in the same transaction,
  and only when `transaction.affected` is non-empty — i.e. exactly when events
  were appended. So `native_manifest.event_high_water == MAX(domain_events.seq)`
  is an invariant, and `verified_snapshot` already hands every reader that value
  (`db.py:63-80`, `queries.py:64`).

Caveats that the contract must handle:

1. **`ix_domain_events_entity` is `(kind, id, seq)`.** There is no index on
   `(seq)` beyond the primary key, which is enough for an unfiltered
   `WHERE seq > ?` scan but *not* for a scoped one (`WHERE seq > ? AND kind=?`
   will scan the PK range and filter). For the scope filters we actually need
   (kind, entity id, epic) this is acceptable at CodeMaestro's ~3.6k entities;
   it must be measured, not assumed, before an index is added. Adding an index
   is a schema change — see D6.
2. **There is no history expiration anywhere.** `grep` finds no `DELETE FROM
   changes` and no `DELETE FROM domain_events` in `taskmaster/`. The spec asks
   for a cursor test covering history expiration, so N09 must *define* the floor
   contract even though nothing prunes yet (D4).
3. **`event_high_water` is the wrong invalidator for a change cursor.** The
   existing list cursor deliberately binds to it (`queries.py:165`), so any write
   invalidates a half-finished page. That is right for a paged snapshot read and
   catastrophic for `changes_since`, whose whole job is to survive writes. The
   two cursors are different animals and must not share `_continuation`.

**Store rebuild discriminator.** `source_digest` is written once at backfill
(`migrate.py:243`) and `store_id` is `meta.creation_token`. A re-backfill
reallocates entity keys and rewrites `source_digest`; a B-092-style rebuild from
the projection produces a new database and therefore a new `creation_token`.
So `(store_id, source_digest)` is a sound rebuild fence, and `queries.py:165`
already uses exactly that pair. Reuse it.

### 1.3 The claim surface that already exists

`locked_by` is a task-operational column (`schema.py` `task_operational`) written
by `task.pick` (`workflow.py:759-781`). Its current semantics:

- Contested **only** when the task is already `in-progress`. A `todo` or
  `in-review` row carrying a stale `locked_by` is silently claimed
  (`workflow.py:771-776`) — deliberately, matching the legacy tool.
- `force=True` steals unconditionally, with no record of the theft.
- There is **no expiry, no renew, no release**. A task completed or archived
  drops `locked_by` via `_task_update` (`workflow.py:638`, `658-662`); a session
  that dies holds the lock until a human passes `force=True`.
- Bundle picks lock every member atomically in one transaction
  (`workflow.py:783-807`) — the all-or-nothing behaviour a claim needs is
  already there.
- Session identity never enters the database by design (N08 constraint 4): the
  adapter passes `bs.SESSION_ID` as an argument.

The liveness signal N09 needs already exists too, in the **retained legacy**
`sessions` table: `session, pid, host, started, last_seen, cwd, current_tool`.
`overview.py:120-130` already computes "live" from it (`last_seen` within 60 s,
or a live local pid). `sessions` is in `RETAINED_TABLES` (`schema.py`), so it is
writable local-only state that does not invalidate the native manifest.

**This is the single most important reuse finding for N09:** claim expiry does
not need a new lease table or a wall-clock TTL column. A claim is expired when
its holding session is not live by the definition `store_status` already uses.

### 1.4 Mandatory blockers and gates already have a pure definition

`taskmaster_v3.py:452-500` gives, as pure functions on a task document:
`required_gates(lane)`, `blocking_gates(lane)` (verdict gates only — status gates
are progress markers), `gate_satisfied(rec)`, `outstanding_required_gates(task)`
and `compute_gate_state(task)`. `backlog_task_pipeline` (`tasks.py:605`) already
renders them. Dependency blocking is computed ad hoc in three different places
(`tasks.py:299` pick, `tasks.py:891` next_available, `backlog_server.py:1595`
`_derive_context`) with three slightly different treatments of a missing
dependency. N09 must collapse that into one function or the "missing mandatory
context is never reported as clear" exit cannot be proven.

Other mandatory-context producers that exist and are already bounded:
`_open_handovers(snapshot, task_id)` (`tasks.py:~660`, one indexed membership
query), `_bugs_found_in(connection, task_id)` (`workflow.py:326`), and the
close-gate bug check that N08's review had to fix for list-shaped `found_in`.

### 1.5 Document detail — built, wired to nothing

`Snapshot.document()` (`queries.py:238`) and `native/documents.py::retrieve()`
exist from N04 and have **no production consumer** — only
`tests/test_native_documents.py` calls them. They return exactly what the spec
asks for: selected sections, `unresolved` with a `not_imported` reason,
`provenance` (path, content_hash, imported_seq) and an `incomplete` flag.

Meanwhile the routed `backlog_get_task` with `sections=` calls
`taskmaster_v3.resolve_sections(..., project_root=...)` (`tasks.py:682-700`),
which **reads the filesystem** and substitutes the literal string
`(unresolved: <path>)` when a doc is missing. Nothing populates
`external_documents`; no importer exists outside a test's direct INSERT.

So document detail in N09 is: route the existing native retriever, and decide
what fills `external_documents` (D7).

### 1.6 Structured mutation — what N08 left

`contracts.validate_operation` (`contracts.py:26-70`) already defines a typed,
validated envelope with `expected_revisions` preconditions, a 1 MiB encoded
cap, a 100-command batch cap, and durable per-`(store_id, caller_scope,
request_id)` receipts (`receipts.py`). `native/batch_lines.py` turned the legacy
batch line rules into pure functions, and `native_routing/batch.py` pre-validates
lines against a snapshot overlay before submitting one all-or-nothing native
batch. The structured mutation interface N09 owes is therefore **an exposure
decision, not a new engine** — see D5.

### 1.7 Summary: reuse vs build

| Need | Reuse | Build |
|---|---|---|
| Change cursor basis | `domain_events.seq`, `command_commits`, `native_manifest.event_high_water`, `(store_id, source_digest)` fence | Scoped change query; a cursor codec that does **not** bind to `event_high_water`; a retention-floor contract |
| Bounded context | `Snapshot.get/list/summary`, `_open_handovers`, `_bugs_found_in`, `blocking_gates`/`outstanding_required_gates` | One mandatory-blocker resolver; byte budgeting; omission counts; provenance |

| Structured mutation | `contracts.validate`, `expected_revisions`, receipts, `batch_lines` | Typed tool exposure only |
| Claims | `locked_by`, `task.pick` transaction, bundle atomicity, `sessions` liveness, `store_status` live-session rule | `renew`/`release` operations; expiry predicate; conflict answers; visibility |
| Proof | `tests/native_twins.py` (legacy↔native parity), `native_oracles.py`, fake clock | A journey harness measuring calls/entities/bytes; property tests for the cursor; a concurrency test for claims |

## 2. Concrete contract proposal

Conventions: every tool keeps the project's `-> str` return. Structured answers
are JSON text, as `backlog_continuity_items`, `backlog_link` and `backlog_linear`
already are. `[seq N]` stamping stays for mutations (`call.finish`). No tool
takes a free-form `op` string; `Literal[...]` actions only, on tools that already
have them.

### 2.1 `backlog_context` — NEW tool

The one call that replaces "status + next_available + get_task + dependencies +
handover_list + issue_list".

```python
def backlog_context(
    focus: str = "",                    # task id; "" = session focus, else project-wide
    scope: Literal["task", "session", "project"] = "session",
    budget_bytes: int = 8000,
    include: list[str] | None = None,   # selected sections, see below
    cursor: str = "",                   # continuation for omitted selected context
) -> str: ...
```

`include` names selected sections from a fixed vocabulary — `spec`, `plan`,
`body`, `links`, `handovers`, `bugs`, `issues`, `notes`, `dependencies`,
`siblings`, `recent` — validated against that tuple, rejected otherwise. It never
governs mandatory content.

Answer (JSON):

```json
{
  "store_id": "…", "sequence": 41207, "scope": "task", "focus": "N09-3",
  "mandatory": {
    "clear": false,
    "blockers": [
      {"kind": "gate", "id": "review-gate", "state": "pending", "source": "lane:full"},
      {"kind": "dependency", "id": "N09-2", "state": "in-progress"},
      {"kind": "bug", "id": "B-118", "severity": "P1", "source": "found_in"},
      {"kind": "claim", "id": "N09-3", "state": "held", "by": "sess-7f2", "live": true}
    ],
    "gate_state": "review-gate:pending",
    "human_action": "…"
  },
  "selected": { "handovers": [...], "dependencies": [...], "links": [...] },
  "budget": {
    "limit_bytes": 8000, "used_bytes": 7614,
    "mandatory_bytes": 1182, "over_budget": false,
    "omitted": {"handovers": 4, "bugs": 0, "siblings": 11},
    "omitted_total": 15
  },
  "provenance": {
    "handovers": {"query": "memberships.task_ids", "truncated": true},
    "spec": {"path": "docs/specs/x.md", "content_hash": "…", "imported_seq": 4011}
  },
  "cursor": "eyJ…"
}
```

Invariants the tests pin:

- `mandatory` is **never** budget-trimmed. If `mandatory_bytes > limit_bytes`,
  `over_budget` is `true`, `selected` is `{}`, every `omitted` counter is filled,
  and `mandatory` is still complete (D1).
- `clear` is `true` **iff** `blockers == []` **and** every mandatory producer
  answered. If any producer could not answer (unreadable row, unresolved
  dependency id, cursor floor), `clear` is `false` and the reason appears as a
  blocker with `"kind": "unknown"`. This is the exit criterion; assert it
  directly, not via a rendered string.
- `omitted` counts are exact, not "more than N". They come from a `COUNT(*)`
  against the same predicate as the truncated list, in the same snapshot.

### 2.2 `backlog_changes_since` — NEW tool

```python
def backlog_changes_since(
    cursor: str = "",                   # "" = start from now; returns a cursor only
    kinds: list[str] | None = None,
    ids: list[str] | None = None,
    epic: str = "",
    limit: int = 100,
    group_commits: bool = True,
) -> str: ...
```

```json
{
  "store_id": "…", "sequence": 41207,
  "commits": [
    {"commit_seq": 41203, "first_seq": 41201, "final_seq": 41203,
     "operation": "task.complete", "ts": "…", "session": "sess-7f2",
     "changes": [{"kind": "task", "id": "N09-2", "op": "update",
                  "fields": ["status", "completed", "gates"]}]}
  ],
  "cursor": "eyJ…", "more": false,
  "resync_required": false, "reason": null
}
```

- `group_commits=false` flattens to a `changes` array of raw events, same order.
- `before`/`after` payloads are **not** returned by default; they are unbounded
  authored values and would defeat the byte goal. `fields` names what changed;
  the caller reads the current value with `backlog_context` or `backlog_get_task`.
- When the cursor is unanswerable, the tool does **not** raise. It returns
  `resync_required: true`, `reason` in
  `{"store_rebuilt", "history_expired", "scope_changed"}`, `commits: []`, and a
  fresh cursor at the current `sequence`, so an agent recovers in one call
  (D3).

### 2.3 Document detail — EXTENSION of `backlog_get_task`, plus a new kind-general tool

`backlog_get_task` already takes `sections` and `verbose`. Extend it with
`provenance: bool = False`; when true its section answer carries the
`path`/`content_hash`/`imported_seq`/`not_imported` block from
`documents.retrieve()` instead of the `(unresolved: …)` literal. This preserves
the tool name and its default answer byte-for-byte.

For non-task kinds add:

```python
def backlog_document(
    kind: Literal["task","epic","phase","handover","issue","bug","decision","idea","note"],
    entity_id: str,
    sections: list[str] | None = None,
    provenance: bool = False,
) -> str: ...
```

This is a thin adapter over `Snapshot.document()` — it exists today and is
wired to nothing.

### 2.4 Structured mutation — EXTENSION of `backlog_batch_update`

No new mutation tool, and no dispatcher. `backlog_batch_update` gains one
optional typed parameter:

```python
commands: list[dict] | None = None,   # [{"operation": "task.patch", "arguments": {...}}, ...]
expected_revisions: list[dict] | None = None,
atomic: bool = False,
```

- When `commands` is given, `lines` must be empty and vice versa — one refusal,
  not a merge.
- `operation` is validated by `contracts.validate_operation` against the existing
  `lifecycle.OPERATIONS` allowlist. An unknown operation is refused by name; there
  is no passthrough.
- `atomic=True` submits one native batch, all-or-nothing, with
  `expected_revisions` as preconditions — which the line form cannot express and
  which N08's pre-validation only approximates.
- `atomic=False` keeps today's per-line partial-apply contract, so
  `tests/test_batch_partial_apply.py` continues to hold unchanged.

Answer gains `receipt: {request_id, commit_seq, affected: [{kind,id,revision}]}`.

### 2.5 Claims — EXTENSION of `backlog_pick_task`, plus one new tool

`backlog_pick_task` keeps its name, its arguments and its rendered answer. It
gains `ttl_seconds: int = 0` (0 = the configured default) and its refusal text
gains the expiry fact when the holder is not live.

```python
def backlog_claim(
    action: Literal["renew", "release", "status"],
    task_id: str = "",
    ttl_seconds: int = 0,
) -> str: ...
```

Claiming stays on `backlog_pick_task` — a claim without a pick is not a state
this system has, and adding `action="claim"` would create two front doors to one
transition. `status` with no `task_id` lists this session's claims.

New core operations (`lifecycle.OPERATIONS`): `task.claim_renew`,
`task.claim_release`. Both are transactional, both refuse when the claim is held
by another live session, both are no-ops-with-a-receipt when this session already
holds/does not hold it.

```json
{"ok": true, "task_id": "N09-3", "holder": "sess-7f2", "expires_at": "2026-09-20T14:31:02Z",
 "state": "held", "live": true, "renewed_from": "2026-09-20T14:16:02Z"}
```

Conflict:

```json
{"ok": false, "error": "claim_conflict", "task_id": "N09-3",
 "holder": "sess-a19", "live": true, "expires_at": "…",
 "hint": "backlog_pick_task(\"N09-3\", force=True) steals it"}
```

### 2.6 Nothing is removed, nothing is renamed

`backlog_status`, `backlog_next_available`, `backlog_get_task`,
`backlog_dependencies`, `backlog_list_tasks`, `backlog_pick_task`,
`backlog_batch_update` all keep their names, signatures (additively extended
only) and default answers. The playbook change is about *which* call a skill
reaches for first, not about deleting tools.

## 4a. Resolutions (2026-09-20, decided with the user)

All eight are settled. The recommendation stands in every case; three were taken
to the user because they change scope or ownership, and all three were confirmed.

| # | Resolution | Decided by |
|---|---|---|
| D1 | UTF-8 bytes of the returned string. Mandatory context is always returned **complete**; on overflow `over_budget: true`, `selected: {}` and exact omission counts. It is a *selection* budget and the field names must say so. | recommendation accepted |
| D2 | Opaque cursor in the existing `_continuation` shape. Recovery ergonomics come from a separate `since_seq: int` parameter that takes its scope from the current call — never from a client-readable cursor. | recommendation accepted |
| D3 | Invalidate on store rebuild, history floor and scope-fingerprint change; **never** on a write. The client sees `resync_required: true` with a typed `reason` and a fresh cursor — not an error, and never a silent replay. | recommendation accepted |
| D4 | Define `sync_state.change_history_floor`; ship **no pruner**. Pruning `domain_events` would break the migration oracle that compares it row-for-row against the legacy `changes` table (`migrate.py:174`) and would complicate N15 reconciliation. Expiration is tested by setting the floor. | recommendation accepted |
| D5 | Structured mutation is a typed `commands=` list on `backlog_batch_update`, with `expected_revisions` and `atomic=`. No `backlog_mutate` tool: a string `operation` keyed to an internal allowlist is the dispatcher the spec forbids, however it is validated. | recommendation accepted |
| D6 | Expiry is **both** a stored `claim_expires` and `sessions` liveness, with **liveness as the authority**. TTL **4 hours**, configurable on the backlog row, `ttl_seconds` per claim. Renew is **`now + ttl`**, never `expires + ttl`. Claims are **fully visible**, and a live peer's claim is a `mandatory` blocker. Stored in **`entity_extensions`** as `claim_expires` — no schema bump, no re-backfill. | **user** (storage); recommendation accepted (semantics) |
| D7 | A **narrow, caller-initiated import** fills `external_documents`: body + `content_hash` + `imported_seq`, no watcher and no implicit import on read. `backlog_get_task` keeps its filesystem fallback and reports `provenance: {"source": "filesystem", "imported": false}` when no import exists. Staleness policy belongs to N13. | **user** |
| D8 | Mandatory context is **fixed in code** for N09 — a configurable set makes "never reported as clear" unprovable, since a project could configure a blocker out of existence. Named constant, with a test that the constant and the resolver agree. The new tools are **dual**: legacy and native both implemented, sharing the presentation and byte-bounding layer. | **user** (dual); recommendation accepted (fixed set) |

**What D6's storage choice costs, stated plainly:** `claim_expires` is operational
state living in the authored-field bag. Promoting it to a `task_operational`
column later is a deliberate migration with its own backfill test, not a silent
double-write. That cost was accepted against a staging schema 4 bump and a
re-backfill of every native store.

**What D8's dual choice buys:** every real project is still legacy and stays that
way until N15/N17, so a native-only `backlog_context` would be a milestone the
user cannot use. Dual also keeps twin parity as an oracle for the shared answer
shape, which matters more here than anywhere: N09 adds capability with no legacy
counterpart, so without a dual path there is nothing to compare against.

## 4b. What S1–S4 found that this document did not say (2026-09-20)

Recorded here because each one either extends a settled decision or corrects a
premise a later step would otherwise inherit.

- **A fourth cursor reason, `cursor_unreadable`.** D3 enumerates three reasons.
  A tampered, truncated, oversized or foreign cursor is a fourth condition, and
  neither of D3's rejected options fits it: attributing it to `store_rebuilt`
  would be a lie, and raising would force into every skill exactly the error
  branch D3 refused for a routine condition. A cursor truncated in transport is a
  routine condition. So the shipped reason set is
  `{cursor_unreadable, store_rebuilt, scope_changed, history_expired}`, pinned as
  `cursors.REASONS`, with a fixed precedence (unreadable, then rebuilt, then
  scope, then floor) so the answer names the most fundamental cause.

- **`epic` scope is membership *at the time of the event*, not current
  membership.** D3 says `filtered_removal` "is a scope change, and the
  fingerprint catches it." The fingerprint catches a caller *re-scoping*; it
  cannot catch an entity *leaving* a scope whose parameters never changed. Scoped
  by current membership alone, the one change an epic watcher most needs — the
  move that took a task out — would be the one change never reported. Both paths
  therefore also match an event whose own `before`/`after` names the scoped epic,
  and `epic` scope includes the epic row itself. Pinned by
  `test_an_epic_scope_reports_the_epic_row_its_tasks_and_a_task_leaving_it`.

- **Only `task.viewer_update` can reassign a task's epic.** `epic` is not in
  `domain.ALLOWED_FIELDS`, so neither `task.update` nor `task.patch` can move a
  task between epics; the viewer's whole-document patch is the sole path
  (`workflow.py::_task_viewer_update`). Anything in S5–S15 that assumes an epic
  move is an ordinary field update is wrong.

- **`since_seq` is `int | None`, not `int`.** D2's escape hatch needs `0` to mean
  "all history", so absence cannot also be spelled `0`. `None` is "start from
  now"; passing both a cursor and `since_seq` is refused rather than merged.

- **S3 needed no `native/schema.py` change at all.** `sync_state` is a kv table,
  as §3 expected, and the floor key constant lives in `native/cursors.py` beside
  the contract it serves. An *unreadable* floor refuses the call rather than
  defaulting to zero: a floor that cannot be read cannot prove history is
  retained, and the failure mode of guessing is a replay.

- **The legacy change log has no commit rows, so the legacy path reports one
  commit per change** (`first_seq == final_seq == commit_seq`, `operation` = the
  tool). `store.py::_record_change` timestamps each row separately, so grouping a
  legacy transaction by `(ts, session, tool)` would be a guess, not a fact. Twin
  parity is therefore asserted on the flat event stream — `(kind, id, op,
  fields)` — which does match row for row; commit grouping is a native capability
  with no legacy counterpart, exactly as §5.1 predicted.

- **A legacy store's cursor fence is `(creation_token, "legacy")`.** A legacy
  project and its native copy share `creation_token` (`assert_native` requires
  it), so the digest is the only thing keeping a cursor from crossing between
  them; `cursors.LEGACY_DIGEST` is that stand-in, and the crossing is tested.

## 4c. What S7–S9 found that this document did not say (2026-09-20)

The context steps, recorded the same way S1–S4 recorded theirs: each item either
extends a settled decision or corrects a premise a later step would inherit.

- **There is no honest `clear` without a task in focus.** §2.1 shows only a
  task-scoped example and never says what `mandatory` means at session or project
  scope. `clear` is a safety claim, and with no focus *no* producer ran, so a
  focus-less answer carries an `unknown` blocker `focus` with reason
  `no_focus_task` rather than an empty blocker list. Pinned on both stores.

- **The continuation is not free, and its cost had to be reserved before the rows
  were chosen.** D1 requires `used_bytes` to be the bytes actually returned and D2
  requires an opaque cursor — but the cursor lives inside the answer it is
  measured against. So `context.assemble` budgets once against the *widest* cursor
  the page could issue (every section resumed at its own total), then re-renders
  the rows that pass chose with the real, never-longer cursor in place. The fence
  is also a single 128-bit digest rather than the cleartext identity tuple
  `queries._continuation` uses: a context cursor is spent out of the caller's own
  byte budget, and the cleartext form cost ~240 bytes — enough to leave a modest
  budget with no room for a single row. Measured, not assumed: the first
  implementation returned zero rows at an 800-byte limit.

- **A page that delivered nothing must not issue a cursor.** It would name the
  same offsets again and the caller would loop on one answer forever. The same
  page, released from the cursor reserve, is re-tried once — if the whole
  selection then fits, no continuation was ever needed.

- **`over_budget` and "nothing selected" are different facts.** D1 states them
  together. They come apart when the blockers fit but leave no room for even one
  row. `over_budget` keeps its one meaning — the mandatory half alone does not fit
  — and the omission counts carry the other case.

- **`include` needed a default per scope, which §2.1 does not give.** Task scope
  defaults to dependencies, handovers, bugs, links and body; session scope swaps
  links and body for notes and recent; project scope drops the task-shaped
  sections entirely. An explicit empty list stays legitimate: blockers alone.

- **The section vocabulary splits three ways.** `spec`, `plan`, `body`, `links`,
  `dependencies` and `siblings` describe one task and are empty (total 0,
  provenance `no_focus`) without one — answering a different question is worse
  than answering none. `handovers` and `bugs` narrow to the focus when there is
  one and widen to the project when there is not. `issues`, `notes` and `recent`
  are always project-wide. `recent` is inherently a top-N question, so its total
  is the cap (20) and not the entity count: "15 of the 20 most recent were
  omitted" is a number a caller can act on, "of 3,412 entities" is not.

- **A handover must be narrowed to `next_action` in the query, not after the
  page.** A task with many silent handovers and one that asks for an action would
  otherwise have the asking one paged out of its own blocker list — the exit
  criterion failing through a paging limit rather than through a producer.

- **A claim holder with no `sessions` row is not live.** §1.3 defines expiry by
  liveness but not what an absent row means. Every session registers, so absence
  is evidence of absence and such a claim does not block; only an *unreadable*
  `sessions` table is unknown, and that blocks. S12/S13 own the claim surface;
  context only reads it, and `context.session_live` is the predicate S13 should
  collapse onto rather than write a second one.

- **A legacy task is not in `_rows`.** `_dict_row(data, "task", id)` is empty on a
  v3 legacy store: tasks live inside their epic in `backlog.yaml`, and a task
  document need not carry an `epic` key at all. The legacy path reads through
  `_find_task` and carries the containing epic alongside the document, or
  `siblings` — and any document comparison against the native side — diverges on
  an absence rather than on a difference.

- **A context cursor is refused, never resynced.** D3's resync contract belongs to
  the change feed. There is no safe "start from now" for a half-read page:
  silently restarting it would hand the caller the first rows again as if they
  were new. So it raises `CursorInvalid` — now the one continuation refusal both
  paged reads share — and the tool answers a JSON refusal.

- **D8's dual requirement forced a shared pure module the step table does not
  name.** §3 lists only `queries.py` and `backlog_server.py` for S7–S9. One
  presentation over two data paths needs a home, and `native/context.py` is it, in
  exactly the role `native/cursors.py` already plays for the change feed.

**Left for later, deliberately.** §3's S5 row promised to collapse the three
divergent dependency treatments at their call sites; the resolver exists and
`backlog_context` is its only caller, while `_derive_context`, `pick_task` and
`next_available` still compute blocking themselves. `native_routing/tasks.py::
_open_handovers` likewise remains a second reader of the open-handover question
next to `Snapshot.open_handovers` — left alone because S12/S13 also edit that
file. And `budget.budget` re-renders the whole answer once per candidate row,
which `assemble` runs up to three times: correct and bounded, not yet measured.

## 4c′. What S12–S13 found that this document did not say (2026-09-20)

Each one either extends a settled decision or corrects a premise the claim
surface would otherwise have inherited.

- **There is no session-liveness computation to reuse — there are three copies,
  and none of them is usable as-is.** §1.3 says the signal "already exists" and
  points at `overview.py:120-130`. It exists as inline SQL-plus-predicate in
  three places (`store.py:3510-3520`, `store.py:3675-3690`,
  `native_routing/overview.py:120-130`), with no shared function. S12 wrote the
  first named one, `native/claims.py::liveness`, and left the three shipped
  copies alone: they feed `store_status`'s rendered output, and rewriting that
  is not this step's scope.

- **Liveness had to become three-valued.** D6(i) reads "expired when its holder
  is not live **or** its stored expiry has passed", and `store_status`'s rule
  reports "not live" for anything it cannot confirm — including a heartbeat
  older than sixty seconds. Taken literally, every session that had not called a
  tool in the last minute would lose its claims, and the four-hour TTL would mean
  nothing. So only *proven* death expires a claim early: a `sessions` row naming
  this host with a pid that is gone. A holder on another machine, or one this
  store has never heard from, is `None` — unknown — and an unknown holder keeps
  its claim until the TTL passes. A migrated `locked_by` with no expiry at all is
  therefore unstealable except by `force`, which is exactly today's behaviour.

- **The native core may not import `socket`.** `test_the_native_core_never_imports_a_remote_client`
  bans it across `taskmaster/native/`, which the obvious liveness check trips on
  its first line. `store._local_host()` was added beside `_local_pid_alive` and
  both are fetched lazily, so the module that writes a `sessions` row is also the
  one that says what "this machine" means.

- **A pick does not take an expired claim.** The document is silent on this and
  §2.5's `hint` implies `force` is the only path. Kept: expiry makes the refusal
  *informed* rather than making the pick a silent steal, because a pick hands out
  worktree instructions a second agent would act on. What expiry buys instead is
  `backlog_claim(action="release")`, which frees a **proven-expired** claim
  without stealing — so reclaiming a dead holder's task costs release-then-pick,
  and `force` stays for a claim that still stands. Renew is never permitted for a
  peer's claim, expired or not: renewing someone else's lease is a steal wearing
  a smaller word.

- **`claim_expires` is never cleared except on release, and does not need to
  be.** D6 chose `entity_extensions` but not what keeps the field honest. Twelve
  shipped sites drop `locked_by` (complete, archive, status change, batch lines,
  viewer writes) across both stores, and keeping an expiry in step with all of
  them would be a wide edit with a silent failure mode. The contract answers it
  instead: **the holder is `locked_by`, and `claim_expires` is only ever read
  beside it**, so an expiry with no holder is inert, not a claim. Nothing else
  had to change, and the two stores agree by doing nothing.

- **`blockers.Claim` needed a third field.** S5 shipped `live: bool | None` and
  reads `live=None` as an `unknown` blocker. But a claim whose holder cannot be
  judged is still determinately *held and unexpired*, and reporting a known fact
  as an unanswered producer misattributes it. `Claim.expired: bool | None` was
  added; `None` preserves S5's reading exactly, so every S5 test stands unchanged
  and only a producer that has actually decided expiry sets it.

- **`backlog_claim` is not an action router.** §2.5 shapes it like
  `backlog_link`, but `scripts/native_contract_inventory.py` reserves that
  category for tools whose legacy body dispatches to per-action functions.
  `backlog_claim` has one body, so it is a `simple-command` routed as
  `(tool, None)`; routing it per action makes the bypass gate's routed-pair
  ledger disagree with the contract inventory.

- **The claim error vocabulary is wider than §2.5's one example.** Shipped:
  `claim_conflict`, `not_claimed`, `not_found`, `task_required`, `invalid_ttl`,
  `unknown_action`, `claim_refused`. A bundle's answer also carries `members`,
  because a bundle is picked as a unit and so is renewed and released as one.

- **`locked_by` and the `sessions` table are keyed by two different session
  identities, so §1.3's central reuse claim does not hold as written.**
  `locked_by` records `backlog_server.SESSION_ID`; the `sessions` table is keyed
  by `store.Store.session`. Both are `{host}-{pid}-{uuid4[:8]}`, built by the
  same expression in two places and **generated independently**, so they never
  match — and `backlog_server` never passes `session=` to `open_store`. A
  liveness check that looks the holder up in `sessions` therefore finds nothing
  on every real project, and the dead-process fast path D6 calls "the
  authority" would have shipped dead: claims would have been governed by the
  TTL alone. Found by probing a twins pair rather than by reading, because the
  unit tests insert the `sessions` rows they then read. The fix is to read the
  holder id itself — it already carries the machine and the pid — and to keep
  the `sessions` lookup as the only signal available for a remote holder.
  Separately, and confirmed by the same probe: a native-routed call writes **no**
  `sessions` row at all, because every write to that table goes through
  `store.Store`, which the bypass gate forbids a native adapter from opening.

- **The viewer boundary (§5.3) is still open.** Nothing in S12–S13 touched the
  viewer, so it renders `locked_by` with no expiry predicate and can show a claim
  that `backlog_claim` considers expired. That contradiction is real and is left
  for N10, as §5.3 anticipated.

## 4. The open decisions

Eight. Each one would send the implementation somewhere materially different.

---

### D1 — What is the byte budget measured in, and what happens when mandatory context alone exceeds it?

**Options.** (a) UTF-8 bytes of the returned string. (b) An estimated token
count. (c) Bytes of the canonical JSON before rendering.

**Tradeoff.** Tokens are what the agent actually pays, but the estimate is
model-specific and would make the same store answer differently across model
versions — untestable and unpinnable. Canonical-JSON bytes are stable but are not
what the transport carries, so the number would systematically understate the
real cost. UTF-8 bytes of the answer are exactly what crosses the wire,
deterministic, and trivially asserted.

**On overflow:** (a) truncate mandatory anyway; (b) return mandatory complete and
over budget; (c) refuse the call.

**Recommendation: (a) UTF-8 answer bytes, and (b) on overflow.** Truncating
mandatory content violates the milestone's own exit criterion — a trimmed blocker
list is indistinguishable from a clear one at the point of use. Refusing is worse:
it leaves the agent with no way to learn *why* it is over budget. Return mandatory
in full, set `over_budget: true`, drop all selected context, and report
`mandatory_bytes` so the caller can raise the budget deliberately. The budget is
a *selection* budget, and the answer should say so in the field names.

---

### D2 — Is the continuation token opaque or structured?

**Options.** (a) Opaque: base64 of canonical JSON, contents undocumented,
validated server-side. (b) Structured: a documented `{seq, scope}` object the
client may construct. (c) A bare integer seq.

**Tradeoff.** A structured or bare-integer cursor lets an agent resume without
having stored one — genuinely useful for a coding agent that lost its context —
but it also lets a client fabricate a cursor whose scope does not match the
query, which is precisely the "filtered removal" failure the spec asks us to
test: resume a narrowed scope with a wider cursor and entities that left the
scope are silently never reported.

**Recommendation: (a) opaque, in the existing `_continuation` shape** — base64url
of canonical JSON with an `identity` tuple, `len <= 4096`, exactly as
`queries.py:158-176` already does. Then add a documented escape hatch that is
*not* a cursor: `backlog_changes_since(cursor="")` starts from now, and a
separate `since_seq: int = 0` parameter starts from an explicit sequence with the
scope taken from the current call. That gives the recovery ergonomics without
letting a mismatched scope masquerade as a valid continuation.

---

### D3 — What invalidates a cursor, and what does the client see?

**Must invalidate.** Store rebuild (`store_id` or `source_digest` changed);
history expired (cursor seq below the retention floor); scope changed (the
fingerprint of `kinds`/`ids`/`epic`/`group_commits` differs).

**Must NOT invalidate.** A write. The existing list cursor binds to
`event_high_water` (`queries.py:165`) so that a paged snapshot read stays
coherent; a change cursor that did the same would be invalid on every call in an
active project.

**Options for the answer.** (a) Raise — the tool returns `Error: …`.
(b) Return a normal answer with `resync_required: true`, a typed `reason` and a
fresh cursor. (c) Silently restart from the beginning of history.

**Recommendation: (b).** (c) is the dangerous one — an agent that silently gets a
full replay cannot tell a quiet period from a lost cursor, and on a rebuilt store
would re-apply history it already acted on. (a) forces an error-handling branch
into every skill for a routine, expected condition. (b) recovers in one call and
is directly assertable. The typed reasons are `store_rebuilt`,
`history_expired`, `scope_changed`; `filtered_removal` is **not** a reason —
it is a scope change, and the fingerprint catches it.

One consequence worth stating: with (b), an agent that re-scopes its query loses
the guarantee that it saw every change in the *new* scope since its old cursor.
`resync_required` is the honest signal for that, and the skills must say
"re-read, do not assume quiet."

---

### D4 — Does N09 ship a history pruner?

**Options.** (a) Define the floor contract, ship no pruner. (b) Ship a pruner
with a retention window. (c) Neither — no floor at all.

**Tradeoff.** (c) makes the spec's history-expiration cursor test untestable
except by hand-deleting rows, which would then be testing nothing real. (b) is
real work with a real hazard: `domain_events` is the only native record of what
happened, the compatibility oracle compares it row-for-row against the legacy
`changes` table (`migrate.py:174-176`), and pruning it would break that oracle
and, at cutover, any reconciliation N15 wants to do.

**Recommendation: (a).** Introduce `sync_state.change_history_floor` (an integer,
default 0), have `changes_since` honour it, and test expiration by setting it —
which is exactly what a future pruner would do. No rows are deleted in N09.
File the pruner as a follow-up for N16's scale work, where there will be evidence
about how large the table actually gets.

---

### D5 — What shape is the "structured mutation interface"?

**Options.** (a) Extend `backlog_batch_update` with a typed `commands=` list.
(b) A new `backlog_mutate(operation, arguments, expected_revisions)` tool.
(c) Per-operation tools (`backlog_task_patch`, …).

**Tradeoff.** (b) reads closest to the native core but is one `Literal`-widening
away from being the untyped all-purpose dispatcher the spec explicitly forbids —
and its `operation` parameter would be a string keyed to an internal allowlist,
which is the dispatcher smell regardless of how it is validated. (c) is the most
typed and the most honest, and also the largest surface-area addition to an
already 83-tool server, for operations that overwhelmingly already have tools.
(a) adds nothing new to the tool list, reuses the validation and receipts that
already exist, and puts multi-entity atomicity where a caller already looks for
multi-entity work.

**Recommendation: (a).** The genuinely missing capability is not "call an
operation by name" — every operation already has a tool — it is *several
mutations in one atomic transaction with revision preconditions*. That belongs on
the batch tool. If a specific unexposed operation turns out to be needed, add a
typed tool for it, not a dispatcher.

---

### D6 — Claim expiry: TTL length, renew semantics, dead holders, visibility

Four sub-decisions; they interact, so decide them together.

**(i) What expires a claim.** Options: a stored `claim_expires` timestamp;
`sessions` liveness; both.

*Recommendation: **both, with liveness as the authority.*** A claim is expired
when its holder is not live by the rule `overview.py:120-130` already applies
(`last_seen` within the window, or a live local pid on this host) **or** its
stored expiry has passed. Liveness alone cannot see a session on another machine
that stopped heartbeating; a timestamp alone cannot see a crashed local process
until the TTL burns down. Neither is sufficient, and the code for both exists.

**(ii) TTL length.** Options: 30 min, 4 h, session-lifetime (no timestamp).

*Recommendation: **4 hours, configurable on the backlog row, with
`ttl_seconds` per claim.*** This system's unit of work is a task worked across a
long Claude session, not a job in a queue. A 30-minute TTL would expire claims
mid-review-gate and turn renew into a heartbeat the agent must remember — exactly
the kind of bookkeeping N09 is supposed to remove. Four hours with liveness doing
the fast path gives quick reclaim of dead processes and a long safety margin for
a live one.

**(iii) Renew extends or replaces.** Options: extends from now (`now + ttl`);
extends from current expiry (`expires + ttl`); replaces with an absolute time.

*Recommendation: **`now + ttl`.*** Extending from the current expiry lets a
chatty agent push a claim arbitrarily far into the future, which makes the TTL
meaningless. `now + ttl` is the standard lease renewal and is what a reader of
`expires_at` will assume.

**(iv) Visibility to other agents.** Options: claims private to the holder; fully
visible; visible as state without the holder's identity.

*Recommendation: **fully visible.*** `locked_by` is already visible — it renders
in `_derive_context`'s `in_progress` entries (`backlog_server.py:1616-1617`), in
`backlog_status` and in the viewer. Hiding the new expiry while showing the old
holder would be strictly worse. A claim must appear in
`backlog_context.mandatory.blockers` with `by` and `live`, because a task claimed
by a live peer is exactly the kind of mandatory fact that must never be reported
as clear.

**Storage.** `locked_by` is a `task_operational` column; the expiry needs a home.
Options: a new `task_operational` column (staging schema 4 + re-backfill + an
ownership move in the compatibility inventory); `entity_extensions` (no DDL,
wildcard ownership already sanctioned by the N02 inventory); `sessions`-side
state (local-only, not projected).

*Recommendation: **`entity_extensions`,*** as `claim_expires`. It needs no schema
version bump, no re-backfill of every native store, and the N02 inventory already
designates extensions as the home for authored fields not yet promoted. The cost
is honest and stated: it is operational state living in the authored-field bag,
and promoting it to a column later is a deliberate migration, not a silent
double-write. **If the user prefers correctness of ownership over migration
cost, the alternative is schema 4 — say so now, because it changes S12 from a
one-commit step into a schema-migration step with its own backfill test.**

---

### D7 — What fills `external_documents`?

Nothing does today. `documents.retrieve()` reports `not_imported` for every
doc-backed section, while the routed `backlog_get_task` still reads those files
off disk.

**Options.** (a) Ship an import command in N09 (`document.import`, hashing the
file into `external_documents`). (b) Keep the filesystem read and only add
provenance around it. (c) Ship the retriever as-is, so doc-backed sections answer
`not_imported` until a later milestone imports them.

**Tradeoff.** (b) keeps the bypass gate's "no projection scan" spirit but has the
native store reading project files at read time — the very coupling the native
rewrite is removing. (c) is honest but is a visible capability regression for
`backlog_get_task(sections=["spec"])`, which today returns the spec's text.
(a) is the right end state and is real work: import triggers, staleness when the
file changes on disk, and an interaction with N13's explicit sync.

**Recommendation: (a), scoped narrowly** — an explicit, caller-initiated import
only (no watcher, no implicit import on read), storing body + `content_hash` +
`imported_seq`, with `backlog_get_task` falling back to the filesystem read and
reporting `provenance: {"source": "filesystem", "imported": false}` when no
import exists. That keeps today's answer intact, makes the provenance honest, and
leaves staleness policy to N13 rather than inventing a second one here.

---

### D8 — Is "mandatory context" a fixed set, and do the new tools work on legacy stores?

Two questions that resolve together, because both are about how much of N09 is
native-only.

**(i) Fixed or configurable mandatory set.** Options: fixed in code;
project-configurable via the backlog/project row; fixed with a project-level
*additive* extension point.

*Recommendation: **fixed in code for N09.*** The exit criterion is "missing
mandatory context is never reported as clear." A configurable set means a
project can configure a blocker out of existence, and then `clear: true` is
true-for-that-config but false in fact — the criterion becomes unprovable in
general. The set is already well-defined by existing pure functions (§1.4):
blocking gates for the lane, unmet dependencies, open P0/P1 bugs whose `found_in`
names the task, open handovers with a `next_action`, `human_action`, and a live
peer's claim. Make it a named constant with a test that the constant and the
resolver agree, and revisit configurability once there is evidence a project
needs it.

**(ii) Legacy-store support for the new tools.** Options: native-only (new tools
refuse on a legacy store); dual implementation; native-only with the legacy path
deferred to N15.

*Recommendation: **dual.*** Today **every real project is legacy** — activation
is test-only and stays gated until N15/N17. A native-only `backlog_context` is
dead code the user cannot use until cutover, which forfeits the entire point of
the milestone ("the first one the user will actually feel") and, worse, forfeits
the twin-parity oracle for the shared answer shape. The dual cost is lower than it
looks: N08 established the pattern of pure presentation helpers over two data
paths, `changes_since` has an exact legacy equivalent in the `changes` table, and
claims have `locked_by` + `sessions` on both sides. The legacy path will be slow —
it loads the whole backlog, as it already does — but it will be *correct*, and
byte-bounding is presentation, which is shared. **Flag:** this is the decision
with the largest effect on step count; native-only would cut S9 and roughly a
third of S4/S13, at the price of shipping a milestone the user cannot use.

## 5. Risks, and what the proof method can and cannot prove

### 5.1 Twin parity does not apply to the new surface

`tests/native_twins.py` proves a native answer equals the legacy answer for the
same call. N09 adds capability that has no legacy counterpart, so there is
nothing to be equal to. Twin parity still covers:

- the **unchanged** default answers of every extended tool (`backlog_get_task`
  without `provenance`, `backlog_batch_update` with `lines`, `backlog_pick_task`
  without `ttl_seconds`) — this is the regression fence and it must stay green;
- under D8's dual recommendation, the *shared shape* of `mandatory` and of the
  change feed on both stores.

It cannot prove that the new contracts are right.

### 5.2 What replaces it as the correctness gate

Four things, in descending strength:

1. **Invariant assertions on the mandatory set.** For a generated population of
   tasks (random lanes, gate records, dependency graphs, bugs, handovers,
   claims), assert: `clear == true` ⟹ the independently-computed blocker list is
   empty. Computed twice by different code — the resolver, and a naive oracle
   that walks the documents — with the two compared. This is the only direct
   proof of the milestone's stated exit criterion, and it is the gate.
2. **Cursor property tests.** Generate an interleaving of writes and
   `changes_since` calls and assert *no lost change*: the union of every reported
   change across a cursor chain equals the set of events in `(start, end]`, with
   no duplicates across commit boundaries. Then the five named cases explicitly —
   store rebuild, floor expiration, scope change, filtered removal, multi-entity
   grouping.
3. **Claim concurrency test.** Two connections, one task, real `BEGIN IMMEDIATE`
   contention: exactly one claims, the loser gets `claim_conflict` and the
   database shows one holder. Plus an expiry test on the fake clock and a
   dead-pid test with a fabricated `sessions` row.
4. **Journey measurement.** Before/after on the CodeMaestro copy for three
   journeys — start-session orientation, pick-a-task, pre-completion review —
   recording calls, entities read, bodies read and answer bytes. This is an
   *improvement* measurement, not a correctness gate, and the report must say so.
   The "same required context" half of the exit is proven by (1), not by this.

### 5.3 Risks specific to N09

- **The dependency-treatment collapse (S5) touches shipped behaviour.** The three
  current sites disagree about a missing dependency id: `pick_task` treats it as
  `todo` and therefore unmet, `next_available` does the same, `_derive_context`
  also does — but `backlog_dependencies` renders it as `[missing] NOT FOUND` and
  sets `all_met=False`. Unifying them is correct and is a behaviour change
  somewhere. Find the disagreement with a test before writing the resolver, and
  record it as an intentional difference the way N07 recorded its nine.
- **Budget accounting and rendering can drift.** If `used_bytes` is computed over
  a structure that is then rendered differently, the number is a lie. Compute the
  budget over the exact bytes returned — assemble, encode, measure, and if over,
  drop and re-encode — and assert `len(answer.encode()) == used_bytes` in a test.
- **`clear: true` is a safety claim.** Any producer that can fail silently — an
  unresolvable id, a malformed `gates` record, a `found_in` shape N08 already had
  to fix once — must degrade to a blocker, never to absence. Test each producer's
  failure mode individually; a single end-to-end happy path proves nothing here.
- **Claim visibility changes the viewer.** `locked_by` renders today; adding
  expiry means the viewer can show a claim that is expired-but-present. Either
  the viewer's read applies the same expiry predicate or it will contradict
  `backlog_context`. Decide in S13; it is a N10 boundary and must not be left
  implicit.
- **`changes_since` scan cost.** §1.2 caveat 1: scoped queries have no covering
  index. Measure on the CodeMaestro copy before deciding whether an index is
  needed; if it is, it is a staging schema change and inherits D6's migration
  cost.
- **The bypass gate must extend to the new paths.** S10 removes a filesystem read
  from the native `get_task` sections path; the gate test must be extended to
  cover the new adapters, or N09 quietly reintroduces the coupling N08 closed.
- **Scope pressure.** Fifteen steps across five independent capabilities is a
  large milestone. If it has to be cut, cut D7's importer (S11) and the structured
  mutation form (S14) — both are additive and neither is load-bearing for the exit
  criterion. Do not cut S5 or the invariant test in §5.2(1).

## 4d. Integration debt carried out of the parallel tracks (2026-09-20)

Recorded at integration, when the four finished tracks and the context track were
merged onto `feat/database-native-foundation`. Each item is real work that the
milestone's own step table implied and that no track owned, so none of it is
closed by S15 writing the report. None of it is a test failure: the merged tip
ran **3,088 passed / 1 skipped / 0 failed** before the context merge.

- **S5's promised call-site collapse did not happen.** The S5 row says the one
  mandatory-blocker resolver would take over its callers in
  `native_routing/tasks.py` and `backlog_server.py::_derive_context`. It did not:
  `backlog_context` is the resolver's only caller, and `_derive_context`,
  `pick_task` and `next_available` still each decide dependency blocking their
  own way. These are exactly the three divergent treatments §5.3 warns about, so
  the milestone currently *adds* a fourth reading rather than collapsing three.
  Deferred during the tracks because the owning files were in flight; it is now
  an integration task with nothing blocking it.

- **`native_routing/tasks.py::_open_handovers` is a second reader** of the
  open-handover question beside `Snapshot.open_handovers`. Same shape as the
  above, same fix window.

- **The legacy `recent` section reads outside the `_load()` snapshot,** so a
  concurrent write can leave that one section inconsistent with the rest of the
  answer it appears in. Native path unaffected.

- **`budget.budget` is quadratic in rows delivered.** Each candidate row rebuilds
  the trial answer and `_stabilise` encodes the whole answer about twice, giving
  Σₖ O(k·b) ≈ O(R²·b); `assemble` runs the loop up to three times (widest-cursor
  pass, no-continuation retry, final render). `PAGE = 50` bounds R at 11 × 50 =
  550, so the bound is finite but poor: at the default `budget_bytes=8000` it is
  ~1,100 encodes of an ≤8 KB answer and invisible, while at `MAX_BUDGET` (1 MiB)
  with prose-heavy sections it encodes on the order of a gigabyte, because answer
  size and rows delivered both scale with the budget. The fix is structural and
  cheap — size each row once, accumulate a prefix sum, render once at the end to
  settle `used_bytes` — but it rewrites S6's landed selection loop and disturbs
  the one invariant (`used_bytes` equals the bytes actually returned) that is
  least safe to disturb mid-milestone. **Decision: state it in the N09 report as
  a known characteristic, fix it in N16** with a measurement, rather than let a
  benchmark discover it. This is the headline new tool of a rearchitecture sold
  on performance; it does not get to be an unwritten surprise.

- **Fixed at integration: the context and claims tracks disagreed about claim
  liveness, and together they reported a held task as clear.** S7–S9 judged a
  holder live only if it had a recent `sessions` row. S12–S13 then established
  that `locked_by` and the `sessions` key are minted independently and never
  match. Each track passed its own tests; merged, `backlog_context` reported a
  task held by a live peer agent as `clear: true` on both stores. That is the
  one answer the milestone says must never be wrong. Fixed test-first
  (`b0792ce`, `55b2fc9`): both context producers now read the claim through
  `claims.read(...).as_blocker()`, and the second liveness rule
  (`context.session_live`) is deleted so it cannot be reused. One query test
  had pinned the superseded rule ("no sessions row does not block"); it now
  pins the settled one: a holder that cannot be judged keeps its claim until
  the TTL expires.

- **Fixed after adversarial review (review A, 2026-09-21), each test-first on
  both stores.**
  - *Context cursors re-delivered finished sections and could loop forever.*
    The cursor named only sections with rows left, so the next page read every
    finished section from offset 0 again; when that filled the page, the page
    returned the cursor it was given. The cursor now names every section with
    rows, finished ones at their total, and `omitted` and `truncated` are
    counted from the page's own offset and from what the budget took. Pinned as
    properties over many budgets and multi-section includes
    (`test_native_routing_context_paging.py`), not as one example.
  - *§4c′'s "`claim_expires` is only ever read beside `locked_by`, so nothing
    has to chase the writers" was wrong.* Reading beside the holder is not the
    same as belonging to it: a paused claim leaves its expiry behind, and a
    later holder set by any non-claim writer read it as its own — a live claim
    reported expired, context reported the task clear, and any peer could
    release it without `force`. Each stamp now records its holder in
    `claim_expires_for` and `claims.read` ignores an expiry stamped for anyone
    else, so no writer needs to know about expiry and the next one added cannot
    reintroduce this. A holder with no expiry of its own is judged on liveness
    alone. Residual: a non-claim writer re-setting the *same* session that
    stamped a burnt expiry reads that expiry again; that session can renew, and
    no peer ever inherits another holder's expiry.
  - *A bundle renew re-claimed members whose holder had been dropped* — a claim
    without a pick. Renew now extends only members this session holds.
  - *A non-string `human_action` raised out of `backlog_context`.* It is now an
    `unknown` blocker, like every other malformed field.
  - *§5.2(1)'s invariant gate now exists*
    (`test_native_routing_context_invariant.py`): seeded populations over every
    blocker dimension, claims produced through the real tools on a controlled
    clock, compared per task and per producer against an oracle written from
    this document, plus legacy == native. It failed on the expiry and
    `human_action` defects before they were fixed.

## 4e. What adversarial review B found, and what was decided (2026-09-21)

Six findings against the change feed, the importer and `commands=`, each fixed
test-first on `feat/native-n09-review-b-fixes`.

- **`commands=` let a caller speak for another session.** The claim operations
  take `session` as an argument, and the structured form takes every argument
  from its caller. **Decision: `task.pick`, `task.claim_renew` and
  `task.claim_release` are internal to `commands=`**, refused by name with the
  tool that supplies this server's own session (`backlog_pick_task`,
  `backlog_claim`). Injecting the session instead was rejected: §2.5 already
  says a second front door to one transition is how they diverge, a pick's
  answer (worktree instructions, bundle members) has no place in a receipt, and
  no use case needs a claim inside an atomic batch. The sweep of every other
  operation `commands=` exposes found three more ways to supply what a tool
  takes from the call, now **reserved arguments**: `note.create` `author` (the
  tool always authors `claude`; a batch could author as the user),
  `task.merge` `merge_targets` (the ladder decides whether the merge gate is
  satisfied; the adapter now resolves it from the manifest as
  `backlog_record_merge` does, where before a batch judged it against none),
  and `task.update` of `locked_by` (names any holder). Left as they are because
  the tool itself takes the same value from its caller, so `commands=` adds no
  power: `task.gate_skip` `by`, `phase.advance` `force`, `bug`/`issue`
  `discovered_by`, `idea` `created_by`, `decision` `raised_in`, gate and spec
  review verdicts and `codex_used`, `linear.link` `workspace_alias`,
  `project.set`. **Still open, outside `commands=`:** `backlog_update_task`
  and the batch line form both accept `field=locked_by`, and any status change
  drops `locked_by` — each can move a peer's claim on both stores, exactly as
  legacy always has. Closing that changes the legacy tool contract and needs a
  decision.
- **`commands=` could store any text as an imported document.**
  `document.import` is internal to `commands=`; only the importer, which reads
  the declared file, supplies a body.
- **Epic scope was current membership plus the event's own `before`/`after`**,
  which §4b claimed was "membership at the time of the event" but is not: a
  change made inside the epic vanished once the task left, and a change made
  elsewhere appeared once it joined. **Decision: derive the epic at each event
  from the event stream's own history** — the `after.epic` of the task's latest
  earlier event that set one, else the `before.epic` of its next move, else its
  current epic — in one predicate, `cursors.epic_condition`, that both stores
  apply to their own table. Recording the epic at write time was rejected: the
  migration oracle compares `domain_events` with the legacy `changes` table row
  for row, and every existing row would need a backfill that changes what it
  says. The fallback to current membership only matters for a task whose
  history predates the log.
- **The importer read any path** — absolute, `../`, or through a link — and
  crashed on a directory. It now resolves the path (symlinks and junctions
  included) and refuses anything outside the project root; a directory,
  undecodable text or an unreadable file is an `Error:` naming the section.
  The *read* fallback (`read_doc_section`, legacy and native) still reads any
  declared path, as it always has; it copies nothing into the store.
- **A partial import hid what committed.** Each section is its own commit, so
  the importer now reports every section's outcome, leads with `Error:` when
  any failed, and names the size and the 1 MiB limit for an oversized document.
- **A floor above the high-water mark looped on resync**, and **a cursor past
  the end of a restored store's history silently skipped the gap.** Cursors
  that start from now or recover are issued at `max(sequence, floor)`, and a
  cursor ahead of that answers resync with a fifth reason,
  **`history_rewound`**. The pinned set is now `{cursor_unreadable,
  store_rebuilt, history_rewound, scope_changed, history_expired}`, in that
  precedence: a store that went backwards is more fundamental than a re-scoped
  question. The fence sees a rewind only while the store is still behind the
  cursor: on legacy, the next read adopts files the restore left on disk as
  fresh imports, which can re-occupy the lost sequences with different events.

- **Resolved with the user (2026-09-21): close the `locked_by` gap in N09.** Only
  the claim tools may set or clear `locked_by`; `backlog_update_task
  field=locked_by` and the batch line form refuse it, and a status change no
  longer drops a live claim held by another session. This changes the legacy tool
  contract on both stores.

flight.** A transition to a terminal status always releases `locked_by`, whoever
makes it; a non-terminal one keeps a live peer's claim. `claims.read` reads a
claim on a `done` or `archived` task as expired (`claims.TERMINAL_STATUSES`), so
the terminal release, `backlog_claim(action="release")` on a stranded claim and
`backlog_context` all follow from one predicate.

The native core `task.update` keeps its `locked_by` branch for its own callers —
the tools refuse the field and `commands=` already reserves it — and judges
"peer" by the command's `caller_scope`. Test seeds that used the bare write to
fake a claim now take it the way a tool does (a pick as that session) or, for a
holder no pick stamped, hand-edit the legacy row before the twins are copied
(`native_twins.hand_set_holder`).
