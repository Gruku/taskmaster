## Goal and fixed contract

Implement design section 7 and N13, including N11's deferred file-side conflict
resolution, handover/issue resync and Linear configuration bootstrap. SQLite
remains the single runtime authority at the repository's main checkout. Explicit
sync imports external edits or reports why it cannot; it never treats absence
as a domain deletion. Managed Git stages/commits one consistent projection
generation. Unmanaged operations remain detectable, not magically coordinated.

## Implementation sequence

1. Extract the existing pure projection parsing/identity helpers without opening
   a legacy Store. Preserve v4 task prose parsing, unknown fields, epic/phase
   split ownership, archive paths and first-canonical-path selection. Backlog
   imports must not replace derived indexes or erase heavy fields owned by their
   entity documents. Discover only known projection patterns; never local DB,
   token, lock or coordinator files. Reject links/out-of-root paths.
2. Prepare import candidates under the coordinator's publication boundary, but
   parse and merge outside the database writer transaction. Each candidate
   captures exact observed bytes/hash, trusted previous base, current entity
   revisions and projection identity. A missing file requests repair unless a
   recorded tombstone/move explains its absence. Parsing failure quarantines the
   observed version while preserving the last good database state and file.
3. Add a bounded native `sync.apply` command family. Inside the sole writer,
   revalidate database revisions/base identities, then apply accepted document
   changes through Transaction.replace/create so events, search, graph, receipts
   and immutable export intent remain atomic. Preserve allocated IDs and reject
   resurrection of reserved tombstones. Capture the externally observed version
   durably for diagnosis; a conflicting external value cannot simply disappear
   from both file and history. Unknown authored fields survive.
4. Revalidate the file snapshot immediately before submission and again before
   reporting success. No correctness claim assumes external editors cooperate
   with the publisher mutex. The export expected-base check must keep a later
   edit, even if it lands between that check and import commit. A mismatch yields
   an explicit changed-during-sync/pending result, never a guessed clean state.
5. Three-way merge is permitted only with actual previously observed base bytes
   whose digest matches the stored base. Reuse the established per-field merge
   semantics, including absence as a value, but report overlap and retain the
   external version. Without a verified base, divergent versions are flagged
   and kept. A rendered entity is never a substitute merge base. Repairing a
   quarantined file with a different hash makes it eligible on the next sync.
6. Add coordinator sync coordination and a short writer-admission pause. Imports
   are submitted before taking the pause, not while holding a lock the writer
   needs. With publication held and admitted writers finished, capture the
   post-import target and export a coherent generation. `flush_through=S` must
   satisfy at least max(S, captured target), report unresolved paths, and not
   chase unrelated later writes indefinitely. Release the writer pause after
   generation capture/publication; normal commands may then commit new intent.
7. Route `take="file"`, handover/issue resync and Linear bootstrap through the
   coordinator. Explicit take-file still validates identity and file/base
   preconditions; it is not permission to erase unrelated rows or unknown data.
   Bootstrap updates the authored configuration atomically under coordination,
   preserving other workspaces and using only token environment-variable names.
8. Add an explicit CLI and managed Git worker. The coordinator owns publication
   for the entire staging/commit or pre-checkout/reconcile/checkout/post-import
   sequence. A short-lived pre-commit hook cannot by itself hold that boundary
   after it exits. The wrapper keeps it until the owned Git child completes;
   hooks validate the managed generation or refuse stale/unmanaged staging with
   recovery guidance. Use argv, bounded output and hidden owned children, never
   shell strings or discovery PIDs. Do not install/overwrite a user's hooks.
9. Linked worktrees resolve to the same main-checkout authority, with separate
   observed projection bases/generation state per checkout. Never compare a
   linked file to the main checkout's byte identity. Verify common Git root.
   Where no trusted checkout base exists, identical files may establish one;
   differing files require explicit resolution. A restored older marker is drift,
   not authority to roll the store back. Pin all participating publication until
   managed Git completes; later domain writes remain pending for the next one.
10. Persist generation/HEAD observations and publication recovery intent. On the
    next sync detect bypassed checkout/branch changes, interrupted publication
    and older markers; reconcile or report pending/conflicts. Interrupted managed
    Git records an unresolved durable pin before starting its child. Coordinator
    death alone is not proof that Git or its hooks stopped. Before restarting
    publication, recover that owned process boundary and inspect Git state;
    never automatically repeat a possibly completed commit or checkout.

## Adversarial review: managed child lifetime

Critical finding: an ordinary subprocess may survive coordinator death and race
the replacement publisher. A coordinator-owned mutex alone cannot meet step 8.
The implementation must therefore include these constraints before acceptance:

- Windows: create a private, unpredictable named Job Object with kill-on-close
  and no breakaway. Persist its recovery identity before launch. Start a hidden
  helper waiting on an owned anonymous pipe; assign it to the job before granting
  permission to launch Git. EOF before permission exits without launching Git.
  This closes the launch/assignment race without probing or signaling PIDs.
- Recovery: under exclusive coordinator ownership, use only that private job
  capability. If it still exists, retire it and wait until its active-process
  count is zero before publishing. Access failure or an unprovable boundary
  leaves publication pending, not silently unlocked. A missing job plus its
  recorded pre-launch/launch state must be interpreted conservatively.
- Other platforms need an equally tested child-lifetime/publication boundary.
  A process group or parent PID alone is not sufficient evidence. Until that
  boundary is verified, an interrupted managed operation remains a reported
  recovery requirement; ordinary restart cannot clear its durable pin.
- After quiescence, inspect HEAD, index and projection generation against the
  saved pre-operation values. Report a completed, failed or ambiguous outcome;
  commit and checkout are never blindly replayed. A recovery operation clears
  the marker only after this reconciliation. There is no permanently held
  kernel lock, but uncertainty can intentionally block publication.
- Crash tests must pause the Git helper/descendant while killing only the
  test-owned coordinator and prove the replacement cannot publish early. Cover
  pre-assignment, pre-permission, active Git and completed-Git/pre-receipt windows.

Decision (step 8 review, M6): while a helper is alive it holds an inherited,
query-only handle to its own job. That explicitly replaces kill-on-close for the
life of the helper: the coordinator's death alone does not kill Git or its hooks.
The helper holds until provable retirement. Rationale: recovery stays provable
and automatic, because the named job remains openable and a replacement
coordinator retires it (terminate + active count 0) on its next start before
anything publishes. The accepted cost: an unsupervised Git/hook may run to
completion in the meantime. Its effect is then reconciled, never replayed.
Kill-on-close still fires once the helper is gone too. The helper's handle
cannot terminate the job or assign processes to it.

This is a design requirement, not an implemented or verified guarantee.
Microsoft documents job lifetime and inherited child membership in
[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
job-scoped termination in [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject),
and the active-process counter in [job accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information).
Git's [hook contract](https://git-scm.com/docs/githooks) also requires clearing
inherited Git environment variables when invoking Git in another checkout;
pre-commit can be bypassed and post-checkout cannot prevent a completed checkout.

## Risks and reversibility

File I/O remains non-transactional to uncoordinated observers. Managed boundaries
and recovery give the stronger guarantee; do not extend it to arbitrary Git or
editor processes. Publication bases cost storage and need bounded, explicit
retention per active checkout; do not garbage-collect a base still referenced by
its checkout marker. Payload limits must reject oversized input without deleting
or mutating the source file. Sync must not replay stale exported live claims as
new claims; retained operational state wins unless an explicit supported domain
command changes it.

Implementation stays on a scoped local branch. Before any future live adoption,
N15 requires a consistent verified backup and a cutover/rollback boundary. Code
rollback is not database rollback after imports have committed: preserve receipts,
observed external versions and export jobs, stop only the owned service, and
restore a whole verified copy only with separate user authorization. Never undo
the milestone by dropping native tables or importing projections over a live DB.

## Step 8 implementation plan

Branch `feat/native-n13-git` (from `b958100`). Verified first by experiment on
this machine: a named job stays openable while an inherited handle in a member
exists, even after its creator's handle closes; its name vanishes once the last
handle closes; nested assignment works under the test runner; Git for Windows'
`sh` hooks run inside the job without breakaway.

Modules:
- `coordinator/job.py`: ctypes Job Object wrapper (no pywin32). Name
  `Local\taskmaster-git-<128-bit hex>`, protected owner-only DACL, refuses an
  existing name, kill-on-close, no breakaway flags; open/assign/contains/
  active-process count/terminate/retire.
- `coordinator/git_helper.py`: hidden helper. Reads one permission line from its
  owned stdin pipe, then runs argv-only commands (bounded output, no shell,
  `CREATE_NO_WINDOW`). EOF before permission never launches Git: an unassigned
  helper exits; an assigned one keeps waiting while it holds its inherited job
  handle, so the job stays openable and recovery can prove it empty. After `done`,
  EOF also means "hold until retired".
- `coordinator/contained.py`: create job -> start helper with only an
  inheritable job-handle duplicate -> assign -> permit -> results -> retire (job
  terminate + active count 0). POSIX: `contained=False`, helper in its own
  session; no boundary is claimed.
- `coordinator/git.py`: managed operations, probes, durable marker, reconcile,
  recovery. `git_cli.py` explicit CLI. `git_hook.py` packaged pre-commit
  validator, never installed by Taskmaster.

Durable state (`sync_state`, written directly by the coordinator under
`publication` with `synchronous=FULL`, like the exporter's lease rows):
- `git.managed`: `op_id`, `request` [caller_scope, request_id], `kind`
  (commit/checkout), `phase` (`prepared` -> `launch` -> `quiesced`), `contained`,
  `platform`, `job` name, `token_hash` (hooks), `pre` {head, ref, index sha256,
  locks}, `generation` {digest, files, through}, `target` (checkout), optional
  `outcome` once quiesced but unresolved.
- `git.last`: bounded result of the last settled operation (idempotent replay
  for a lost response; `recovered: true` when settled by recovery).

State machine (publication held throughout; writers keep committing intent, which
stays pending for the next generation):
1. Refuse if a pin/marker exists, Git root != coordinator root, or any index/HEAD/
   ref lock exists. Run the step 6 barrier with import (`synchronized` required),
   then capture the generation: every projection row's disk bytes must match its
   published hash.
2. Write `git.managed` phase `prepared` (job name) BEFORE creating anything.
3. Create job, start helper (blocked on pipe), assign, verify membership.
4. Write phase `launch`, then send permission with the argv plan.
   Commit: `git add -A --pathspec-from-file=- --pathspec-file-nul` (projection files
   plus tracked deletions, `:(top,literal)`), then `git commit -m`. Checkout:
   `git checkout <ref> --`, then a post-import sync inside the same hold.
5. Read results (bounded timeout), retire the job, and require an active count of
   0. Otherwise, pin publication and report ambiguity.
6. Reconcile HEAD/ref/index/locks against `pre` and the generation (commit tree
   blobs vs published bytes). The outcome is `completed`, `failed` or
   `ambiguous`. Completed/failed clears the marker and writes `git.last`
   atomically. Ambiguous keeps the marker and the pin.
Any exception after step 2 fails closed: an in-memory pin plus the durable marker.

Recovery: at startup an existing marker sets the pin before the exporter runs; a
recovery thread takes publication. `prepared` + missing job = permission never
granted (proven). Present job = retire + wait for 0 (proven). `launch` + missing
job, access failure, or a non-Windows marker is unprovable. It stays pinned until
the explicit `git_recover(acknowledge_quiescent=True)`. Ambiguous stays pinned
until `accept_outcome=True`. A completed checkout runs the post-import sync.
Nothing replays a commit or a checkout.

Publication gate: the exporter skips, `flush`/`sync` answer pending with the pin
reason, and Linear bootstrap refuses while pinned. An active operation holds the
`publication` RLock itself. IPC: `git_run`, `git_status`, `git_recover`.
SERVICE_PROTOCOL 2 -> 3, so a new client never talks to an owner that lacks the
pin gate. (An old coordinator binary started directly still ignores the marker;
the release boundary covers that.)

Tests (`-n 2`, multi-process ones in `heavy_processes`): job unit tests (EOF
before/after assignment, grandchild containment, retire to 0, name lifetime);
managed commit happy path and generation verification; a writer racing staging
(pre-commit hook paused in a temp repo); partial multi-file generation; Git
failure; refusals (lock, pin, root mismatch, conflict); hook helper
managed/unmanaged; crash windows with a subprocess coordinator killed through its
own Popen handle at `git_helper_started` (pre-assignment), `git_permit`
(pre-permission), active Git (hook paused) and `git_helper_done`
(completed/pre-receipt). The replacement is an in-process coordinator whose
checkpoints assert that nothing is published before retirement and the zero count;
POSIX pin refusal is checked via a monkeypatched platform.

## Steps 9-10 implementation plan

Branch `feat/native-n13-checkouts` (from `039b960`). All Git work uses disposable
temp repositories (`git worktree add` inside tmp); no real hook or repository.

**Publication model (decision).** Design D01 keeps one authority at the main
checkout; section 7 asks for pre-commit flush and post-checkout import "across
main/linked worktrees". The main checkout stays the continuously published
projection (background exporter, `flush`). A linked checkout is published *on
demand only*: an explicit `sync(worktree=W)` or a managed `git_run(worktree=W)`
imports W's edits against W's own bases, runs the ordinary main barrier, then
copies the main checkout's published generation into W by compare-and-swap
against W's bases. Nothing renders into W directly and the background exporter
never writes W, so agents' feature-branch worktrees are not rewritten behind
their backs. This is reversible (continuous linked publication would be additive)
and follows the scope's "pin all participating publication": only checkouts an
operation names participate, and the global `publication` lock pins them all.

**Checkout identity.** `main` for the coordinator root. A linked checkout is
`wt-` + sha256(common dir, admin dir name, admin dir device:inode)[:24], so a
removed-and-recreated worktree with the same name or path is a new checkout
(new admin directory), while `git worktree move` keeps its identity. Validation
(`git -C W rev-parse --show-toplevel --absolute-git-dir --git-common-dir`): W must
be its own top level, its common dir must equal the coordinator root's (else
refused: common-root mismatch), and its git dir must be `<common>/worktrees/<n>`.
The coordinator root must itself be the main checkout (git dir == common dir).

**Storage.** Main keeps `projection`/`projection_base` (unchanged fence). Linked:
`checkout_base(checkout,file,digest)` plus content-addressed `checkout_blob
(digest,content)` (bases are nearly always published bytes, so they dedupe);
`checkout_hold(checkout,file,reason,digest)` for drift/conflict/quarantine/no-base
holds that stop publication into that path of that checkout only. Per checkout
`sync_state['checkout.<id>']` = {path, git_dir, observed {head, ref}, generation
{digest, through}, intent (publication recovery), released {rel: digest}}. Main
drift stays in `git.drift`. Retention: one base per (checkout, file); a blob is
deleted with its last reference in the same transaction; at most 32 linked
checkouts; a checkout's rows are dropped only when Git's admin directory for it
is gone or now belongs to a re-added worktree (ids are recomputed from the admin
dir on every registration; never while its marker/admin dir exists); bases of paths the store no
longer publishes are dropped when W's file is removed by publication.

**Linked sync algorithm.** Per path (W's discovered files plus main's published
rows): no W base + bytes equal to the published bytes -> establish the base;
no base + differing -> pending "no trusted base in this checkout" (take_file or
remove the file to receive the published one); base + equal -> unchanged; base +
differing -> the bypass classifier below; drift is held, otherwise a three-way
import with W's base bytes (`sync.apply` gains `checkout`, which fences W's base
token, records W's new base atomically and never touches main's manifest,
conflict flags or quarantine; conflict/quarantine become W holds). Then the main
barrier; then W publication: intent is durable first ({rel: target digest}); each
file is set aside, the aside bytes are verified against W's base, the temp is
installed with no-overwrite, as the exporter does; W's base becomes the target.
Files the generation no longer contains are removed from W only if they still
carry W's base. A held, dirty or unbased file is never overwritten; it is named
pending. The next sync first settles a leftover intent (asides restored or
dropped, installed targets recorded) and reports it as interrupted publication.

**Bypass detection (both kinds of checkout).** HEAD/ref are observed after each
full sync and settled managed operation (a named-file sync classifies but never
advances the observation). Movement O->N is `none`, `commits` (every reflog entry
since O is a plain `commit`/`commit (amend)`/`commit (initial)`: the worktree was
not rewritten), `rewrite` (checkout/switch/reset/merge/pull/rebase/cherry-pick or
an unreadable reflog) or `unknown` (nothing observed yet). A file differing from
its checkout base is **drift** (held, never import authority) when:
- Git is part-way through an operation in that checkout (`MERGE_HEAD`,
  `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `SQUASH_MSG`, `AUTO_MERGE`, `rebase-*`, or
  unmerged index entries): every differing file, missing ones included;
- the movement is `rewrite` and Git changed that path between O and N (or the
  change is unknowable);
- its bytes equal a blob that path had in any commit Git still knows (all refs,
  the stash, every reflog), except the plain commits made since O: `checkout <rev>
  -- p`, `restore --source`, committed reverts, stash applies, squash results once
  committed. The walk is bounded (5,000 commits per 100 paths); a walk that hits
  the bound holds the unmatched bytes too. **Deliberate semantics:** a hand edit
  back to an earlier committed value is held as well; `take_file` adopts it.
Everything else is authored (bytes no earlier commit holds, including a plain
commit of them). `unknown` uses the same byte rules rather than holding every
differing file, so the first sync after an upgrade does not hold the whole
projection: any bytes Git could have put there are historical blobs or the result
of an in-progress operation. Missing files follow the same rules; otherwise missing
means repair. A file is imported only while it carries exactly the digest that was
classified and while HEAD is where classification saw it (else pending, retry); an
uninspectable Git state fails closed (pending, nothing imported). Drift is held
(main: `git.drift`; W: hold) and released by bytes returning, `take_file`, or an
explicit verb: `git recover --release-drift import [--worktree W]` (the digests
are recorded so ordinary sync imports them; unbased linked paths need
`take_file`) or `--release-drift take-published [--worktree W]` (a path still
carrying exactly its held bytes, or missing, is retained in `git.discarded` - the
newest 32, up to 256 KiB each - then receives the published file by
compare-and-swap; a path whose bytes changed since the hold stays held). `recover`
never picks a checkout from cwd, and results name the checkout acted on.
Unmanaged commits whose committed projection blobs are not the checkout's bases
are reported as a mixed/unverified generation warning with the commit id.
Known limit: a `cherry-pick -n`/stash result merged with local changes and then
committed is a new blob and is treated as authored.

**Managed Git in a linked checkout.** `git_run(worktree=W)` lifts the
non-top-level refusal for validated linked checkouts. The marker records the
checkout (id, path, git dir); probes, locks (W's git dir plus common refs), index, commands
(`cwd=W`), tree verification and reconciliation all use W. The pre-sync is
`sync(worktree=W)`; the generation check compares W's files to the published
bytes. A completed checkout in W records drift as W holds; main is unaffected.
Containment, durable marker, receipts, trailer, `--only` pathspec commits and
recovery are unchanged. The pre-commit hook uses the checkout's own top level when
its git dir is the common dir (main checkout, submodules, `--separate-git-dir`) and
the first `git worktree list` entry for a linked worktree, so a linked commit is
validated instead of passing as "no native store"; a resolution failure, or a local
store the resolved main checkout lacks, refuses. A linked operation holds the global
`publication` lock, so a crash pins main too (accepted: publication is one
authority); once its job is proven empty, a marker whose linked worktree admin dir
is gone or replaced settles as `failed` without operator acceptance.
`SERVICE_PROTOCOL` 3 -> 4: an old owner would silently ignore `worktree`.

**Test matrix.** Identity (main, linked, recreated worktree, common-root
mismatch, non-top-level path); linked sync (base establishment, unbased
differing file kept, edit imported via W base, conflict held only in W, dirty
file never overwritten, deletion of a moved path, interrupted W publication
recovered on next sync); bypass in main and linked (plain `checkout`, `switch`,
`reset --hard`, `commit` of an edit imported, `checkout -- path` restore, mixed
unmanaged commit warning); store never rolls back; managed commit and checkout in
a linked worktree (crash-path parity via existing marker/recovery tests run with
a linked marker); hook in a linked worktree.
