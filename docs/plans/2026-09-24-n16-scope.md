# N16 execution scope: scale, durability and end-to-end acceptance

Status: scoped 2026-09-24. No live project activation. All measurement runs use disposable copies
or synthetic datasets. Heavy runs happen **one at a time**.

## Grounding

- **First sync after activation: 310–682 s on CodeMaestro.** Root cause measured
  (report in this milestone):
  - Cutover leaves `projection_base` empty, so each of 3,703 files takes the `observe` import path.
  - Every submitted file spawns `git` twice (`checkouts.observe`, `sync_worker.py:329`). That
    costs about 138 ms per file, 512 s of the 682 s.
  - "Import outcome uncertain" is budget expiry after submit: every such write had in fact
    committed.
  - Seeding bases (A) takes the first sync to 10.9 s; adding the fingerprint cache (B) takes it
    to 4.6 s.
- **Existing tooling:**
  - `scripts/benchmark_native_core.py` (DB core, ≥200 samples, p50/p95/p99, no IPC);
    `benchmark_store.py` (legacy);
  - rehearsal scripts N13–N15 (single-client coordinator);
  - `measure_test_memory.py` (RSS);
  - `Transaction.counters` (graph and FTS work);
  - the bypass gate and zero-graph-work tests (deterministic gates).
- **Gaps:**
  - no 8/12-client coordinator harness;
  - no synthetic 10× generator;
  - no lock-wait/hold, files-read, cache-hit or IPC-startup counters;
  - `Server-Timing` is wired on only 2 routes.
- **Carried performance items:**
  - `budget.budget` is O(n²) (`native/budget.py:106`);
  - dashboard `reads.tree` takes 411 ms vs 120 ms legacy;
  - export and `coordinator/git.py` `generation()` read and hash every file (6–9 s per managed
    operation);
  - backup archive takes 28–53 s;
  - large-board native apply is slower (a browser measurement).
- **FTS diagnostic:** cause documented and legacy fix tested (B-092). The native admission path
  must be re-verified to give the supported outcome.

## Tracks (ordered; A and B in parallel, then C and D, then E)

**A. Make the first sync after activation fast and honest.**
1. Seed `projection_base` inside activation for each non-quarantined file whose bytes hash to
   `content_hash`. It runs after `verify_carryover`, or the oracle allows additive bases.
2. Seed the sync fingerprint cache at activation.
3. `observe` plans skip the Git HEAD check, which stays for `apply`/`conflict`. Check HEAD once
   per batch, or read it without spawning a process.
4. Keep a time reserve before submitting. On a timeout, grant a short grace period, then look up
   the receipt and report the real outcome. Report observes separately from imports.
5. Exit: the first sync on a CodeMaestro copy completes in one round well under the 120 s
   budget, and no "uncertain" appears for a committed write.

**B. Carried performance defects.**
- **`budget.budget`:** render once, using a prefix sum or incremental size, with an unchanged
  answer.
- **Dashboard:** targeted aggregate queries in place of `reads.tree`, with byte-identical output.
- **Export and generation check:**
  - add an mtime/size/inode short-circuit, with a full read on any doubt and a periodic full
    verification;
  - keep `generation()`'s full read where correctness needs it, but measure whether the Git
    barrier can use the same safe fingerprint rules;
  - document the decision.
- **Backup archive:** measure, and store files rather than recompressing already-small ones, if
  cheap.
- Each item gets an oracle proving identical output, plus a before/after measurement.

**C. Instrumentation.**
- **Per-command work counters:** lock wait/hold, DB time, rows read/written, files stat-ed/parsed,
  cache hits, output bytes.
- **Coordinator:** IPC startup and export lag.
- **Opt-in:** off by default and uninstrumented for latency samples, as the plan requires.

**D. Harness.**
- **Synthetic generator:** small and 10× CodeMaestro-shaped datasets with a controlled path/edge
  distribution, anonymized from measured shape statistics only.
- **Multi-client load:** real coordinator clients as processes at 1/4/8/12, same and disjoint
  entities, duplicate retries.
- **Scenario runner:** the plan's N16 matrix (datasets × reads × writes × clients × sync ×
  failure × history × migration). At least 200 measured operations per steady-state scenario;
  p50/p95/p99/max and errors; cold/adoption runs kept separate; counters in a separate
  instrumented pass.

**E. Run and report.**
- **Correctness gates first:** the full suite, the 8×200 `-m scale` profile, 12-client
  no-lost-ack and no-reused-ID, crash and export matrices, and FTS on native.
- **Then performance:** the matrix on synthetic small, the CodeMaestro copy and synthetic 10×,
  with viewer workflows.
- **Report:** the results against the design §11 budgets (reads p95 < 100 ms, core < 50 ms,
  simple writes < 250 ms). Budgets are provisional: misses are reported, not hidden, and never
  bought with a correctness relaxation. The deterministic work assertions are the hard gates.

Each track uses its own worktree off `feat/native-n16`, works test-first, and gets an independent
adversarial review. The CodeMaestro-copy runs are copy-only.

## Risks

- **Machine noise:** measurements on a shared, RAM-tight machine vary by 1.5–2×. Pin runs, run
  them alone, and record load.
- **Pinned timings:** seeding bases must never trust bytes it has not hashed.
- **Budget misses:** some budgets may be unrealistic on this hardware with `synchronous=FULL`.
  Report them, and raise them to the user rather than weakening durability.
