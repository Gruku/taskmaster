# N14 execution scope: consumer graph migration and compatibility completion

Status: **scoped; F1 decided = A (user, 2026-09-23)**. Implementation starting at step 1. This
repository has no backlog; evidence goes to the ledger and an N14 report. No live
CodeMaestro mutation, activation or hook installation is authorized by this plan.

## Where the code stands (verified 2026-09-23 at `2ca2d20`)

**Two graph representations coexist in a native database.**

- *Canonical claims/edges* (N03, `native/schema.py:16-34,99-111`): `dependencies`,
  `memberships`, `declared_links`, `path_claims`, each with indexed reverse access
  (`ix_{table}_target`, `ix_{table}_target_key`, `ix_path_claims_path`). The typed
  read API `Snapshot.relations()` / `Snapshot.references_to()` (`native/queries.py:209-230`)
  exists, is tested, and **has no production caller**.
- *Legacy derived tables* `entity_paths`, `links`, `related`, `handover_tasks`
  (`store.py:369-408`), kept synchronously current inside every native command by
  `native/relations.maintain()` (`native/commands.py:159-162`). They are computed
  from document before/after diffs, not from the canonical tables. N06 proved them
  equal to the legacy full rebuild (`tests/test_native_relations.py:19`).

**`related` semantics (the frozen contract).** Undirected pair stored once as sorted
`(a,b)`. `via='path'`: one row per pair, `weight` = number of matching
anchor/location claim pairs (exact equality, or case-sensitive `fnmatchcase` in
either direction, including glob-vs-glob); prose paths excluded; self-pairs
excluded. `via='handover'`: `weight=1`, **one row per co-membership** (multiplicity
as row repetition). Declared links and `depends_on` never enter `related`; they are
in `links` (directed, typed, with `derived=1` reverse mirrors). Archived-but-live
entities keep their rows; deleted entities lose them.

**What each native command pays today.** Metadata-only edits issue no graph SQL
(`test_metadata_only_maintenance_executes_no_graph_sql`). Link and handover changes
touch only affected pairs. But a changed anchor/location runs
`_path_neighborhood` (`native/relations.py:81-94`), which loads **every**
anchor/location row in the project and `fnmatch`es each against each own path:
cost `k × all paths` (~3,800 rows on CodeMaestro), not `k × candidates`. This is
the remaining violation of the N14 exit ("pay only for changed relation inputs").
Also `_kind_for_id` guesses `task` for an unresolved link target where the
canonical table already records `target_kind`.

**Consumers.**

| Consumer | Reads | Semantics relied on |
|---|---|---|
| `hooks/edit_resurface.py` `_RELATED_SQL` (`:87-90`, `_count_related` `:226-250`) | `related`, both stores, no native branch | Distinct neighbours, weight ignored, filtered live by open status / `archived=0` / `deleted=0`; answer deduped per `revision()` |
| `backlog_query` (`backlog_server.py:2896`; native via `native/compatibility.py:14-63`) | Any of the 10 frozen names; `WITH RECURSIVE` allowed; 5 s / 500 rows | Whatever the table holds. On native, every call copies all ten tables into a private in-memory DB (documented as deliberately expensive) |
| `backlog_dependencies` (`backlog_server.py:3155`; native `native_routing/tasks.py:861-943`) | `depends_on` fields; downstream by O(n) scan of every task | One hop each way; no recursion, depth or cycle handling |
| Viewer `/related` (`backlog_server.py:10314`; `native_routing/viewer.py:98-124`) | Continuity files + O(n) `depends_on` scan | Not a `related` consumer |
| `native/context.py` | Canonical `dependencies` / `declared_links` | Already canonical |
| `backlog_blast_radius` | Source import graph + anchors | Not a backlog-graph consumer; out of scope |

So the only automatic `related` reader is the edit hook. Everything else that reads
it arrives through `backlog_query`. No native repair operation exists for the graph
tables: `grouped_weights()` (the exact full oracle, ~0.1 s compute on CodeMaestro's
3,784 path rows / 39,027 relation rows per the 2026-09-09 roadmap) is used only in
tests.

## Decision F1 — freshness of direct `related` SQL (user decision)

The design (§6, §9) fixes the constraints: a retained `related` SQL surface must
never quietly return stale or partial rows; a full-graph materialization is either
a documented operation or the synchronous representation; it is never an
unannounced normal-read cost. Options:

- **A. Keep `related` synchronously maintained, make it incremental (recommended).**
  `related` stays current at commit exactly as today. The per-change cost drops
  from `k × all paths` to `k × candidates` through indexed exact lookup, a
  glob-only peer set, and literal-prefix range scans for own globs. The matrix
  records `related` as "current at commit". On-demand replacement is recorded
  as a later capability, as the plan explicitly allows. Pros: zero semantic
  risk, and `backlog_query` latency is unchanged. The candidate function is also
  reused by the hook's canonical neighbourhood query, so one algorithm serves
  both. Cons: path-changing commits still pay a small, bounded maintenance cost,
  and two graph representations remain.
- **B. On-demand materialization in the compatibility snapshot.** Stop
  maintaining `related` in commands. When a `backlog_query` statement names
  `related`, build it from canonical claims with `grouped_weights()` inside the
  private in-memory DB it already builds, and report it in `materialized_rows`.
  Pros: commits pay nothing for the path graph, and the representation that
  could go stale disappears. Cons: each such query pays about 0.1–0.5 s more on
  CodeMaestro-scale data, which must stay inside the 5 s deadline. The live
  database's `related` table becomes dead or must be dropped, which is a schema
  change and a problem for downgrade (N15). Legacy stores still maintain it. The
  hook must migrate first.
- **C. Dirty-set with repair-on-read.** Commands only mark changed entities, and
  the next `related` read repairs them first. Rejected: a read would need the
  writer, which reintroduces the writer-mutex read stalls of B-082. It is also
  the most complex option.
- **D. Drop `related` from the public surface.** This breaks a frozen N02
  contract, is an unannounced product change, and is excluded for this release.

**Decided: A** (user, 2026-09-23). Recommendation was **A**: Its remaining cost is bounded by the edited entity's actual
candidates. It changes no answers. It keeps the N15 downgrade simple because the
tables are identical on both stores. It leaves B available later as an explicit
capability.

## Implementation sequence

1. **Oracles first.** A hook-neighbourhood oracle: legacy `_RELATED_SQL` plus the
   status filter against the new canonical answer, on both stores, over the N06
   seeded edit sequences. A work-counter oracle: `path_comparisons` counts
   candidates examined and must not grow with unrelated path rows (2,000 unrelated
   anchored documents, as in the N06 work-budget test). Both tests fail on today's
   code.
2. **Indexed incremental path neighbourhood.** A single candidate-discovery
   function over `entity_paths`: exact via `ix_entity_paths_path`, peer globs
   from a glob-only index/partial index, own globs via literal-prefix range. It
   preserves glob-vs-glob, case-sensitivity, duplicate contribution weights and
   self-pair exclusion. It must be equal to `grouped_weights()` on the 100-case
   seeded set and the N06 80-edit sequence. `_kind_for_id` takes the canonical
   `target_kind`, with a test for unresolved targets that stays
   answer-compatible.
3. **Canonical neighbourhood read.** Add `Snapshot.neighbourhood(kind, id,
   limit)`: path neighbours via step 2's function plus handover co-members via
   `memberships` reverse index, returning distinct `(kind, id, via, weight)`. No
   top-K or ranking change. The limit is a page with `truncated`, not relevance.
4. **Edit hook migration.** The native branch of `_count_related` uses step 3
   through `hook_reads` (stdlib-only admission rules preserved). The legacy branch
   stays unchanged. `test_related_open_work_is_counted_not_named` and the dedup
   tests run on both stores.
5. **Typed graph queries.** `backlog_dependencies` downstream and the viewer's
   dependency half use `references_to` on `dependencies` (indexed reverse)
   instead of O(n) scans. Add bounded recursive traversal as an **additive**
   optional `depth` (default 1 = today's output byte for byte): a recursive CTE
   over canonical `dependencies` with cycle detection, depth cap, output cap and
   deadline, reporting `truncated`/`cycle`. Legacy gets an equivalent
   Python-bounded walk for parity. Verify current vs archived targets and
   unresolved ids.
6. **Compatibility completion.** Update the N02 matrix: `related` freshness
   (current at commit), `links`/`handover_tasks`/`entity_paths` status, the new
   neighbourhood/depth APIs as explicit additions. Add a native graph
   verify/repair maintenance operation, built on `grouped_weights()` plus the full
   link and handover rebuild. It must report its cost and must never run on a
   normal path. API docs.
7. **Copy-only CodeMaestro rehearsal** on a fresh clone at stock settings. Check
   that `related`/`links`/`handover_tasks` equal the full oracle after a mutation
   script (anchor add/remove, glob anchors, handover edits, link edits,
   archive/unarchive, delete), that hook answers match between legacy and native,
   that work counters are bounded by candidates, that `backlog_query` timings and
   `depth` traversal behave, and that nothing in the live checkout is touched.

Each step: own worktree/branch off `feat/native-n14`, test-first, independent
adversarial review by a fresh sub-agent, merge `--no-ff`. The full suite runs at
the milestone boundary (`-n 3`, ≥8 GB free).

## Acceptance evidence

- Selective `related`/`links`/`handover_tasks` equal the full oracle across seeded
  and random edits, on both stores.
- Work counters are bounded by candidates, and adding unrelated anchored documents
  does not raise them.
- Hook answers are identical on both stores, `depth=1` dependencies are byte for
  byte, and traversal budgets and cycles are covered by tests.
- The matrix records the freshness of every retained graph SQL name.
- The rehearsal passes on a copy, and the full suite is green.

## Risks

- Glob semantics are subtle (glob-vs-glob, character classes, case). The oracle
  equality must cover them before the full scan is removed.
- An unchanged glob elsewhere can match the edited entity's new path, so reverse
  glob discovery is mandatory.
- Handover multiplicity is expressed as row repetition. Neighbourhood `weight`
  must aggregate it explicitly and must not change `related` rows.
- Hook admission must stay stdlib-only and fail-open.
- `depth` must be additive. Any change to default output is a contract break.
