# N15 execution scope: migration and downgrade rehearsal

Status: **scoping; blocked on decision M1 (below).** No live project migration is authorized.
Every run uses disposable copies marked `.benchmark-copy`.

## Where the code stands (verified 2026-09-24 at `69f2aba`)

- **Backfill exists and is crash-safe; activation does not.**
  - `native/migrate.py` `backfill()` runs the stages admitted → schema → entities → relations
    → history → search → verified in one transaction. It is repeatable and always leaves
    `authority='legacy'`, so it is a verified staging snapshot, not a cutover.
  - The only code that flips authority is test scaffolding, `tests/native_twins.py`
    `activate_native()`. It bumps `meta.schema_version` and `minimum_client_protocol` to 2,
    sets `native_manifest.authority='native'`/`state='ready'`, runs
    `repair_graph_for_activation`, and seeds `id_counters`/`id_reservations` from rows plus
    the `id-reservations.json` sidecar. It does all of that in one bare commit, with no
    checkpoints, backup, fence or process check.
- **Fencing.** `admission.assert_compatible` refuses newer schema/protocol and any
  `migration_state != 'ready'`. Nothing publishes `migrating`. Pre-bridge binaries ignore
  these markers, so they must be stopped, not merely refused. The fencing handoff's
  launcher inventory lists them: Claude and Codex plugins, the manual MCP server, the
  viewer, hooks, scripts and the Linear worker.
- **Ownership.** `coordinator/ownership.py` holds an exclusive OS lock (`owner.lock`), and a
  running coordinator retires itself when the authority identity changes. No command
  quiesces MCP servers, viewers or hooks, or waits for them to drain.
- **Rollback, backup and downgrade.** None exist. The only backup code is the dev rehearsal
  script's `sqlite3.backup()`.
- **Verification gaps.** `_verify()` checks entities, events, FTS and FKs. It does not check
  `linear_queue`, `projection` (dirty or quarantined), receipts, `projection_jobs`, ID
  counters or reservations, or pending changelogs.
- **Pending changelog.** N11's `progress.seed()` copies `meta` into `sync_state` once, on the
  first native write. The cutover must reconcile it explicitly and verify the seed.
- **Carried in.** The graph repair must run inside the switch transaction (it fixes 4,610
  `links` rows on CodeMaestro). The first post-activation sync took about 350 s on
  CodeMaestro.

## Decision M1: downgrade support (user decision)

- **A. No old-format reverse migration (recommended).**
  - *Before activation:* rollback is exact. Restore authority from the consistent backup,
    or simply leave `authority='legacy'`.
  - *After activation:* recovery rolls forward only. Code can roll back only to a
    native-capable version, and older binaries are refused by the protocol markers.
  - *Escape hatch:* the projection files (v4 YAML/markdown) remain the durable exchange
    format. A native store can flush a coherent generation, and a fresh legacy adoption
    of those files recovers every authored document. Only DB-local state is lost:
    receipts, sessions, queue leases and history sequence. The runbook documents this as
    a manual, lossy-for-local-state procedure.
  - *Why:* a real reverse migration doubles the surface area, and it must never discard
    acknowledged writes. Restoring the pre-migration snapshot would discard them, so it
    is refused once any native write has committed.
- **B. Supported reverse migration.** A `cutover --reverse` command rebuilds legacy
  `entities`, `changes` and `meta` from native state, keeps every acknowledged write, and
  republishes legacy markers. This is a large extra deliverable with its own crash matrix,
  and it keeps two formats alive.

## Implementation sequence (assuming A)

1. **Cutover journal and state machine.** A durable `migration_state` sequence: `ready`,
   then `migrating:<stage>` with owner and token, then `ready` under native. It is published
   under the coordinator ownership lock and a `BEGIN IMMEDIATE` fence, so admission refuses
   bridge-capable clients while the fence is up. The stages are fence, reconcile, backup,
   backfill, compare, activate and release, and each is idempotent and recorded.
2. **Quiesce and refusal.**
   - The command acquires ownership.
   - It refuses if a coordinator or service is live, or if the store has other open
     writers: a WAL writer probe plus the coordinator discovery record.
   - It runs a best-effort, stdlib-only scan for processes from the launcher inventory.
     That is PowerShell/CIM on Windows and `/proc` or `ps` on POSIX, and it only warns,
     because pre-bridge binaries can't be refused.
   - Proceeding past a warning requires an explicit `--confirm-stopped` flag.
   - Tests cover warm clients (a running server) and cold clients (next launch).
3. **Reconcile.** Drain or refuse pending exports and imports: dirty projections,
   quarantine, the Linear queue, and both pending changelogs. The changelog is reconciled
   explicitly into `sync_state`, and the seed marker is written and verified.
4. **Consistent backup.** Use `sqlite3.backup()` to `.taskmaster/local/backups/pre-native-<ts>.db`,
   plus a projection manifest (path, hash, size), the ID-reservation sidecar and a digest.
   The backup is verified by reopening it and running an integrity check.
5. **Backfill, then compare.** Reuse `backfill()`. Extend the comparison oracle to cover the
   `linear_queue` rows, projection flags and quarantine, receipts, ID high water and
   reservations, and the pending changelog. The `native_twins` activation's ID import
   moves into production code.
6. **Activate.** One transaction publishes the schema and protocol markers,
   `authority='native'`, `ready`, runs `repair_graph_for_activation`, imports the ID
   counters and reservations, and records the journal as done. Then release the fence.
   `native_twins.activate_native` delegates to this code path, so every twin test exercises
   the production activation.
7. **Rollback and roll-forward.**
   - `cutover --resume` continues from the last durable stage.
   - `cutover --rollback` works only before activation commits. It drops the fence and
     returns authority to legacy, or restores the backup if staging was corrupted.
   - After activation, `--rollback` refuses and names the escape hatch.
   - A crash at every stage is tested (exception plus `os._exit`) for resume and rollback.
   - Code rollback to a non-native-capable version is shown to be refused.
8. **Dry run and runbook.** `cutover --dry-run` reports every check and the counts without
   writing. An operator runbook, `docs/runbooks/native-cutover.md`, covers the launcher
   stop list, commands, expected output and recovery.
9. **Copy-only rehearsal on CodeMaestro.** Follow the full sequence at stock settings: dry
   run, cutover, verify, the first sync (timed; target the ~350 s carry-forward), crash
   injection at each stage on fresh copies, resume and rollback, the escape hatch
   demonstrated, and old-client refusal.

Each step gets its own worktree branch off `feat/native-n15`. The work is test-first, each
step gets an independent adversarial review, and the full suite runs at the milestone.

## Acceptance evidence

- A crash at each stage both resumes and rolls back correctly.
- The extended oracle proves state is preserved: seq, IDs, queues, reservations,
  quarantine, unknown fields, in-flight exports and both changelogs.
- Warm and cold old clients are refused.
- The dry run and runbook have been executed on a copy.
- Zero live migrations.

## Risks

- **Pre-bridge processes** can't be refused, only detected on a best-effort basis. The
  runbook stop list is the real control.
- **The first sync** after activation (about 350 s) may exceed client timeouts. It must be
  measured, and the fix may be deferred to N16.
- **Backup size and time** on CodeMaestro: measure both.
