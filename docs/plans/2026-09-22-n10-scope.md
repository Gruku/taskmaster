## 1. What is actually true today (evidence, not assumption)

### 1.1 The board is one unconditional full GET every 3 s

- **Poll loop.** `main.js:92-124` calls `store.setBacklog(await api.backlog())`
  (`:99`) and then sleeps `BACKLOG_POLL_MS = 3000` (`:6`). It backs off up to 60 s
  on failure (`:106-109`) and pauses while the tab is hidden (`:112-122`). There
  is no SSE and no WebSocket.
- **No conditional GET on either side.** `api.js:21-30` stores the board's ETag
  as `etags.backlog` (`:29`), but nothing reads it back. No file under `viewer/js`
  sends `If-None-Match`. The server never answers 304: `do_GET`
  (`backlog_server.py:10403-10661`) has no `If-None-Match` branch, and every
  route ends in `_send_json(200, …)` (`:11312-11334`).
- **Measured (2026-09-09, CodeMaestro copy, legacy store, before native):**
  `/api/backlog` returned **16,209,089 bytes** and took 2.279 s on the first request. The same
  request with `If-None-Match` also returned **200** with the same bytes, in 0.932 s
  (roadmap `:284-294`). The harness is `scripts/benchmark_performance_audit.py:203-222`.
  No native measurement exists, and nothing has measured the client.
- **The client pays twice per poll.** `store.setBacklog` (`store.js:51`) runs
  `jsonEqual`, which calls `JSON.stringify` on both the old and the new payload
  (`:37-42`). That happens every 3 s whether or not anything changed. If anything
  differs, `emit('backlog')` repaints every subscribed screen from scratch:
  `kanban.js:467`, `table.js:296`, `epics.js:17` and `archived.js:93`.

### 1.2 What the payload carries, and why most of it is waste

`_serve_json` (`backlog_server.py:10782-10816`) serves the store's compatibility
dict almost unchanged:

- **Tasks appear twice.** The tree keeps them under `epics[].tasks`. When the tree has no top-level
  list, `_serve_json` builds one (`:10793-10798`). On CodeMaestro this came to
  5.82 MB under `epics` and 5.67 MB under `tasks` (roadmap `:291-292`).
- **Private `_rows` is shipped.** Legacy serializes every bug, issue, handover,
  decision, idea, note, area and tracker with its body: 4.36 MB on CodeMaestro.
  Native replaces the map with `NativeRows(None)` (`:10786-10789`), which
  `json.dumps(default=str)` renders as an object repr. The parity test documents
  this: `tests/test_native_routing_viewer.py:77`.
- **Prose rides on every task and epic.** Native `reads.tree` attaches each
  task's `_body` (`native_routing/reads.py:196-201`). Epics come from
  `reads.epics` → `document(entity)`, which includes the epic body (`:32-37`,
  `:70-76`). Legacy carries `_body` the same way: `_task_full_from` pops it off
  the tree's own task (`backlog_server.py:10180-10181`).
- **Archived tasks are included** (`reads.py:198`, `include_archived=True`).
  The archived screen needs them (§1.3).
- **`context` is not a pure function of committed state.** `_derive_context`
  (`backlog_server.py:1678+`) builds `next_up` by excluding
  `_claims.foreign_holder(t, SESSION_ID)` (`:1737`). That depends on which
  server process answers. It also puts the raw `locked_by` into
  `context.in_progress` (`:1703-1704`), with no expiry predicate. Only
  `context.active_epic` has a consumer (§1.3).
- **`meta._version` = the server's `VERSION`** (`:10792`). The body changes on
  upgrade even when the store has not changed.

### 1.4 Detail reads cost a full tree each, and there are several per open

- Opening a task runs `getTaskFull` and `getTaskRelatedFull` in parallel
  (`task-detail.js:34-38`, `detail-modal.js:79-81`), which means two GETs.
- **Each GET builds the whole board to serve one task.** Legacy
  `_load_task_full_identified` → `_load_snapshot` → `load_dict_with_identity`
  (`backlog_server.py:1115-1129`; `store.py:2433-2505`). Native `task_full`,
  `epic_full`, `related` and `recent_events` all go through `snapshot()`, which
  runs `reads.tree` and then decodes **every** row kind (`native_routing/viewer.py:45-58`,
  `:68-124`).
- **A native PATCH builds the tree at least three times:** `snapshot()` for the
  precondition (`viewer.py:411`), `_task_errors` (`:415`), and `snapshot()` again
  for the response ETag (`:449`). An archive calls `snapshot()` for its ETag too
  (`:395`).
- **Two of them are then thrown away by the client.** After any inline edit, `task-detail-document.js:19` and
  `task-actions.js:47` do a full `api.backlog()` to refresh the list screens.

### 1.5 Edit preconditions are weaker than they look

- `api.js:12-19` attaches `If-Match` from `etags['task:<id>']`. That entry is only
  set by `http()`'s capture (`:21-30`). **`getTask` uses a raw `fetch`
  (`api.js:62-69`), so the ETag of the detail read is never captured.** The
  first edit after opening a task therefore carries no `If-Match`, and the server
  accepts it unconditionally (`_check_if_match` returns early on an empty value,
  `backlog_server.py:9928-9940`; pinned by `tests/test_server_etag.py:91`). A
  precondition applies only to later edits, using the ETag from the previous
  PATCH response.
- **The ETag is store-wide:** `<creation_token>:<max changes.seq>` on legacy
  (`:9974-9994`) and `<store_id>:<event_high_water>` on native
  (`viewer.py:40-42`, checked inside the writer lock by
  `native/workflow.py:1463-1471`). Once a precondition is in play, any write
  anywhere, including an agent filing a bug, turns the next field edit into a
  409 conflict banner (`inline-field.js:101-122`, `task-actions.js:48-63`).
- **The detail cache is never invalidated.** `_taskCache` and `_relatedCache`
  (`store.js:70-90`) are cleared only by the view toggle (`task-detail.js:50`).
  Re-opening a task after a peer's write shows the version cached the first
  time. After the viewer's own write, the inline field keeps its local copy.

### 1.6 The claim boundary handed over by N09

- The detail page renders a lock banner whenever `task.locked_by` is truthy
  (`task-detail-document.js:113-115`). It applies none of `claims.read`'s rules
  (`native/claims.py:232-251`): an expiry stamped for this holder, a terminal
  status, or a holder proven dead. So it can show a claim that `backlog_claim`
  and `backlog_context` treat as expired, or show a holder on a `done` task
  from before N09's terminal rule (N09 scope §4c′, §5.3, row 3 of §4f).
- **Writes are already closed:** every viewer payload drops `locked_by`,
  `claim_expires` and `claim_expires_for` (`backlog_server.py:9996-10001`,
  `claims.without_claim_fields`). The form lists them as `systemManaged`
  (`task-form.js:95-96`). N10 only has to fix the read side.
- Claim state depends on the **wall clock** and on the `sessions` table
  (`claims.read`: `now`, `holder_liveness`). It cannot sit in a payload whose
  304 is keyed on committed state alone (§2.2).

### 1.7 What the stores already give us

- **Per-row sequence on both stores.** Legacy `entities.updated_seq`
  (`store.py:300-312`) is bumped by every update, archive, unarchive and soft
  delete (`:4963`, `:6447`, `:6518`, `:6544`, `:6562`). Native keeps
  `entity_core.last_seq` with `ix_entity_core_changed(last_seq, entity_key)`
  (`native/schema.py:53-56`). **The legacy dict cache already refreshes
  incrementally on `updated_seq > ?`** (`store.py:2719-2745`). That is the
  precedent a row-based delta reuses.
- **Neither store hard-deletes an entity row.** A grep for
  `DELETE FROM entities` / `entity_core` finds nothing. Legacy sets `deleted=1`
  (`:6562`). Native has no command that sets `deleted=1` (N11 scope §2.6). A
  removal is therefore always visible as a row whose sequence moved.
- **The N09 feed** (`native/queries.py:241-310`; legacy
  `backlog_server.py:5754-5829`) is scoped and grouped by commit, and resyncs
  instead of erroring. But it returns field **names**, not values ("authored values
  are never returned"). On legacy each change is its own commit. A delta built
  on it still has to read the current rows (D3).
- **Legacy reads adopt hand edits** through `_maybe_scan_on_read`, throttled to
  once every 2 s (`store.py:101`, `:3244-3271`). A cheap revision check on legacy
  has to run the same scan first, or a hand edit would be answered with 304.

## 2. Concrete contract proposal

### 2.1 Endpoints (D1)

| Route | Purpose | Conditional | Notes |
|---|---|---|---|
| `GET /api/board` | Board DTO (§2.3) | `If-None-Match` → **304, no body** | New. The viewer's only poll target |
| `GET /api/board?since=<token>` | Scoped delta (§2.4) | 304 when `<token>` is current | Same route. Answers a delta, or a full DTO marked `resync` |
| `GET /api/task/<id>/detail` | Task, related, claim and per-task ETag from **one** snapshot (§2.5) | none | New. Replaces the two parallel detail GETs |
| `GET /api/backlog` | Compatibility | 304 as well | Keeps its documented shape (`docs/TASKMASTER.md:353`) **minus `_rows`**. The viewer stops calling it |
| `GET /api/task/<id>`, `/related`, `/api/epic/<id>` | Unchanged shape | none | `task/<id>` gains the per-task ETag (D5) |

### 2.2 Revision, ETag and 304

- **Board revision** = `(store identity, board-scope sequence, DTO_VERSION, VERSION)`.
  The board-scope sequence is `MAX(seq)` over the rows the DTO reads: tasks, epics,
  phases and the backlog document (D2). Native uses `entity_core.last_seq` for
  `kind IN (…)`. Legacy uses `entities.updated_seq`, **after** `scan_for_read`.
  Legacy on a network share (projection-only) uses `_projection_identity()` and never
  answers a delta.
- `ETag: "b1:<store_id>:<scope_seq>:<VERSION>"`. It is strong: the body is a pure
  function of it (§5.2(1)).
- **The 304 decision runs before any construction.** It is one read transaction
  that reads the identity and the scope sequence, then answers 304 with an
  `ETag` header and no body. There is no tree build, no DTO build and no row decode.
- Every response carries `Server-Timing: rev;dur=…, build;dur=…, encode;dur=…`,
  plus `Content-Length`. This is how server construction is measured without
  instrumenting the harness (§5.3). It is also visible in DevTools.
- `/api/backlog` gets the same 304, keyed on the **store-wide** identity it already
  sends, because its body includes every kind.

### 2.3 Board DTO (version `b1`)

```jsonc
{
  "revision": "b1:<store_id>:<scope_seq>:<VERSION>",   // same as the ETag
  "cursor":   "<opaque delta token>",                 // §2.4
  "tasks":  [ { /* one row per board task, once */ } ],
  "epics":  [ { "id","name","status","last_referenced","done_when","design_status" } ],
  "phases": [ { "id","name","status","order" } ]      // sorted by order, as today
}
```

- **Task row fields, exactly the §1.3 list:** `id, title, status, priority, epic, phase,
  area, branch, estimate, created, started, completed, bundle, docs, tracker_id,
  spec_review:{verdict}, depends_on, sub_repo, lane, gate_state,
  merge_gate_state, human_action, blockers_count, archived_reason`.
  - The `order` field is kept too, for the delta ordering rule.
  - Absent values are **omitted**, not sent as `null`, so the bytes stay small.
  - `blockers` becomes `blockers_count`, the only thing a card reads (`card.js:228-232`
    changes accordingly).
  - The board row carries **no claim field** (D6).
- **Inclusion:** the task rows of today's board, in today's order:
  - archived tasks are included (D4);
  - orphan tasks (whose epic is missing) are excluded, as `reads.tree` excludes them;
  - order is epic creation order, then `(order, id)`.
- **No `context`.** `active_epic` is derived on the client from the DTO, with the
  same rule `_derive_context` uses (D9). This removes the only
  `SESSION_ID`-dependent content (§1.2).
- **One field list, two languages.** `taskmaster/viewer_dto.py` declares
  `BOARD_TASK_FIELDS`, `BOARD_EPIC_FIELDS` and `BOARD_PHASE_FIELDS`.
  `viewer/js/lib/board-fields.js` exports the same lists. A test asserts they are
  equal. Adding a card field then fails a test until both sides agree.
- **One builder, two stores.** `build_board(task_docs, epic_docs, phase_docs)` is
  pure and store-agnostic.
  - Native feeds it from bounded `snapshot.list` pages with `fields=` restricted to
    the DTO fields. No `_body` and no `bodies()` query.
  - Legacy feeds it from its cached dict (D8).
  - One renderer, as N11's rule for projections requires.

### 2.4 Scoped deltas (D3)

- **Token** = the `revision` of the state the client holds (`b1:<store_id>:<seq>:<VERSION>`).
  The client sends `?since=<token>` with `If-None-Match: "<token>"`.
- **Server, in one read snapshot:**
  1. Identity or `VERSION` differs, or the token does not parse →
     **200 full DTO with `"resync": "<reason>"`** (`store_changed`,
     `version_changed`, `bad_token`).
  2. `scope_seq == token.seq` → **304**.
  3. Read the board rows with `seq > token.seq`.
  4. If more than `DELTA_MAX` rows (default 200) changed → full DTO with
     `resync: "too_many"`.
  5. If any epic or phase row changed: when an epic **left** the board (a legacy
     soft delete), send the full DTO with `resync: "epic_removed"`, because its
     tasks orphan without their own sequence moving. Otherwise include the complete
     `epics` and `phases` arrays (they are small).
  6. Tasks: every changed row that satisfies the inclusion predicate is an
     **upsert** (a full DTO row). Every changed row that does not (deleted, or
     now orphaned) is a **removal** by id.
- **Delta body:**
  `{ "revision", "cursor", "since", "tasks_upsert": [...], "tasks_remove": [ids], "epics"?: [...], "phases"?: [...] }`.
- **Commit boundaries hold by construction:** the whole delta is read in one
  snapshot and never paged. A client can never hold half of a multi-entity commit
  (design §9). The cap turns a large delta into a full resync, not a page.
- **Removal needs no before-state:** the server judges each changed row's
  *current* membership, and the client removes idempotently.
- **Filter membership stays on the client:** `applyFilters` and `groupTasks`
  (`filters.js:9-127`) re-run over the patched task array on the next paint. A
  priority, epic or phase change moves a card in or out of the filtered view
  without a server-side filter scope.

### 2.5 Detail: one snapshot, targeted reads, a real precondition

- **`GET /api/task/<id>/detail`** returns
  `{ task, related, claim, etag }` from one read.
  - Native reads the task, its epic, the handover and issue membership and the
    dependency statuses with targeted queries (`reads.find_task`,
    `snapshot.list` filters). There is no `reads.tree` and no row materialization.
  - Legacy builds the same shape from its one `_load_snapshot`, so there is one tree
    instead of two (D8).
  - `task` is today's `/api/task/<id>` body, byte for byte except the claim fields
    (below). `related` is today's `/related` body.
- **Per-task ETag (D5).**
  - Format: `"t1:<store_id>:<task row seq>"`. Native reads it from
    `entity_core.last_seq`, legacy from `entities.updated_seq`.
  - Returned by `/detail`, `/api/task/<id>` and each task write's response.
  - `If-Match` on `PATCH`, `PUT` and archive accepts **either** a per-task ETag,
    compared with that task's row inside the writer lock, **or** the old store-wide
    form, compared exactly as today. Old clients and tests keep their semantics.
  - The stale answer is unchanged: 409 `{error:"stale", current, current_etag}`.
    `current_etag` is now the per-task form.
- **Claim display (D6).** `claim` =
  `claims.read(...).as_dict()` → `{holder, expires_at, live, expired, state}`,
  computed at read time. `task` no longer carries `locked_by`, `claim_expires` or
  `claim_expires_for`. The banner shows only when `state == "held"` and
  `!expired`, and the text names the expiry. `/api/task/<id>` keeps `locked_by`
  for compatibility but adds `claim`. The detail route is not conditional, so the
  wall clock cannot hide behind a 304.
- **Native write path:** the precondition is checked by the command itself
  (`workflow._viewer_precondition`, extended for the per-task form). The pre-check
  `snapshot()` and the response `snapshot()` in `_task_update`/`_task_archive`
  become an identity read and a targeted task read.

### 2.6 Client contract

- **`api.js`:**
  - `board(sinceToken)` sends `If-None-Match` and `?since=`, and returns
    `{status: 304}` or the parsed body.
  - Every JSON GET goes through `http()`, so ETag capture applies to detail reads
    too. The raw `fetch` in `getTask`/`getTaskRelated`/`getEpic` goes away.
  - A 304 carries no body and is never parsed.
- **`store.js`:**
  - `setBoard(full)` and `applyDelta(delta)`. The pure function lives in new
    `lib/board-delta.js`: upsert by id, remove by id, replace epics/phases when
    present, then re-sort tasks by (epic creation index, `order`, `id`).
  - Emit when `revision` changes. The `jsonEqual` stringify pair goes.
  - Keep the `backlog` subscription key and the `getBacklog()` shape
    (`{tasks, epics, phases}`) so every screen keeps working unchanged.
    `context.active_epic` becomes a getter backed by `lib/epics.js`.
- **`main.js`:** the poll sends the held token and ignores a 304 (no emit, no
  parse). It applies a delta, or replaces everything on `resync`. On any
  delta-apply exception it falls back to one full `GET /api/board`.
- **After a viewer edit:** the task write's response carries the new task and
  ETag, and the client runs one `board(since)` instead of a full backlog refetch
  (`task-detail-document.js:19`, `task-actions.js:47,60`).
- **Detail cache:** entries are keyed by id and tagged with the task's board-row
  `revision`/`seq`. A delta that upserts or removes the id invalidates the entry.
  An open detail with **no local edit in progress** re-fetches. One **with** a
  local edit in progress keeps the draft, and the next save meets the per-task
  precondition and gets today's conflict banner.
- **Unknown task:** a detail for an id that is not on the board, or that is
  removed while open, keeps today's "Could not load" / 404 behaviour. The modal
  never throws. A delta naming an id the client never saw is an upsert.

## 3. Step breakdown

Ten steps. Each is `test-first`: a failing behavioural test commit, then the
implementation commit.

**Ownership, to avoid N09's integration debt.** Two tracks after S1. **Each shared
file has exactly one owner.**

## 4. The open decisions

### D1: A new `/api/board`, or reshape `/api/backlog`?

**Options.** (a) A new `/api/board` for the DTO, with `/api/backlog` kept in its
documented shape minus `_rows`, plus a 304. (b) Turn `/api/backlog` into the DTO.
(c) Keep `/api/backlog` fully unchanged.

**Recommendation: (a).** `/api/backlog` is documented (`docs/TASKMASTER.md:353`),
parsed by `scripts/benchmark_performance_audit.py`, and asserted in
`test_phase_ordering.py`, `test_store_bypass.py`, `test_viewer_reads_rows.py` and the
twin parity test. (b) breaks each of them for no gain. `_rows` goes in every
case: it is private, no client reads it, and native already ships a repr.

### D2: Store-wide sequence, or a board-scope revision?

**Options.** (a) Store-wide (`event_high_water` / `MAX(changes.seq)`), as the ETags use today.
(b) `MAX(seq)` over the rows the DTO reads.

**Recommendation: (b).** On a store with agents working, bug, handover, note and
decision writes are frequent. Under (a) each one costs every open board a full
rebuild and download. The risk with (b) is a future DTO field that reads another kind while the
revision does not include it. §5.2(1) closes that with a property test that
mutates every non-scope kind and asserts identical DTO bytes, plus the rule that
`viewer_dto.py` declares its input kinds next to its field lists.

### D3: What backs deltas: row sequences, or the N09 feed?

**Options.** (a) Changed rows by `updated_seq` / `last_seq` in one snapshot
(§2.4). (b) `backlog_changes_since` for the id list, then a row read.

**Recommendation: (a).** The feed returns field names, not values, so (b) still
needs (a)'s row read, plus cursor, floor and scope-signature machinery that the
board does not need. Legacy has no commit grouping, and the feed's paging adds a
half-commit hazard that a single-snapshot read does not have. Row sequences exist
on both stores, and legacy's cache refresh already uses them (`store.py:2719-2745`).
This means **N09's feed is not reused**. The plan said it "may" back deltas. The
report should say why not. The feed stays the agent interface.

### D4: Do archived tasks stay on the board?

**Options.** (a) Keep them as compact rows. (b) Move the archived screen to its
own endpoint.

**Recommendation: (a) for N10, measured in S1/S9.** The archived screen, the
epics progress bars (`epics.js:41-42`) and the relation picker read them from the
board. A compact row is a few hundred bytes. If S1 shows that archived rows
dominate the CodeMaestro DTO, (b) becomes an N16 input, not an N10 change.

### D5: What is the edit precondition?

**Options.** (a) Keep the store-wide ETag and only fix capture, so the first edit
is conditioned too. (b) A per-task ETag from the detail read and task writes, with
the store-wide form still accepted. (c) Change nothing.

**Recommendation: (b).** (c) keeps a precondition that the first edit never has
(§1.5). (a) makes that precondition real, but then every unrelated agent write
produces a conflict banner: correct in form, and it teaches the user to press
"keep mine". (b) is standard HTTP (one ETag per resource). It detects exactly the
conflicts that can lose a field. Accepting the old form keeps every existing
caller's semantics. **This is a user-visible change:** fewer spurious 409s, and
the first edit can now return a 409 where it could not before.

### D6: Where does claim state live in the viewer?

**Options.** (a) Only in the detail read, as a computed `claim` object with the
banner gated on it, and no claim fields on the board. (b) Claim fields on the
board with expiry computed on the client from `expires_at`. (c) Raw `locked_by`
everywhere, as today.

**Recommendation: (a).** Claim state depends on the clock and on process
liveness (§1.6), so it cannot be keyed by a committed-state 304. (b) would still
miss the dead-holder rule, which only the server can judge. No list screen reads
a claim field today. The detail route is unconditional, so each open or refresh
re-judges the claim. `context.in_progress[].locked_by` leaves with `context`.

### D7: Transport

**Recommendation: keep the 3 s poll with 304s and deltas. No SSE in N10.** A 304
is a few hundred bytes and one indexed `MAX`. SSE adds connection lifecycle,
server threads per tab, and reconnect/resync logic. That belongs with N12's
coordinator, if anywhere.

### D8: Legacy construction depth

**Options.** (a) Same wire contract on legacy (304, DTO, deltas, `/detail`), built
from its cached dict. Only the revision read and the delta row read are new SQL.
(b) Native-only N10, with legacy keeping today's payload.

**Recommendation: (a).** Every project is legacy until N15, and the viewer must
have one client path. Legacy's 304 is cheap anyway (scan, then two `MAX` queries).
What legacy keeps is the deep copy of the cached dict per rebuild
(`store.py:2726`); that is recorded for N16, not optimized here.

### D9: Where does `context.active_epic` come from?

**Recommendation: derive it on the client from the DTO** (most
in-progress/in-review tasks, ties alphabetical, else the first active epic
alphabetically, else the first epic). It is the only `context` key with a
consumer. Serving `context` would force the board to recompute
`_derive_context` over every task on each rebuild, and would bring back the
`SESSION_ID` dependence. A unit test pins parity with `_derive_context` on the
golden fixtures.

### D10: The `depends_on_unmet_count` read that nothing produces

**Recommendation: leave it unproduced in N10 and file it as a bug.** Producing it
is a new board feature: a dependency-status join per task, and a card badge that
has never shown. It is not a DTO concern. Record it in the report as a
consumer with no producer.

## 5. Risks, and what the proof method can and cannot prove

### 5.1 How the browser checks run

- **Tool: Playwright**, since the repo already has it (§1.8). Add a new project
  config, `viewer/tests/playwright.n10.config.js`, with two projects,
  `legacy` and `native`.
  - Each `webServer` runs `scripts/viewer_fixture_server.py --store {legacy|native}
    --port …` on a **seeded scratch root**, built with `tests/native_twins.py`'s
    `scaffold` and `activate_native`.
  - Peer writes come from the fixture's `ctl` sub-command, which calls the real
    tool functions against that root and is invoked by the spec through
    `child_process`. The browser therefore sees writes from a different process,
    as it would from an agent.
  - Never run this suite against the live `.taskmaster`. `run_smoke.sh` stays
    as it is.
- **Browsers:** Chromium for everything. The conditional-GET spec also runs on
  Firefox (installed), because a 304 that reaches the application when
  `If-None-Match` is set manually is Fetch-spec behaviour that N10 depends on (§5.4).
- **Exit specs (S9), each on both stores:**
  1. **Unchanged board:** after load, N polls answer **304 with a zero-length body**
     (CDP `Network.responseReceived` status and `encodedDataLength`). There is no
     `backlog` emit, counted through a test hook on `store.subscribe`.
  2. **No duplicate task payloads:** the board response has each task id exactly
     once, no `_rows` and no `context`, and every key is in the field lists.
  3. **Detail editing:**
     - An inline edit sends `If-Match` on the **first** save and succeeds.
     - A peer write to *another* task between open and save does not conflict.
     - A peer write to *the same* task gives the conflict banner. "Keep mine" and
       "use server" both leave the store and the page in agreement.
     - The board card reflects the edit through a delta, not a full refetch.
  4. **Navigation:**
     - Modal open, dependency click-through, "Open full", back and Escape.
     - Re-opening after a peer write shows the new value.
     - A task removed while open shows the not-found state without a console error.
     - An unknown id in the URL shows the same.
  5. **Filter membership:** with a priority filter, then an epic filter, then a
     phase filter active, a peer write moves a task into or out of the filter. The
     card appears or disappears within one poll, **the response was a delta**, and
     no reload happened.
  6. **Claims:** a live peer claim shows the banner with its expiry. An expired
     claim, a `done` task with a stale holder and a dead holder show none.
  7. **Resync:** a store swap (a new scratch root under the same port) and a
     200-plus-row batch both resync to a board equal to a fresh load.
- **Claude-in-Chrome** is used only for a reviewer's manual look at the
  CodeMaestro copy (layout, scroll position kept across deltas). It is **not**
  exit evidence: one tab, not repeatable, no CDP heap access.

### 5.2 Oracles

1. **304 soundness (server property test, both stores):** for random operation
   sequences, whenever two reads return the same board ETag, their full DTO
   bytes are identical.
   - Writes to every non-board kind leave the ETag *and* the bytes unchanged.
   - Writes to every board kind change the ETag.
   - The DTO is a pure function of the ETag's inputs: tested under a moving fake
     clock and under two `SESSION_ID`s.
2. **Delta soundness (server and client):**
   - For random sequences, `apply(full(s0), delta(s0→sN)) == full(sN)`.
   - Deep-equal includes array order.
   - Checked in pytest over the JSON, in node over `board-delta.js`, and once in
     the browser against the store's own state (S9 spec 7).
3. **Twin parity:** legacy and native DTO, delta and `/detail` bytes are equal
   (the existing `Twins` harness; `test_native_routing_viewer.py:111-123`
   extended).
4. **Consumer parity:** each board screen (kanban, table, epics, archived, the
   issues status lookup, the relation picker) renders **the same DOM text**
   from the S1 full payload and from the DTO. This is route-mocked Playwright
   with a DOM text snapshot per screen. It proves the consumers were updated
   before fields were removed, which the plan requires.

### 5.3 Measurement (the plan's four quantities, never UI from HTTP)

| Quantity | How | Where |
|---|---|---|
| Wire bytes | `Content-Length` and CDP `encodedDataLength` per response: full, 304, delta, `/detail`, old `/api/backlog` | fixture and CodeMaestro copy, both stores |
| Server construction | `Server-Timing` (`rev`, `build`, `encode`); `native_n10_viewer_bench.py` calls the builders directly (median of 20, warm and cold) | same |
| Client parse/render | User Timing marks in `main.js`/`store.js`/`kanban.js` (`tm:fetch`, `tm:parse`, `tm:apply`, `tm:paint`), read by Playwright from `performance.getEntriesByType('measure')` | Chromium |
| Heap | CDP `HeapProfiler.collectGarbage`, then `Runtime.getHeapUsage` after load, after 50 idle polls and after 50 deltas; median of 5 runs | Chromium |
| Responsiveness | **Long tasks** (`PerformanceObserver('longtask')`) during 60 s of polling, and Event Timing for a card click → modal painted. HTTP timings are never used as a proxy | Chromium |

- The CodeMaestro run uses a fresh scratchpad copy, as N09 and N11 did. Raw output
  goes to ignored `test-results/n10-*`, and the live checkout is never opened.
- Before and after are the S1 baseline versus S9 on the same copy and machine.
- **No DTO size is claimed in advance.** The roadmap's 16.2 MB is legacy-only and
  pre-native, and S1 re-measures it.

### 5.4 What this proof cannot show

- **Other browsers and real users.** Chromium and Firefox headless on one machine.
  Perceived responsiveness on a slow laptop, or with twenty tabs open, is not
  measured. Long-task and Event Timing are proxies for it.
- **Proxies and caches.** No intermediary sits between the viewer and a loopback
  server. The 304 path assumes none does, and JSON responses stay uncached
  (`_send_json`'s comment).
- **Future DTO fields.** The field-list equality test and the §5.2(1) property
  test catch a field added on one side, or one read from an unscoped kind. They
  cannot catch a client reading a field through a computed key that the grep
  inventory missed. The consumer-parity DOM snapshots (§5.2(4)) are the backstop
  for today's screens only.
- **Legacy hand edits** reach the board up to 2 s after the edit, because of the scan throttle (§1.7). That
  is today's behaviour for every read, not a new window.
- **Scale beyond CodeMaestro** (about 2.5k tasks). `DELTA_MAX` and archived-row weight are
  tuned on that one board.

### 5.5 Risks specific to N10

- **A stale 304 is the failure to fear most.** It is silent: the board just stops
  updating. Every cause is a DTO input outside the revision. Candidates:
  - derived content (`context`, which is removed);
  - `VERSION` (in the ETag);
  - the legacy scan (run before the revision read);
  - an epic removal orphaning tasks (a resync);
  - a projection-only share (identity from the projection).

  §5.2(1) tests each one separately.
- **Delta ordering drift.** The board's array order is part of what screens
  render (table default order, bundle clustering). The client re-sort has to use
  the server's order key, and §5.2(2) compares order, not just membership.
- **A draft lost to a refresh.** Invalidating an open detail on a delta must not
  replace an in-progress edit. The per-task precondition, not the refresh, decides
  conflicts (S8 test).
- **D5 changes when 409s happen.** The first edit can now conflict, and
  unrelated writes no longer do. The report lists it as an intentional difference.
  `test_server_etag.py` must pass unmodified, as the proof that the store-wide form
  is unchanged.
- **Twins drift on legacy's cached dict.** Legacy builds the DTO from the dict
  and native from bounded reads. Field shapes (priority normalization, the
  `created` fallback in `_normalize_task`) must pass through one normalizer in
  `viewer_dto.py`, or §5.2(3) fails on real data but not on the fixture. The
  CodeMaestro copy has to run the twin comparison, not only the timing.
- **The N02 contract fixture and the bypass gate.** New routes change
  `tests/fixtures/native_contracts.json` and need a bypass-gate exercise
  (`test_native_bypass_gate.py:357`). N11 was hit by an un-regenerated inventory
  fixture, and S3 regenerates it in the same commit.
- **Out of scope, still broken:** `GET /api/dashboard/recent-events` drops the
  connection on tool-created tasks on both stores (pinned by
  `test_native_routing_viewer.py:103-108`). The desk screen, not the board, depends
  on it. It is not N10's to fix, and the report should keep it visible.
